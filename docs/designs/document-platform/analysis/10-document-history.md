# 10 · Document History

## Objective

Define how every generated document is logged, what the history records, and how it integrates
with the Documents module — using **both** a document-scoped event log **and** the existing
unified audit trail (correction #8).

---

## 1. Two complementary trails (not either/or)

| Trail | Table | Role | Why both |
|-------|-------|------|----------|
| **Document lifecycle events** | `document_events` (new) | Fast, document-scoped history: issue, print, reprint, regenerate, void; print counts; delivery. Powers the module's per-document timeline and the "print count" column. | Cheap, targeted queries per document; carries document-specific metadata (page count, delivery channel) that doesn't belong in a generic audit row. |
| **Unified audit / security trail** | `activity_events` (existing) | Records the **important audit/security actions** (issued, voided, and — where relevant — regenerated) into the clinic-wide, append-only, spoof-proof timeline already used for accountability. | Keeps document actions visible in the one place the clinic already reviews operational accountability; reuses the SECURITY DEFINER write boundary that stamps the actor server-side. |

This mirrors the codebase's own precedent: `activity_events` already coexists with a generic
`audit_logs`. We follow the same "semantic timeline + targeted log" split.

---

## 2. What history records (minimum, per the requirement)

For every generated (issued) document:

- **Document number** — the immutable visible number.
- **Document type** — from the catalog.
- **Generated by** — the issuing user (actor).
- **Generation date** — issue timestamp.
- **Print history** — each print/reprint event with actor + timestamp (+ running count).
- **Regeneration history** — links between an original and any regenerated successor(s).
- **Verification identifier** — the opaque token (and thus the verification URL).

`document_events` captures these as append-only rows; the `documents` row holds the current
aggregate (issued_by, issued_at, print_count, status, token).

---

## 3. `document_events` shape

```
document_events (
  id          uuid pk,
  clinic_id   uuid not null,
  document_id uuid not null references documents(id),
  event       text not null,   -- 'issued' | 'printed' | 'reprinted' | 'regenerated'
                               -- | 'voided' | 'delivered'
  actor_id    uuid null,        -- null = system
  is_system   boolean default false,
  metadata    jsonb default '{}',  -- page_count, delivery_channel (whatsapp|email), successor_document_id, …
  occurred_at timestamptz default now()
)
```

- **Append-only**: corrections are new events; history is never rewritten (matching the
  `activity_events` invariant).
- **Write boundary**: events are written only by the document server actions (and the issue/
  reprint/void RPCs), never by arbitrary client writes.
- **Read scope**: RLS scopes rows to the clinic and to users authorized for the document
  (mirrors the module's authorization, doc 08 §6).

---

## 4. Integration with the Documents module

- The module list surfaces aggregate history columns (issued by, issue date, print count,
  status) straight from the `documents` row.
- `/documents/[id]` renders the full **event timeline** from `document_events` (issued → printed
  ×N → reprinted → delivered → …).
- **Quick access from originating surfaces**: each surface links into the module filtered to its
  context (this patient's documents, this period's revenue documents, this staff member's files),
  giving the "quick access to history" the requirement asks for.
- Security-relevant actions (issue, void, regenerate) also appear in the existing unified
  activity timeline, so an admin auditing accountability sees document actions in context with
  everything else.

---

## 5. Retention

Issued documents, their snapshots, their PDFs, and their events are **retained** even after
void/cancel (SHARED_REQUIREMENTS §11 — retired, not deleted). History is durable evidence that a
document existed and what happened to it.
