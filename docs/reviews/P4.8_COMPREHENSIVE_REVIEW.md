# ClinicFlow — Phase P4.8 Comprehensive Review

**Phase:** P4.8 — Contextual Assistant Launchers & Page-Context Contract  
**Scope:** P4.8A + P4.8B  
**Review type:** Comprehensive implementation, security, UX, documentation, and validation review  
**Date:** 2026-07-22  
**Branch:** `feat/p48a-ai-actions`  
**Baseline commit:** `52ecdd2`  
**Code changes made by this review:** None  
**Roadmap changes made by this review:** None

## Verdict: **APPROVED WITH FIXES**

P4.8 has the correct overall architecture. The reusable launcher is deny-by-default, page-time serialization is small, expensive history/capability hydration is deferred until first open, both server boundaries parse the strict context union, patient context is independently re-authorized, non-patient context cannot affect the tool mount, and all actual data access remains behind the existing per-tool authorization, RLS/RPC, auditing, billing, usage, and provider-execution controls.

No High-severity issue was found. In particular, this review found no cross-tenant access, PHI exposure, privilege escalation, unauthorized clinical tool, service-role regression, billing/usage bypass, audit bypass, mutable AI action, generic query surface, or P4.9 implementation.

Three Medium findings prevent an unconditional approval:

1. report-context suggestions check only whether the generic report tool is mounted, not whether the current report is allowed for this role and financial grant;
2. revenue context claims visible department/doctor filters that the supporting financial tools cannot apply; and
3. the new deferred hydration endpoint has no abuse-rate or request-size control.

Four Low findings cover doctor-schedule context accuracy, the roadmap's missing-schema failure contract, asynchronous error accessibility, and insufficient scenario-level regression coverage/documentation accuracy.

The Medium findings should be closed before merge. The Low findings should be fixed in the same correction pass or explicitly carried into the focused re-review.

### Medium

#### P48-M1 — Report suggestions are not authorized at the specific-report level

**Evidence**

- [`suggestionsFor`](../../components/assistant/assistant-chat.tsx#L421) offers both current-report prompts whenever `capabilities.toolNames` contains the generic `run_clinic_report` tool.
- The report tool deliberately remains mounted when only some reports are allowed. Its actual authorization is report-specific: `revenue` is financial, `followups` excludes managers, and the two performance reports exclude receptionists ([`run-clinic-report.ts`](../../lib/ai/tools/run-clinic-report.ts#L76), [`allowedReportsForRole`](../../lib/ai/tools/run-clinic-report.ts#L150)).
- The launcher registry has one coarse `reports` definition for admin, manager, and receptionist and requires only `ai.staff_analytics`; it does not apply the current report's role/financial requirements ([`launchers.ts`](../../lib/ai/launchers.ts#L90)).
- The page-context report ids are `doctors` and `receptionists`, while the tool contract uses `doctor_performance` and `receptionist_performance` ([`page-context.ts`](../../lib/ai/page-context.ts#L83), [`run-clinic-report.ts`](../../lib/ai/tools/run-clinic-report.ts#L33)).

**Impact**

A manager without the personal financial grant can open the existing revenue report page, receive the Reports launcher, and see “Summarize the report I'm viewing” because `run_clinic_report` is mounted for their non-financial reports. The same tool will refuse `revenue`. The UI therefore advertises a contextual operation that the server-derived report policy explicitly withholds. The id mismatch also makes the doctor/receptionist performance contexts less deterministic for the model.

No unauthorized report data is returned: the tool's execution guard and underlying RPC still deny it. This is a capability-honesty and functional-correctness defect, not a data-access bypass.

**Required remediation**

- Define one shared report-id vocabulary for page context and `run_clinic_report`; use `ClinicReportId` or a shared explicit route-to-tool mapping rather than separate string unions.
- Derive structured `allowedReportIds` from the same report registry, role, entitlement, and user-permission resolution used by the tool description.
- Render a current-report suggestion only when the exact normalized context report id is in that allowed set.
- Apply the financial gate to the revenue-report contextual affordance, or keep the general Reports launcher but suppress every revenue-specific suggestion and state clearly that the current report cannot be analyzed.
- Add a role × report × financial-grant matrix test, including manager-without-grant on `revenue`, manager on `followups`, receptionist on both performance reports, and the two route/id mappings.

#### P48-M2 — Filtered revenue context can produce unfiltered financial answers

**Evidence**

- `/revenue` serializes the visible `departmentId` and `doctorId` into page context ([`revenue/page.tsx`](../../app/(protected)/revenue/page.tsx#L184)).
- The prompt tells the model that the user is viewing revenue filtered by those ids ([`page-context.ts`](../../lib/ai/page-context.ts#L177)).
- The UI offers “Summarize revenue”, period comparison, and outstanding-balance prompts whenever the corresponding financial tool name is present ([`assistant-chat.tsx`](../../components/assistant/assistant-chat.tsx#L410)).
- `get_revenue_summary` accepts only a date range and sends only `p_start`/`p_end` to its RPC ([`get-revenue-summary.ts`](../../lib/ai/tools/get-revenue-summary.ts#L23)). `compare_revenue_periods` also accepts only two periods ([`compare-revenue-periods.ts`](../../lib/ai/tools/compare-revenue-periods.ts#L24)). `list_outstanding_invoices` accepts only a range and limit ([`list-outstanding-invoices.ts`](../../lib/ai/tools/list-outstanding-invoices.ts#L37)). None can apply the department or doctor filters represented by the context.

**Impact**

On a filtered revenue page, the model can reasonably interpret the advisory context and suggestion as a request to summarize the visible subset, while the only supporting tools return clinic-wide values for the date range. That can present an unfiltered financial total as if it reconciled with the visible filtered page. The tool data remains authorized and same-tenant, but the answer can be materially wrong.

**Required remediation**

Choose one honest contract:

- preferred if already supported by the existing report core: extend the relevant AI financial tools/RPCs with independently validated, clinic-scoped doctor/department filters and return the applied-filter metadata; or
- minimal P4.8 correction: omit unsupported filters from the context, change the page description/prompt to say the assistant can use only the visible date range, and suppress wording that implies reconciliation with the filtered view.

Add fixtures proving that a filtered page either produces the same filtered totals as the page or explicitly does not claim to summarize that subset.

#### P48-M3 — The deferred session endpoint is not rate- or size-limited

**Evidence**

- `POST /api/agent/launcher-session` authenticates and then parses the entire request body before resolving launcher state, history, usage, permissions, and capabilities, with no `checkRateLimit` call or request-size check ([`launcher-session/route.ts`](../../app/api/agent/launcher-session/route.ts#L39)).
- The streaming chat route does apply a 30-per-minute clinic rate limit before body parsing and expensive work ([`chat/route.ts`](../../app/api/agent/chat/route.ts#L92)).
- Current route tests cover authentication mappings, malformed context, no-store responses, and fail-closed resolution, but no throttling or oversized payload behavior ([`p48a-launcher-session-route.test.ts`](../../tests/unit/api/p48a-launcher-session-route.test.ts#L60)).

**Impact**

Any authenticated staff account can repeatedly invoke a read-heavy boundary that performs multiple authorization/entitlement/usage queries, conversation/history reads, and capability resolution. It cannot spend model budget or cross authorization boundaries, but it can amplify database and server load outside the established assistant abuse control. An oversized JSON body is also fully materialized before validation.

**Required remediation**

- Add a dedicated per-user or per-user-and-clinic launcher-session rate-limit key after authentication and before JSON parsing/resolution; return `429` with `Retry-After`.
- Enforce a small request-body ceiling suitable for the compact context contract before calling `request.json()`.
- Preserve fail-closed launcher authorization and `private, no-store` response headers.
- Test allowed bursts, throttled requests, backend-failure behavior, oversized requests, and that throttled/oversized requests never call the session resolver.

### Low

#### P48-L1 — Doctor-schedule context does not describe its actual host

The launcher is mounted inside the recurring weekday working-hours editor, which loads `getDoctorSchedule(doctorId)` and displays days of week and start/end times ([`staff-profile-sheet.tsx`](../../components/settings/staff-profile-sheet.tsx#L430)). The server page nevertheless synthesizes the current Monday–Sunday range and shares it as though it were visible ([`settings/staff/page.tsx`](../../app/(protected)/settings/staff/page.tsx#L22)). The prompt says the user is viewing a doctor schedule “for” those dates, and suggestions offer clinic appointments and availability for that fabricated range. The context also intentionally omits the sheet's doctor id, so those suggestions cannot target the doctor whose schedule is open.

The help suggestion is valid; the two date/availability suggestions are not contextual to the host.

**Remediation:** until a safely server-bound per-doctor context exists, describe this host as the recurring working-hours editor, remove the fabricated date range, and expose only the schedule-help suggestion. If a future context includes the doctor identity, re-authorize it at first-open and chat boundaries exactly like other advisory ids and still keep tool authorization independent.

#### P48-L2 — Missing persistence no longer silently omits the patient launcher

The authoritative roadmap says missing `agent_conversations`/`agent_messages` must silently omit the patient launcher ([`AI_AGENT_PLAN.md`](../AI_AGENT_PLAN.md#L669)). The lightweight page resolver checks page visibility, features, subscription, usage, role, and optional permission, but not persistence ([`launchers.ts`](../../lib/ai/launchers.ts#L157), [`surface.ts`](../../lib/ai/surface.ts#L27)). With a missing migration, the patient launcher can render and then change to the retryable unavailable state on first open.

This remains fail-soft—the patient page does not fail and no data leaks—but it differs from the roadmap and from the implementation report's claim that persistence is part of launcher gating.

**Remediation:** add a lightweight cached deployment/persistence readiness signal that does not load conversation history at page render, or otherwise reconcile the implementation with the existing silent-omission contract without restoring eager history/capability hydration.

#### P48-L3 — Asynchronous launcher failure is not announced to assistive technology

The loading state is a polite live status, but the state that replaces it after a failed first-open request has no `role="alert"`, `role="status"`, or live-region semantics ([`assistant-launcher.tsx`](../../components/assistant/assistant-launcher.tsx#L157)). Keyboard users can reach the retry button, but a screen-reader user may not be told that loading changed to failure.

**Remediation:** announce the failure with an appropriate live status/alert while avoiding duplicate dialog announcements, and add an accessibility assertion for the asynchronous transition and retry focus behavior.

#### P48-L4 — Tests and documentation overstate scenario-level coverage

The focused suites are broad and all pass, but important host assertions are source-text checks rather than rendered page or flow tests ([`p48a-entry-points.test.ts`](../../tests/unit/components/p48a-entry-points.test.ts#L9)). The contextual-suggestion test supplies a synthetic `toolNames: ["run_clinic_report"]` value and checks only one allowed `no_shows` case; it does not exercise report-specific role/grant policy. There is no P4.8 browser test for authorized/unauthorized host rendering, nested Dialog → Sheet focus/RTL behavior, or the new hydration endpoint's abuse controls.

The P4.8B report also calls `doctors`/`receptionists` “exact report id,” calls the recurring-hours screen a “current visible week,” and says contextual prompts are absent whenever the capability is not supported ([`P4_8B_IMPLEMENTATION.md`](../reports/P4_8B_IMPLEMENTATION.md#L16), [`P4_8B_IMPLEMENTATION.md`](../reports/P4_8B_IMPLEMENTATION.md#L47)); P48-M1 and P48-L1 show those claims are too strong.

**Remediation:** add direct tests for the scenarios in P48-M1–M3 and P48-L1–L3, at least one English and one Arabic/RTL browser flow across a top-level and nested launcher, and correct the implementation report after the fixes are verified.

## 4. Deferred hydration, serialization, UX, i18n, RTL, accessibility, and performance

### Deferred hydration and serialization

Pass.

- Closed launchers serialize only strict context, role, and the patient-only presentation label where applicable.
- Conversation history, capabilities, the chat component, and AI SDK/tool-presentation dependencies load only after first Sheet open.
- The fresh production manifests include `assistant-launcher` on P4.8 host pages but include `assistant-chat` only on the standalone Assistant page; the launcher invokes it through an event-time dynamic import.
- The session response is authenticated and `Cache-Control: private, no-store`.
- Repeated first-open events are deduplicated and successful hydration remains mounted for that launcher instance.

P48-M3 is the remaining performance/abuse-control gap. The two pages with nested launchers also repeat some page visibility/usage work per launcher, but the expensive history/capability path remains deferred and the current duplication is not severe enough to classify separately.

### English/Arabic and RTL

Pass for key parity, interpolation parity, logical layout, and static RTL validation.

- All P4.8 launcher and suggestion keys exist in English and Arabic with matching variables.
- The Sheet uses `side="inline-end"`; new layout classes are logical.
- `pnpm lint:i18n`, message missing/unused checks, and `pnpm lint:rtl` pass.

P48-L1 is a semantic parity issue shared by both languages rather than a translation-key mismatch.

### Accessibility and UX

Mostly pass.

- Trigger buttons have text labels; Sheet title/description are wired; loading has a polite status; dialogs use logical direction; retry is keyboard-operable; the shared chat retains its existing live response region and focus handling.
- Unauthorized/null resolver results render no client launcher boundary.
- Optional AI failure does not break the underlying page, billing dialog, or schedule editor.

P48-L3 covers the missing asynchronous failure announcement. P48-L4 covers the lack of browser-level nested Sheet/RTL/focus verification.

## 5. Roadmap, documentation, scope, and P4.9 check

### Roadmap alignment

The main P4.8 deliverables exist: one strict union, one reusable launcher, one declarative resolver, all nine roadmap areas, page-context prompt plumbing, and deferred hydration. Context remains advisory and non-patient context never selects the tool mount.

Alignment is partial until P48-M1, P48-M2, and P48-L1/L2 are corrected. These are implementation-contract issues within P4.8, not requests for new product scope.

### Documentation accuracy

Validation counts, current branch, no-migration claim, deferred-hydration architecture, authorization boundaries, and P4.9 exclusion are accurate. The capability-specific suggestion, exact report-id, visible schedule-week, and persistence-gate claims need correction after remediation (P48-L4).

### Feature-creep and later-phase check

Pass.

- No P4.9 entitlement, `assistant_launcher_settings`, `assistant_launcher_user_overrides`, placement editor, or per-user launcher override exists.
- No P4.10 conversational entity memory or P4.11 workflow engine/ledger was introduced.
- No patient-facing AI, mutable assistant action, or generic text-to-SQL/query mechanism was added.

**P4.9 has not started.**
