## Verdict

**APPROVED WITH FIXES**

The security and trust-boundary design of P4.10 is sound, complete against the roadmap, and proven behaviorally by tests rather than by assertion. The headline guarantee — active context is an **advisory identity default only** that never widens access, with every tool re-authorizing the effective id on every turn — holds across all six entity types. Model/client-supplied UUIDs are never promoted into stored context; display labels never enter a prompt or the chat request body; the lifecycle (archive/delete) and tenant isolation are enforced structurally and covered by live RLS tests. No P4.11 workflow or write-capable AI behavior was started.

Two **Medium** correctness findings and one **Low** hardening finding are raised. None is a security defect (no access widening, no PHI egress, no tenant crossing). They concern the *accuracy* of answers produced by the list/financial tools when an active slot is present, and one missing rate limit. They are fixable additively and do not require re-architecting the phase.

## Findings

### P410-M1 — Active entity slots are applied as hard filters/defaults on *list* tools, silently narrowing intentionally broad queries

**Files:**
- `lib/ai/tools/list-appointments.ts:70-101` (`effectiveAppointmentId`, `effectiveDoctor`, `effectiveDepartment` → `.eq("id"/"doctor_id"/"department_id")`)
- `lib/ai/tools/list-doctor-appointments.ts:43-53` (`effectiveAppointmentId` → `.eq("id")`)
- `lib/ai/tools/list-outstanding-invoices.ts:66-82` (`effectiveInvoiceId` → `.eq("id")`)

**Problem.** The advisory-prompt contract in `buildActiveContextPrompt` tells the model to *"Use an active value only when the user refers to that same entity or uses a pronoun without naming a new one."* But the enforcement mechanism is a **server-side default keyed purely on argument omission**: whenever the model omits `appointment_id` / `doctor` / `department` / `invoice_id`, the tool injects the active slot id as a hard `.eq` filter. Omission is exactly what a well-behaved model emits for a genuinely broad request ("list all appointments tomorrow", "list every outstanding balance"), so the model has no lever to *not* use the active slot — following the prompt instruction cannot prevent the filter. For the single-entity patient tools (`get_patient_summary`, `search_patient_visits`) this mismatch is harmless because those tools are single-entity by nature; for **list** tools it converts a list into a silently narrowed result.

**Impact.** A plausible conversation produces a materially wrong answer:
1. "Does the clinic have any outstanding balances?" → one row → invoice slot pinned.
2. "What's our total outstanding right now?" → model omits `invoice_id` → query scoped to that one invoice → the assistant reports a single balance as the clinic total.

The same pattern applies to an active staff/department slot scoping a later "how busy are we tomorrow?" `list_appointments` call to one doctor/department. This is a correctness/trust-in-answers defect, not a security one: RLS still applies, no data widening, and the chip is visible + the audit records `from_active_context`. Aggregate tools (`get_appointment_stats`, `get_revenue_summary`, `compare_revenue_periods`) do **not** consume active context, which limits blast radius, but the two list tools that return rows the model then summarizes are affected.

**Required fix.** Give the model an explicit opt-out or stop force-applying single-entity slots on list tools. Options: (a) only apply the active appointment/invoice slot when the model *explicitly* references it (e.g. add an explicit boolean/param the model sets, rather than inferring from omission); or (b) do not use the appointment/invoice slot as an `.eq("id")` filter on list tools at all — reserve the "pin one entity" behavior for a dedicated detail path — and keep only patient/staff/department defaults where scoping is the documented intent; or (c) at minimum, when a list/financial tool applies an active-slot filter, return an explicit structured notice (like `from_active_context`) that the UI surfaces to the user so a scoped total is never read as a clinic-wide total.

**Regression tests.**
- With an active invoice slot, `list_outstanding_invoices` called with no `invoice_id` and a multi-row clinic result must either not silently collapse to the single active invoice, or must emit a machine-readable "scoped to active invoice" notice the payload carries.
- With an active staff/department slot, `list_appointments` for a broad range must not silently drop to one doctor/department without a surfaced notice.
- Assert the chosen fix's opt-out lever actually lets the model retrieve the full list while the slot remains set.

### P410-M2 — `list_outstanding_invoices` records an active invoice from a *truncated* single-row result

**File:** `lib/ai/tools/list-outstanding-invoices.ts:91-127`

**Problem.** `effectiveLimit = min(limit, 25)`, the query fetches `effectiveLimit + 1`, `truncated = fetched.length > effectiveLimit`, and `rows = fetched.slice(0, effectiveLimit)`. The context proposal at line 112 fires on `rows.length === 1 && !invoice_id && !activeInvoiceId && ctx.conversationId` — with **no `!truncated` guard**. When the model calls the tool with `limit: 1` (a legitimate "show me the single largest outstanding balance" request) and the clinic has several outstanding invoices, `fetched.length === 2`, `truncated === true`, `rows` is sliced to one, and that one (merely the top of a longer list) is pinned as **the active invoice**. It is not a deterministic unique resolution — it is an artifact of the model's `limit`. This then feeds directly into the P410-M1 wrong-total scenario.

By contrast the appointment resolutions in `list-appointments.ts:140` and `list-doctor-appointments.ts:58` are effectively safe from this because their caps are 50/100 (a single-row truncation is not reachable in practice), so the fix is local to the invoice tool.

**Impact.** A non-representative invoice is silently established as conversation context; combined with M1, subsequent broad financial queries can report that one balance as a total. Correctness only; no authorization impact.

**Required fix.** Add `!truncated` to the invoice proposal condition (only treat a single row as a deterministic resolution when it is the complete result set), and mirror the guard on the appointment tools for defense-in-depth.

**Regression tests.**
- `list_outstanding_invoices({ limit: 1 })` against a clinic with ≥2 outstanding invoices records **no** invoice slot (`recorder.takeAll()` empty).
- `list_outstanding_invoices({ limit: 10 })` against a clinic with exactly one outstanding invoice still records it (existing behavior preserved).

### P410-L1 — Context mutation server actions have no rate limit

**File:** `actions/assistant-context.ts` (`chooseAssistantConversationContext`, `clearAssistantConversationContext`)

**Problem.** The streaming chat route and the launcher-session route each apply `checkRateLimit(...)`. The two context server actions perform authenticated DB reads (patient/appointment/invoice/profile/department lookups, plus financial/analytics gate calls) on every invocation and are directly callable by any authenticated staff user, but carry no rate limit. Because they re-read strictly within the caller's own RLS scope and only mutate the caller's own conversation, this is not an authorization or data-exposure issue; it is an unbounded-work / minor existence-oracle surface (a caller can probe `{type,id}` pairs and distinguish `success` from `not_found`, though only for ids their RLS already governs and which they can already probe via the normal app pages).

**Impact.** Low. No access widening; bounded to the caller's own clinic/rows. Primarily a resource-abuse hardening gap and consistency gap with the routes.

**Required fix.** Apply the same `checkRateLimit("assistant-context-mutation", \`${clinicId}:${userId}\`, { limit, windowSeconds, failureMode: "open" })` pattern used by the launcher-session route to both actions before the DB reads.

**Regression tests.** A test asserting the rate limiter is invoked (mocked) for both actions and that exceeding it returns a stable failure result without touching the DB.

## Observations (non-blocking; no action required)

- **Appointment/invoice explicit-choice paths are reachable via direct server-action call even though no UI button emits them.** `contextChoicesForToolResult` only produces patient/staff/department/report candidate buttons, but `chooseAssistantConversationContext` accepts `entityType ∈ {appointment, invoice}`. This is safe: the action re-reads through RLS + the financial gate and derives the label server-side, so a forged call can only set context to an entity the caller is already authorized to see, and context is advisory. Recorded for continuity, not a defect.
- **`persistDoctorTurn` writes `active_context`/title in separate statements not scoped by `status`.** The immediately preceding re-select is scoped by `status='active'` and throws on a concurrent archive, closing the meaningful race; a slot written onto an already-archived row is never read again (both `loadLatestDoctorConversation` and `ensureDoctorConversation` filter `status='active'`). Pre-existing persistence shape, unchanged risk.
- **The advisory prompt places real server-derived UUIDs (and report slugs) in model context.** Consistent with the already-reviewed `page-context.ts` mechanism; the prompt forbids displaying internal ids and the ids grant no access (re-authorized every call). Acceptable and consistent with P4.10A.
- **P4.10B carry-forward guarantee from the P4.10A review is honored:** `display_label` is rendered only in the React chip and is grep-confirmed absent from prompt construction, tool arguments, and the chat payload.

## Conclusion

P4.10 delivers the complete conversational entity-context system across all six roadmap entity types with its security contract intact: context is set only from server-derived, RLS-authorized resolutions or server-revalidated explicit choices; model- and client-supplied ids are never promoted into stored context; every tool re-runs full authorization on the effective id so stale, deleted, cross-clinic, and cross-department context fails closed; no tenant-authored label reaches the model or the chat payload; the archive/delete lifecycle clears or removes context; and no billing, entitlement, RLS, PHI, audit, or tool-mount regression was introduced. No P4.11 workflow or write-capable AI functionality was started.

The two Medium findings (P410-M1, P410-M2) are correctness/answer-accuracy defects in how the *list and financial* tools apply and record single-entity slots — not authorization defects — and P410-L1 is a rate-limit hardening gap. All three are additive fixes that do not disturb the trust boundary.

**Verdict: APPROVED WITH FIXES.** Address P410-M1 and P410-M2 before the list/financial context defaults are relied on in production; P410-L1 is a recommended hardening follow-up.
