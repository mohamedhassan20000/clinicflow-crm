## 2. P45-R2 (= P45-M2) — Billing bucket derived from actual finalized cost — ✅ RESOLVED

**Finding:** The managed bucket (`managed_included`/`managed_addon`/`managed_overage`) was stamped at reserve time from the worst-case reserved cost and copied immutably onto each attempt, so events could be permanently misbucketed even while period aggregates stayed exact — a latent over/under-charge the moment invoicing reads event dispositions.

The implementer chose the stronger of the two offered options: **both** the actual-cost re-derivation **and** the documented aggregate-authoritative invoicing contract.

### 2.1 Mechanism is correct

`20260719150000_p45c_review_fixes.sql` re-`create or replace`s the 7-arg `reconcile_ai_budget` wrapper, inserting a bucket-correction block **before** the inner reconcile call that inserts the immutable attempts:

- **Accounting basis is right.** I traced `spent_micros` semantics through `…120000`: the reserve path bumps only `reserved_micros` (line 408), never `spent_micros`; `spent_micros` accrues actual cost only at reconcile (line 582), and the wrapper subtracts strict/hybrid direct spend in the same transaction, so `spent_micros` is managed-only. At the moment of re-derivation the inner reconcile has **not** yet run, so `v_period.spent_micros` holds the prior cumulative managed spend excluding the current reservation. `v_period.spent_micros + p_managed_cost_micros` (150000:103–109) is therefore the cumulative managed spend *including* this reservation — the correct classification basis against `included_limit_micros` / `+ addon_limit_micros`.
- **Serialization is right.** The period is re-`SELECT … FOR UPDATE` (150000:97–101) so concurrent reconciliations serialize on a consistent cumulative spend. Re-locking within the same definer transaction that already holds the reservation lock is reentrant and safe.
- **Immutability is preserved.** The correction is written to the still-mutable `ai_budget_reservations` row (150000:112–115, guarded `status = 'reserved'`). The existing BEFORE INSERT trigger `derive_ai_usage_billing_disposition` reads `reservation.managed_billing_disposition` **fresh** from the table at insert time (`…140000`:719–722), so the corrected value is what lands on the immutable event. **No `ai_usage_events` row is ever updated** — I confirmed there is no `UPDATE … ai_usage_events` anywhere in the fix.
- **Correct-once.** `v_should_adjust := status = 'reserved'` (150000:75) gates the re-derivation; idempotent retries (status already `reconciled`) skip it and leave written events untouched.
- **Hybrid is safe.** For hybrid, `p_managed_cost_micros` is the caller estimate, but the pre-existing post-insert SQL re-derivation (150000:129–138) sums the managed attempts and rolls the whole transaction back on any mismatch, so deriving the bucket from the estimate cannot persist a wrong value. `byok_strict` is correctly excluded (no managed event to bucket).

### 2.2 No regression in the wrapper

I diffed 150000's wrapper against 140000's line by line. Every pre-existing branch is preserved verbatim: the `service_role` auth gate, the `p_managed ≤ p_actual` validation, the reservation `FOR UPDATE` lookup, the `managed == actual` / `byok_strict == 0` guards, the inner-reconcile delegation, the hybrid managed-sum re-derivation, and the double-guarded (`v_reconciled AND v_should_adjust`) direct-cost subtraction with its `spent_micros >= v_direct_cost` floor. The only change is the inserted correction block. The `revoke … / grant execute … to service_role` and updated `comment on function` are re-applied. No behavioral drift.

### 2.3 Contract limitation is honest and documented

The single-enum-per-reservation model still cannot split one reservation whose managed spend straddles a bucket boundary. The migration header comment, the function comment, the P4.5C report, and (per cycle-1's option b) the invoicing contract all state that **the sole source of truth for add-on/overage invoicing is the exact period aggregate** (`ai_budget_periods.spent_micros` vs `included/addon/overage_limit_micros`). This is the correct and intended residual limitation, not a defect.

### 2.4 Tests are appropriate

- `tests/unit/integration/p45c-ai-commercial-integration.test.ts` adds a genuine behavioral scenario (273–323): two overlapping 800-micros reservations; the second is stamped `managed_addon` at reserve time (asserted, 290), then reconciled at real 100-micros cost and re-derived to `managed_included` on both the reservation (303) **and** the immutable event's `billing_disposition` (310); the period aggregate is asserted at 200 micros inside the included allowance (321–322). This exercises exactly the misbucketing R2 describes and proves the fix.
- `tests/unit/integration/p45a-ai-budget-ledger.test.ts` (242–253) was updated so a genuine provider over-run that crosses the included ceiling is now recorded as `managed_overage` from actual cost — confirming the suite's expectations were migrated to the new behavior rather than left stale.
- `tests/unit/db/p45c-review-fixes-migration.test.ts` locks the source-level contract (actual-cost re-derivation, period `FOR UPDATE`, correct-once gate, no `ai_usage_events` UPDATE, aggregate-authoritative invoicing comment). I re-ran it green independently.

**Assessment:** Fixed correctly, no regression, well tested. **Closed.**
