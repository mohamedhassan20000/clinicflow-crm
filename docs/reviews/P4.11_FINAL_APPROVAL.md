## Finding resolution

### M1 — resume is now re-bound to the confirmed preview snapshot — **RESOLVED**

The gap was that the resume branch validated only the content-free *shape/summary* hash and executed against fresh reads, so a same-shaped literal swap or a grown referenced read set could dispatch to a target that was never previewed. The fix closes this with a **hash rotation at the atomic claim** plus an **action-input rebind on resume**, without persisting any value:

- **First confirmation** ([executor.ts:517-556](../../lib/ai/workflows/executor.ts#L517-L556)) still recomputes the full action preview and compares `workflowActionSnapshotHash` against the stored preview hash (`preview_stale` on drift). In the *same atomic claim* that records the confirmer and moves the run to `running`, `claimConfirmation` rotates `dry_run_snapshot_hash` from the preview-snapshot digest to `workflowActionInputsHash(preflight.actionInputs)` — a SHA-256 over each action step's id, closed-registry tool name, and exact server-resolved input ([ledger.ts:105-138](../../lib/ai/workflows/ledger.ts#L105-L138), [plan.ts:323-333](../../lib/ai/workflows/plan.ts#L323)). The claim's `WHERE state='previewed' AND dry_run_snapshot_hash=<preview> AND confirmed_at IS NULL` preserves the original atomic, single-winner, non-replayable guarantee.
- **Resume** ([executor.ts:564-587](../../lib/ai/workflows/executor.ts#L564-L587)) re-runs the plan in `preview` mode with `skipActionExecution: true`, so authorized read steps re-resolve action inputs **without invoking any action tool**, then compares `workflowActionInputsHash(rebound.actionInputs)` to the rotated binding and throws `preview_stale` before any unfinished action can run.
- The rebind intentionally covers every action input (literal and read-derived) and intentionally excludes mutable step statuses, so a completed pending booking stays terminal even though it consumed availability, while an unfinished reminder cannot gain a recipient absent from the confirmed set.

Both the honest-drift scenario (referenced read grows A → A+D) and the client-swap scenario (partial run resumed with a different literal `patient_id`) now return `preview_stale` and make **no** second action attempt. Verified by the new tests in `p411-comprehensive-workflow-confirmation.test.ts`.

### L1 — clinic-formatted dates in the confirmation card — **RESOLVED**

Appointment-reminder drafts and pending-booking previews now carry a `scheduled_at_label` produced by the shared `formatScheduledAt` from the clinic timezone, locale, digit system, and 12/24-hour preference ([pending-workflow.ts:107-117](../../lib/booking/pending-workflow.ts#L107-L117)). The raw ISO value stays in the transient action object because it is part of the exact confirmation/execution contract, but the UI no longer displays it and retains `<bdi>` for mixed-direction safety.

### L2 — infrastructure failures are distinct from authorization denials — **RESOLVED**

`confirmAssistantWorkflow` now maps outcomes explicitly ([actions/assistant-workflows.ts:52-69](../../actions/assistant-workflows.ts#L52-L69)): `denied` **only** for `AiToolAuthorizationError`; `preview_stale` / `preview_expired` / `invalid_request` for plan outcomes; and `internal_error` for any unexpected failure, which is reported to Sentry with an area tag and **no** plan or patient data attached. English and Arabic copy render distinct expiry and temporary-failure states.

### L3 — unconfirmed previews expire — **RESOLVED**

`WORKFLOW_PREVIEW_TTL_MS = 15 min` ([executor.ts:29](../../lib/ai/workflows/executor.ts#L29)). Only unconfirmed `previewed` runs are age-gated; a missing/invalid completion timestamp fails closed as expired. Age is checked both before the preview recomputation and again immediately before the atomic claim ([executor.ts:519, 540](../../lib/ai/workflows/executor.ts#L519)). Confirmed partial runs do not expire and stay protected by the M1 action-input rebind plus core idempotency.

## Integration confirmations

- **Architecture / registry closure:** action steps remain limited to appointment reminders, invoice reminders, and pending booking; only the orchestrator is model-visible; nested mounts set `workflowStepMount: null`; action tools carry `taskClasses = ["staff_workflow"]`.
- **Authorization / RLS / tenant isolation:** every nested step runs through `harden()` and re-asserts role/entitlement/visibility/permission; the ledger's composite `(user_id, clinic_id)` / `(confirmed_by, clinic_id)` integrity and owner-read RLS are unchanged and live-tested for forgery + cross-tenant denial. Pending booking uses the RLS user client (`createClient()`), not admin.
- **PHI protection:** `ai_workflow_runs` persists only versioned shapes, ids, timings, bounded error codes, and the one-way rotated digest — the rotation adds no value column and no new persisted content.
- **Workflow integrity:** first-confirmation snapshot check and resume action-input rebind together enforce "exact preview + explicit confirmation" and "stale data invalidates confirmation" on both paths; completed action steps stay terminal; messaging idempotency (per-channel dedupe) and booking idempotency (existence check + partial unique index) prevent duplicates on resume.
- **Billing:** usage reserved once per `staff_workflow` turn via `prepareAiExecution`, which re-checks `ai.workflows` before provider reservation; the confirmation action is independently rate-limited (10/60s, fail-closed).
- **Booking safety:** pending-only, `patient_notification: "not_sent"`, no dispatch import — no patient notification emitted.
- **Roadmap completeness:** §8 and the reports accurately describe the shipped closed registry, confirmation/resume model, migrations, and the explicit P5+ boundary. No destructive, unattended, scheduled, auto-send, billing-mutation, arbitrary-query/tool, patient-facing, or later-phase behavior was introduced.

## Residual notes (non-blocking, not required)

- The resume rebind can over-reject (fail-safe `preview_stale`) if a read step feeding a *completed* booking legitimately changes after that booking consumed availability, forcing a fresh preview. This is safe (rejects rather than dispatches) and consistent with the documented design.
- No new findings were discovered during this review.
