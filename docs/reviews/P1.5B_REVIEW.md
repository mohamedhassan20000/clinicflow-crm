## 2. Findings — required fixes

### P15B-R1 — HIGH — Executive aggregates regress the documented exact-count design and will silently plateau

- **Affected:** `lib/operator-analytics.ts:27-56`, `lib/supabase/admin.ts` (`listOperatorClinicMetadata` `limit(1000)`)
- **Explanation:** The deleted Mission Control code carried an explicit correctness comment: *"Headline totals are exact count queries: row arrays are capped by PostgREST max_rows, so counting fetched rows would silently plateau."* The replacement does exactly what that comment warns against: `db.from("subscriptions").select(...)` with no limit (PostgREST caps at 1000 rows) and `listOperatorClinicMetadata()` with `limit(1000)`, then counts/filters/sums in JS. Additionally the semantics are looser than the old page: "active" is `status === "active"` without the `current_period_end` guard, and "trialing" ignores `trial_ends_at > now` — so lapsed-but-not-yet-transitioned subscriptions inflate the counts. `activeClinics` also counts **subscription rows**, not distinct clinics, and defines "active clinics" as active + trialing.
- **Why it matters:** every headline number on the operator's primary screen (active/trial/paid clinics, revenue, both growth figures, the growth chart) becomes silently wrong at ≥1000 rows and is already drifting from billing truth today. This regresses a deliberate, documented P1D correctness decision.
- **Required fix:** use exact `count: "exact", head: true` queries (or reviewed aggregate RPCs) for all headline totals, reinstating the `current_period_end`/`trial_ends_at` guards; compute distinct-clinic counts; keep the 6-month series query bounded by an explicit `created_at >= sixMonthsStart` **server-side filter** (not a client-side filter over a capped list).
- **Verification:** integration test reconciling each widget against raw platform tables (see P15B-R3); assert counts match seeded data that exceeds semantic edge cases (expired trial, lapsed active).
- **Blocks merge:** **YES**

### P15B-R2 — HIGH — P1D operational Mission Control capabilities deleted wholesale

- **Affected:** `app/(operator)/operator/page.tsx` (rewrite)
- **Explanation:** The rewrite deletes, without relocation: the **orphaned signup accounts backstop** (the compensation surface for auth-user-without-profile, a P1 review deliverable), trials expiring within 7 days, top usage counters this month, registration mode + weekly accepted counter, pending requests / open invitations, coupon and feature-override counts, and the delivery-health/error placeholders. The plan says Mission Control "becomes an executive analytics dashboard," but the P1.5 umbrella mandates **zero loss of business capability** ("Every P1.5 deliverable is presentation, preference, or read-model work **on top of** the P1 platform"). Removing the orphan backstop removes the only UI where operators detect stuck signups.
- **Why it matters:** operational monitoring the platform depends on (especially the orphan backstop and expiring-trials list) is no longer reachable anywhere in the product.
- **Required fix:** restore the operational widgets — either as a section below the executive overview on Mission Control, or on a dedicated operator page linked from Quick Actions. The orphan backstop, expiring trials, usage counters, and registration-mode/weekly-limit readouts must remain reachable. (The registration status readout could also live on `/operator/invitations` — implementer's choice, but it must exist.)
- **Verification:** each restored widget visible in the operator UI; existing P1D integration tests still cover their queries.
- **Blocks merge:** **YES**

### P15B-R5 — MEDIUM — "User Growth" widget is a hardcoded placeholder

- **Affected:** `lib/operator-analytics.ts` (`userGrowth: 0`), `app/(operator)/operator/page.tsx` (`<Stat label="User growth" value="Platform-safe" …/>`)
- **Explanation:** The plan's widget list includes User Growth. What shipped renders the literal string "Platform-safe" as the stat value and hardcodes `userGrowth: 0`. A real, PHI-free aggregate is available: a count-only query over `profiles` (row counts by month via a reviewed admin helper or platform read RPC exposes no clinical data and no personal fields).

- **Required fix:** implement user growth as a platform-safe count aggregate (e.g. profiles created this month vs last, count-only, via a reviewed helper following the `listOperatorClinicMetadata` pattern with `count: "exact", head: true`), or — if deliberately deferred — remove the widget rather than shipping placeholder text, and record the deferral in this file. Implementing it is the plan-conforming choice.
- **Verification:** widget shows a numeric value; covered by the reconciliation integration test.

### P15B-R6 — MEDIUM — Report filters are declared but never rendered or applied

- **Affected:** `lib/operator-reports/registry.ts` (filter declarations on invitations/subscriptions/activity), `components/operator/report-shell.tsx` (no filter UI), report queries (ignore filters)
- **Explanation:** The registry contract includes `filters` per the plan ("id, title, **filters**, columns, query fn, export fn rendered by one shared report shell"), and three launch reports declare filters — but the shell renders no filter controls and no query consumes a filter value. The declared contract is dead configuration.
- **Why it matters:** the shared-shell architecture is the core P1.5B deliverable; a contract field that does nothing misleads the next registry author (P6B lands cost dashboards on this contract) and under-delivers the spec.
- **Required fix:** implement minimal filter support end-to-end: shell renders declared filters (select/date/text) as GET form inputs; `[reportId]/page.tsx` and the export route pass validated `searchParams` into `query(filters)`; the three declared filters actually constrain their queries. Alternatively (minimum acceptable): remove the dead filter declarations and the `filters` field until implemented — but the plan names filters in the contract, so implementing is the conforming choice.
- **Verification:** registry contract test extended to cover a filtered query; manual check that filter + export honor the same filter state.
- **Blocks merge:** **YES**

### P15B-R7 — MEDIUM — Launch reports don't deliver their titular content

- **Affected:** `lib/operator-reports/registry.ts`
- **Explanation:** Three of the seven launch reports are stand-ins: **Users** is the clinics list relabeled (name + created_at, "no staff or patient details" — but also no user data at all); **Growth** is the same clinics list again; **Revenue** contains no monetary column (status + created_at only) despite its description promising "recurring plan revenue overview in canonical USD plan pricing."
- **Why it matters:** the plan names these seven launch reports as deliverables; shipping duplicates under different titles is scope compliance in name only, and the Revenue report is unusable for its stated purpose.
- **Required fix:** *Users*: platform-safe per-clinic user counts (count-only aggregate over `profiles` grouped by clinic via a reviewed admin helper — clinic name + user count + latest signup month; no names/emails). *Revenue*: join `plans(monthly_price_usd)` so rows carry plan name + monthly price + status (+ clinic name where platform-safe). *Growth*: monthly new-clinic counts (month + count), matching the dashboard series, rather than a raw clinic list.
- **Verification:** each report's columns show its titular data; no-PHI integration test covers the new queries.
- **Blocks merge:** **YES**

### P15B-R8 — MEDIUM — CSV export lacks spreadsheet formula-injection hardening

- **Affected:** `lib/operator-reports/types.ts` (`exportReportCsv`)
- **Explanation:** Values are quoted and inner quotes doubled — good — but cells beginning with `=`, `+`, `-`, `@` (or tab/CR) are not neutralized. Clinic names are **tenant-controlled input** (self-signup onboarding) and flow into the clinics/users/growth exports opened by the platform operator in Excel/Sheets, which evaluate such cells as formulas.
- **Why it matters:** classic CSV-injection: a clinic named `=HYPERLINK("https://evil","…")` executes in the operator's spreadsheet — a tenant-to-operator injection channel.
- **Required fix:** in the shared escape function, prefix any cell starting with `=`, `+`, `-`, `@`, `\t`, or `\r` with a single quote (`'`) before quoting. One function fixes every report because export is centralized (good architecture — keep it that way).
- **Verification:** unit test: `{ name: '=HYPERLINK("https://evil")' }` exports as `"'=HYPERLINK…"`.
- **Blocks merge:** **YES**

### P15B-R9 — LOW — Invitation email link host is not pinned (required, non-blocking)

- **Affected:** `actions/operator.ts` (`sendInvitationEmail` link validation)
- **Explanation:** The raw invitation link necessarily arrives from the operator's browser (the server never holds the raw token — correct lifecycle). Validation checks it is a URL whose path starts with `/signup/` but accepts **any host**, so the action can be made to email a foreign-host link. Only a platform admin can invoke it, so exploitation requires a compromised operator session — low likelihood, but the check is one line.
- **Required fix:** require the link origin to equal `NEXT_PUBLIC_SITE_URL` when set (production), otherwise the request origin.
- **Verification:** unit test in the P15B-R3 suite: foreign-origin link → validation error.
- **Blocks merge:** No

### P15B-R10 — LOW — Email-send bookkeeping edge cases + plan-revision commit hygiene (required, non-blocking)

- **Affected:** `actions/operator.ts` (`sendInvitationEmail`); repo hygiene for the stashed plan revision
- **Explanation:** (a) If the email sends but the `email_sent_at` update fails, the audit event is skipped entirely — an email was genuinely sent with no audit trail; write the audit event regardless of the timestamp-update outcome (it records the send, not the bookkeeping). (b) Failures return generic strings with no server-side diagnostic at all; log a sanitized error (Resend error code/message only — **never** the link, token, or recipient-identifying payload beyond the invitation id). (c) The revised `docs/AI_AGENT_PLAN.md` — the authority for P1.5 — is stranded in `stash@{0}`; commit it (with the other production-domain docs) as its own docs commit so reviews stop depending on a stash.
