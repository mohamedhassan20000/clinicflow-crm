## Finding resolution

### P410-M1 — advisory context no longer silently narrows list/financial tools — **RESOLVED**

The fix replaces omission-driven defaulting with explicit per-entity intent flags. An active slot is applied as a filter **only** when its matching `use_active_*` flag is `true`:

- `list_appointments` ([lib/ai/tools/list-appointments.ts:99-109](../../lib/ai/tools/list-appointments.ts#L99-L109)) — `use_active_appointment`, `use_active_staff`, `use_active_department`, each gating its own slot independently.
- `list_doctor_appointments` ([lib/ai/tools/list-doctor-appointments.ts:49-51](../../lib/ai/tools/list-doctor-appointments.ts#L49-L51)) — `use_active_appointment`.
- `list_outstanding_invoices` ([lib/ai/tools/list-outstanding-invoices.ts:80-81](../../lib/ai/tools/list-outstanding-invoices.ts#L80-L81)) — `use_active_invoice`.
- `run_clinic_report` ([lib/ai/tools/run-clinic-report.ts:242](../../lib/ai/tools/run-clinic-report.ts#L242)) — `use_active_staff` on the doctor dimension.

Argument omission now leaves broad and aggregate queries broad. An explicit `use_active_*` with no corresponding slot returns a `needs_clarification` result instead of silently widening ([list-appointments.ts:111-137](../../lib/ai/tools/list-appointments.ts#L111-L137), [list-outstanding-invoices.ts:83-91](../../lib/ai/tools/list-outstanding-invoices.ts#L83-L91)). Per-entity flags prevent one active entity's intent from applying every stored slot. Audit `from_active_context` now reports only filters that were explicitly selected and available. The M1 wrong-total scenario ("what's our total outstanding right now?") no longer collapses to a single pinned invoice.

### P410-M2 — context promotion requires a true, unique, non-truncated result — **RESOLVED**

`list_outstanding_invoices` now guards the invoice proposal with `!truncated` in addition to the single-row condition ([list-outstanding-invoices.ts:136-142](../../lib/ai/tools/list-outstanding-invoices.ts#L136-L142)). A `limit: 1` request over multiple matches sets `truncated = true` and therefore proposes **no** slot. The same guard is mirrored on `list_appointments` ([list-appointments.ts:203-208](../../lib/ai/tools/list-appointments.ts#L203-L208)) and `list_doctor_appointments`, which now also fetches `cap + 1` and slices back before deciding ([list-doctor-appointments.ts:74-84](../../lib/ai/tools/list-doctor-appointments.ts#L74-L84)). Only a complete, genuinely unique result establishes context.

### P410-L1 — context mutations use the shared platform rate limiter — **RESOLVED**

Both server actions call the existing `checkRateLimit` via `contextMutationAllowed` with namespace `assistant-context-mutation`, caller key `${clinicId}:${userId}`, and the launcher-consistent `{ limit: 30, windowSeconds: 60, failureMode: "open" }` policy ([actions/assistant-context.ts:51-58](../../actions/assistant-context.ts#L51-L58)). The check runs **before** any Supabase client creation or DB read in both `clearAssistantConversationContext` ([actions/assistant-context.ts:113-116](../../actions/assistant-context.ts#L113-L116)) and `chooseAssistantConversationContext` ([actions/assistant-context.ts:240-243](../../actions/assistant-context.ts#L240-L243)); a denied call returns the stable `{ success: false, reason: "rate_limited" }`.

## Required confirmations

- **Advisory-context contract preserved.** `buildActiveContextPrompt` still enumerates entity type + internal id/slug only and instructs the model to use an active value only for same-entity/pronoun reference. It was extended — not weakened — to direct the model to set the matching `use_active_*` flag only for explicit entity-scoped intent, to omit all such flags for broad/aggregate requests, and to never copy an active id into an explicit id argument ([lib/ai/conversation-context.ts:290-292](../../lib/ai/conversation-context.ts#L290-L292), both en + ar). **Confirmed.**
- **Broad queries no longer implicitly narrowed by active context.** Filtering is now gated exclusively on explicit `use_active_*` flags; omission preserves breadth. **Confirmed.**
- **Context promotion requires a true unique, non-truncated result.** All three list tools require `rows.length === 1 && !truncated` (and exclude model-supplied ids) before proposing a slot. **Confirmed.**
- **Context actions protected by the existing rate-limiting strategy.** Both actions use the same `checkRateLimit` mechanism and policy shape as the launcher-session route, pre-DB. No new limiter was introduced. **Confirmed.**
- **No trust-boundary regressions.** Model/client UUIDs remain `trustedForContext:false` and are never promoted; explicit choices carry only `{type,id}` and are re-read + re-gated + server-labeled; `display_label` stays UI-only and absent from prompt and chat payload; every consumer re-authorizes the effective id on each call through the RLS client. The fixes are purely additive (new optional flags, a boolean guard, a pre-existing limiter call). **Confirmed.**
- **No new regressions introduced.** Focused P4.10 suite green (67 tests, 7 files); `tsc --noEmit` clean. Regression tests explicitly cover: broad queries staying broad with slots set, explicit-scope fail-closed on stale/unauthorized slots, `use_active_*` with no slot returning clarification, `limit:1`-truncation recording no slot, ambiguous results recording nothing, and both actions rate-limiting before DB-client creation. **Confirmed.**
- **P4.11 not started.** Grep across `lib/ app/ actions/ supabase/migrations` finds no `ai_workflow_runs`, `ai.workflows`, workflow engine, dry-run, or write-action step. Everything remains read-only/advisory. **Confirmed.**
