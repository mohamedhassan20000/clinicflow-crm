## Final Verdict: **NOT APPROVED — REQUIRED FIXES BEFORE MERGE OR P4.8A**

P4.7 has a strong security baseline and most of the intended architecture is present, but the phase is not complete against its own roadmap contract.

No new path was found that leaks PHI, crosses clinic boundaries, exposes tenant data through the help/capability tools, or grants an unauthorized operation. The static corpus is data-free; the `staff_help` mount contains only three data-free tools; capability discovery reads registry metadata rather than clinic records; tool calls re-assert Assistant access; and links are sanitized before rendering.

However, five Medium findings prevent approval:

1. the permission-aware navigation resolver advertises two primary-admin-only settings workflows to every admin;
2. it falsely denies the Messaging settings page when WhatsApp is disabled even though reminder and email-dunning settings remain usable;
3. the capability panel and `list_my_capabilities` describe a union mount, not the actual task-class mount used by the model in that turn;
4. the promised cited-article/deep-link help presentation is incomplete and mislabels non-report navigation links;
5. multiple corpus statements contradict the shipped UI and authorization behavior.

These are not cosmetic defects. They break the phase's central promises that guidance cannot contradict authorization, the corpus describes only behavior that exists, and panel ↔ tool ↔ mounted capabilities remain identical. The roadmap currently records P4.7 as complete and P4.8A as next; that status is premature until the required findings are fixed and re-reviewed.

## 3. Medium findings

### P47-M1 — Navigation and help expose primary-admin-only settings as available to every admin

**Files:** `lib/ai/help/navigation.ts:420-430`, `lib/ai/help/navigation.ts:456-467`, `lib/ai/help/navigation.ts:632-658`, `app/(protected)/settings/ai/page.tsx:25-32`, `app/(protected)/settings/customize/page.tsx:16-31`, `actions/page-permissions.ts:113-124`, `lib/ai/help/corpus.ts:565-618`, `lib/ai/help/corpus.ts:885-940`  
**Category:** authorization honesty / navigation correctness  
**Severity:** Medium

`settings_customize` and `settings_ai` declare only `roles: ["admin"]`. The resolver then checks the role-level page matrix, entitlement metadata, and `user_page_permissions`; it has no representation of the platform's separate **primary clinic admin** authority.

That does not match the real surfaces:

- `/settings/ai` explicitly redirects a non-primary admin to `/dashboard`.
- `/settings/customize` calls `listStaffPagePermissions`, which returns the localized primary-admin-only error for a non-primary admin; the Settings navigation also hides this entry unless `canCustomize` is true.

For a secondary admin with the Settings page visible, `resolveNavigationTarget` therefore returns `status: "available"` plus `/settings/ai` or `/settings/customize`. `search_help` also serves the full `manage-ai-settings` and `control-page-visibility` steps. The user is sent to a redirect or an unusable page after the assistant explicitly claimed access was verified.

This violates the phase's headline contract that guidance can never contradict server-side authorization. It does **not** bypass the real primary-admin checks and does not expose PHI, but it makes the help architecture give a materially false authorization answer.

**Required remediation:** extend navigation preconditions to model the real primary-admin requirement (or reuse a shared server-side target-access resolver), apply it to both targets and their articles, fail closed on lookup failure, and add secondary-admin fixtures for `get_navigation_target` and `search_help`.

### P47-M2 — Messaging navigation is falsely gated by WhatsApp entitlement

**Files:** `lib/ai/help/navigation.ts:432-443`, `lib/ai/help/corpus.ts:459-510`, `tests/unit/ai/p47a-navigation-registry.test.ts:125-133`, `app/(protected)/settings/messaging/page.tsx:27-68`, `components/settings/settings-nav.tsx:8-18`  
**Category:** entitlement correctness / false denial  
**Severity:** Medium

The `settings_messaging` target and `configure-reminders` article require the `whatsapp` feature. The real `/settings/messaging` route is not WhatsApp-gated: admins and managers can open it, and the page continues to expose appointment-reminder and invoice-follow-up settings, including email subject/body, while the WhatsApp card independently receives `entitled={false}`. The Settings navigation likewise shows Messaging without checking the WhatsApp feature.

With a valid `pro_ai` subscription and a clinic-level WhatsApp override disabled, the resolver returns `not_entitled`, withholds the link, and the help filter removes the reminder article. A real, reachable workflow is described as a plan feature the clinic does not have. The unit test at `p47a-navigation-registry.test.ts:125-133` currently pins this incorrect behavior rather than detecting it.

This is the inverse of a permission leak, but it still violates authorization honesty and sends the user to the wrong remedy (upgrade/contact an administrator instead of opening the existing settings page).

**Required remediation:** separate the page-level Messaging destination from the WhatsApp-only connection capability. The page/reminder article should follow the real route access; WhatsApp-specific guidance may retain a feature precondition. Replace the existing false-denial test with fixtures for both the accessible page and the unavailable WhatsApp sub-capability.

### P47-M3 — Panel/tool parity compares a union mount to itself, not the model's actual turn mount

**Files:** `lib/ai/capabilities.ts:156-180`, `lib/ai/staff-agent.ts:22-34`, `tests/unit/ai/p47b-capability-panel.test.ts:128-143`, `tests/unit/ai/p47a-help-tools.test.ts:105-116`, `docs/AI_AGENT_PLAN.md:1143-1148`  
**Category:** capability drift / acceptance mismatch  
**Severity:** Medium

`resolveAssistantCapabilities` intentionally omits `taskClass`, producing the union of every tool the role could mount across task classes. `list_my_capabilities` and the panel both use that union. The real model mount does not: `createStaffAgent` passes the certified turn's task class, and a `staff_help` turn mounts exactly:

- `search_help`
- `get_navigation_target`
- `list_my_capabilities`

The P4.7B parity test calls `resolveToolMount` without a task class and compares the capability payload to that same union. It proves panel = tool = union, but not the roadmap's stated panel = “tool set actually mounted for that user in the same request context.” During a help-routed turn, the panel/tool can enumerate operational or financial capabilities that the active model cannot call until a later message is rerouted.

The previous P4.7B review recorded this as Info I3. Because this comprehensive review was explicitly asked to establish **no drift between mounted tools, the panel, and `list_my_capabilities`**, and because the roadmap repeats the same-request parity criterion, I3 is upgraded to a real finding.

There is no privilege escalation: the per-turn mount remains authoritative, and every tool re-authorizes. The defect is a contract and truthfulness mismatch.

**Required remediation:** choose and document one honest contract. Either resolve/show the active task-class mount and test exact same-request parity, or formally redefine the panel/tool as the user's cross-turn capability union and update the roadmap, names, copy, and tests so they no longer claim equality with the active model mount. The current mix of union behavior and per-turn parity language is not acceptable.

### P47-M4 — Cited-article/deep-link help presentation is not fully delivered

**Files:** `lib/ai/help/search.ts:130-151`, `lib/ai/tool-presentation.ts:235-256`, `components/assistant/assistant-chat.tsx:178-187`, `components/assistant/assistant-chat.tsx:260-268`, `components/assistant/assistant-chat.tsx:294-300`, `docs/AI_AGENT_PLAN.md:1140`, `docs/AI_AGENT_PLAN.md:1148`, `docs/AI_AGENT_PLAN.md:1158-1161`  
**Category:** UX / phase completeness  
**Severity:** Medium

P4.7B owns “help-answer presentation (cited article + deep link),” and phase acceptance requires an Arabic receptionist question to produce accurate steps plus a working deep link.

The actual presentation path does not satisfy that contract reliably:

- `search_help` returns article ids and links inside `results[]`, but `summarizeToolResult` reads only a top-level `result.link`; the search article citation and link are not rendered from structured output.
- Assistant text parts render as plain `<p>` content, not link-aware Markdown. A model-written Markdown citation/link is displayed as literal text rather than a clickable link.
- A subsequent `get_navigation_target` call can produce a top-level link, but `ToolActivity` labels every such link with `openFullReport` / “Open the full report,” even when the destination is Patients, Appointments, Preferences, or a Settings page.
- No test exercises the complete Arabic question → cited article → correctly labelled clickable destination flow.

The tools contain the data needed to build the UX, but the approved presentation deliverable is incomplete and the existing report's claim that `ToolActivity` already supplies it is overstated.

**Required remediation:** render a safe, localized help citation and internal link from structured `search_help`/navigation output, use destination-appropriate link copy rather than report-only copy, and add an integration/component test for the roadmap's Arabic receptionist acceptance case plus the hidden-page no-link case.

### P47-M5 — The “describe only what exists” corpus rule is already violated

**Files:** `lib/ai/help/corpus.ts:140-174`, `lib/ai/help/corpus.ts:512-550`, `lib/ai/help/corpus.ts:943-980`, `app/(protected)/patients/page.tsx:55-74`, `actions/settings.ts:56-90`, `lib/ai/permissions.ts:26-34`, `lib/ai/permissions.ts:81-86`  
**Category:** product-knowledge accuracy / maintainability  
**Severity:** Medium

At least three shipped statements disagree with the implementation:

1. **Patient list search:** `find-patient-file` says the Patients-page search understands Arabic/English spellings and tolerates misspellings. The page uses direct `ILIKE '%term%'` filters over the stored name/phone/file/national-id fields. The bilingual fuzzy/transliteration behavior belongs to the Assistant's ranked patient-search RPC, not the Patients-page search box.
2. **Manager staff creation:** `add-staff-member` is served to managers and gives creation steps, then says managers have read-only access and only administrators can create staff accounts. `createStaff` explicitly admits managers and only prevents them from creating an `admin` account.
3. **Admin financial permission:** `ask-assistant-financial` is served to admins but says an administrator must grant the user financial-insights permission. Admins carry that permission implicitly and are never grant-dependent.

These are not translation nuances; they create contradictory or false instructions in the corpus that the system prompt orders the model to relay as the product's single source of truth. The current integrity tests check ids, role subsets, counts, and localization shape, but do not validate article claims against the affected surface contracts.

**Required remediation:** correct both locales, distinguish page-search behavior from Assistant search behavior, express the manager/admin staff-creation split accurately, and make the financial prerequisite role-aware (or split the article). Add targeted contract fixtures for every corrected statement.

## 5. Security, authorization, privacy, and PHI review

### What holds

- `search_help` reads a static in-repo corpus and no tenant table. The free-text query is deliberately absent from the audit row.
- `get_navigation_target` accepts a closed target enum; it is not an arbitrary path probe.
- Every P4.7 tool calls `assertStaffToolAccess` on execution, so Assistant-page visibility, subscription, and Assistant entitlement are rechecked mid-conversation.
- The `staff_help` task class mounts exactly the three data-free P4.7 tools. No patient, appointment, financial, report, or clinic-analytics reader exists in that mount.
- `list_my_capabilities` returns static registry descriptions resolved against role/entitlement/user-permission state. It reads no clinic record and audits only a count with `tableName: null`.
- Help/capability results still pass through the common hardening/provenance wrapper.
- Available links are internal paths and pass `safeInternalLink` before the client renders them.
- No new migration, RLS policy, service-role read, database function, provider credential path, or raw audit/log payload was introduced by P4.7.
- No PHI or clinic-data leak was found in the P4.7 changes.

### What does not hold

The claim that navigation guidance always agrees with authorization is false until P47-M1 and P47-M2 are fixed. These are false-positive/false-negative access descriptions, not successful authorization bypasses: the real pages/actions still enforce their own rules.

The capability union in P47-M3 does not grant data access, but it means “what this turn mounted” and “what the panel says” are not the same object despite the current documentation and tests claiming they are.

## 6. Localization, RTL, UX, accessibility, and maintainability

- **Localization:** message parity and unused-key checks pass; corpus/navigation content exists in both locales; Arabic retrieval fixtures pass. P47-M5 requires content corrections in both languages.
- **RTL:** the automated logical-properties gate passes. The capability panel uses logical spacing/alignment and direction-safe icons.
- **Accessibility:** the panel toggle has `aria-expanded`/`aria-controls`; the panel uses a labelled section; the close action has a localized accessible name. Direct behavioral/axe coverage is missing (P47-L2).
- **UX:** grouping and long-list scrolling are implemented. The help link/citation presentation is not production-ready (P47-M4).
- **Maintainability:** registry-driven descriptions, shared navigation resolution, one batch visibility reader, and exhaustive status unions are good foundations. The corpus currently lacks contract tests strong enough to enforce its authoring rule (P47-M5).
- **Performance:** help retrieval is bounded deterministic in-memory scoring over 19 articles; visibility reads are deduplicated per page slug; no embedding/model call is added for retrieval.
