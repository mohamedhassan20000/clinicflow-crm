# P1.5B — Invitation-Email "Invalid Request" Fix & Status-Badge Polish

**Date:** 2026-07-18
**Scope:** Operator → Invitations → "Send invitation by email" flow (P1.5B one-click invitation email) plus the invitations-table status badges.
**Branch:** `main` working tree (see *Files changed*).

---

## 1. Symptom

An operator creates an invitation, the one-time signup link is generated correctly, but clicking **"Send invitation by email"** fails with the Arabic error:

> طلب إرسال بريد الدعوة غير صالح.
> *("The invitation email request is invalid.")*

This is the `operator.theInvitationEmailRequestIsInvalid` action error returned by
[`sendInvitationEmail`](../../actions/operator.ts) when its zod payload validation fails.

## 2. Root cause

The invitation link is built **in the operator's browser** from `window.location.origin`:

```tsx
// components/operator/operator-action-form.tsx
invitationLink={`${window.location.origin}/signup/${state.rawToken}`}
```

`sendInvitationEmail` then validated that link's origin **strictly** against a single
environment value:

```ts
const expectedOrigin = process.env.NEXT_PUBLIC_SITE_URL ? new URL(...).origin : null;
// refine: url.pathname.startsWith("/signup/") && (!expectedOrigin || url.origin === expectedOrigin)
```

The SEO production hardening changed the canonical marketing/site domain to **www**:

- `5dd4152 fix(seo): use canonical www domain` — `MARKETING_SITE_URL = "https://www.clinicflow.fit"`
- `b4cebb3 test(seo): update canonical www expectations`

After that change the operator browses at `https://www.clinicflow.fit`, so the link is built
with the **www** origin. But `NEXT_PUBLIC_SITE_URL` in Vercel Production still carried the older
**non-www** origin (`https://clinicflow.fit`). The two origins no longer byte-match, so
`url.origin === expectedOrigin` is `false`, the zod `.refine()` fails, and the action returns the
invalid-request error **before it ever looks up the invitation or calls the email provider.**

The design was fragile: it compared a client-reported origin against one hardcoded env origin,
unlike [`actions/auth.ts`](../../actions/auth.ts)'s `siteOrigin()` helper, which already resolves
"env when set, otherwise the request host." The same class of failure would also hit Vercel preview
hosts and any host that does not exactly equal the env var.

## 3. Fix (at the source)

`sendInvitationEmail` now accepts the link when its origin matches **either**:

1. the configured canonical origin (`NEXT_PUBLIC_SITE_URL`), **or**
2. the **actual request origin** (from `x-forwarded-host` / `x-forwarded-proto`) — where the
   operator genuinely is.

Both are app-controlled, so a www/non-www (or preview-host) mismatch between the deployed host and
the env var can no longer reject a legitimate link, while a foreign origin (matching neither) is
still refused and the path must still start with `/signup/`.

A new helper `resolveAllowedInvitationOrigins()` builds that allow-set, mirroring the resolution
already used by `auth.ts`. As a bonus this **closes the review's residual gap** (P15B-R9): when
`NEXT_PUBLIC_SITE_URL` is unset on previews/local, the check now pins to the request origin instead
of accepting any origin.

### Defense-in-depth hardening

The post-parse guard previously rejected only non-`pending` invitations. It now **also rejects
expired invitations** whose status has not yet been flipped (`expires_at <= now`), so an expired
link can never be emailed. Revoked/accepted/expired all return the existing safe
`operator.thisInvitationIsNoLongerAvailable` message.

### Preserved behavior (verified unchanged)

- Authorization: `requirePlatformAdmin()` still guards the action first.
- Token security: the raw token still lives **only** in the operator's browser; the server never
  persists or logs it; neither failure branch logs the link, token, email, or HTML body.
- Weekly invitation limits, issuance/resend token rotation, single-use consumption, and expiry are
  all handled in `issueClinicInvitation` and are untouched.
- Resend behavior, audit event (`invitation.email_sent`), and `email_sent_at` bookkeeping are
  unchanged; provider/transport failures still leave the invitation pending and the link valid.

## 4. Status-badge polish

The invitations table previously rendered the status as raw text (`row.status` / `"requested"`).
Added [`components/operator/invitation-status-badge.tsx`](../../components/operator/invitation-status-badge.tsx),
following the existing [`components/appointments/status-badge.tsx`](../../components/appointments/status-badge.tsx)
pattern (shadcn `Badge variant="outline"` + semantic classes), with consistent semantic colors:

| Status | Color |
|---|---|
| Pending | Warning — amber |
| Accepted | Success — emerald/green |
| Revoked | Destructive — red |
| Requested (pending, no token) | Neutral — muted |
| Expired | Neutral — muted |

New i18n keys `operator.pending` / `operator.revoked` / `operator.expired` added to
`messages/en.json` and `messages/ar.json` (`accepted` / `requested` already existed).

## 6. Tests added

Extended `tests/unit/actions/p15b-invitation-email.test.ts` (now 11 tests):

- **www regression** — env origin non-www, request host www, link on www origin → `{ ok: true }`
  (the exact failure this fix targets).
- Configured env origin still accepted when it matches.
- Origin matching **neither** env nor request origin → invalid, no send.
- Revoked invitation → rejected, no send/audit/write.
- Accepted invitation → rejected, no send.
- Expired invitation (status still pending, `expires_at` in the past) → rejected, no send.

Retained the pre-existing coverage: successful send + audit + `email_sent_at` without persisting the
token; provider-failure and transport-exception paths (sanitized logs, no token/PII leak); timestamp
bookkeeping failure still audits; foreign-origin / non-`/signup/` path rejection.
