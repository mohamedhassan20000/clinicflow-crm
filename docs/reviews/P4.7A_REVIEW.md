## Final Verdict: **APPROVED WITH MINOR FIXES** — *all findings remediated 2026-07-21 (see §8)*

P4.7A is a disciplined, correctly-scoped, low-risk sub-phase and the security-relevant parts are right. The central promise — *guidance can never contradict server-side authorization* — is enforced structurally, not by prompt: `href` is present only on `available`; the resolver re-derives all four gates (`ROLE_PAGE_SLUGS` **and** the target's own role list, entitlement + `subscriptionAllowed`, then `user_page_permissions`) from the same machinery the shell and middleware use; a failed visibility lookup fails **closed** (`lookup_failed`, no link); and the two tools re-assert `assertStaffToolAccess` on every invocation. Retrieval is deterministic and auditable (no embedding model), with a stop-token guard and a minimum-score floor that both defend against confident-but-wrong matches. The `staff_help` class genuinely retires caveat M6 — I verified independently that its mount resolves to exactly `search_help` + `get_navigation_target` with no clinic-data tool present, for administrative **and** doctor personas.

Independently verified during this review:
- **Deny-by-default + additivity**: help tools mount for every staff role under `ai_assistant` alone; absent that feature, neither mounts; help is additive in clinical/operational classes and exclusive in its own. (`resolveToolMount` task-class gate, confirmed by test and by re-reading `lib/ai/tools/index.ts:41-52`.)
- **Honesty cases**: hidden-page → section returned, no steps, no link, `unavailable_reason: hidden_by_admin`; `role_forbidden`/`not_entitled`/`lookup_failed` all withhold `href`; unknown id → denial, never a probe.
- **Reuse**: P4.6C normalizer/transliterator (`normalizeSearchText`/`transliterateQuery`), `getEntitlements`/`hasFeature`, `hasAiUserPermission`, `getPageVisibilityState`, `logAgentTool`, `assertStaffToolAccess`, `AI_ASSISTANT_FEATURE`/`AI_FINANCIAL_INSIGHTS_FEATURE` — all reused, nothing re-implemented.
- **Tests**: the three P4.7A suites re-run during this review — **48/48 passing** (the report's "41 new" undercounts; 48 across the three files).
- **No PHI, no new RLS surface, no migration, no new entitlement key** — as the roadmap requires; corpus is static product documentation.

No High or Medium findings. **Four Low** findings follow (one is a factual error in the report/roadmap; three are routing/convention issues that never weaken authorization and at most cost budget or an extra rephrase). Three Info notes. None blocks merge; L1 should be corrected because it is a stated count that is wrong, and L2/L3 are worth a design acknowledgement before P4.7B builds on the router.

## 4. Low Findings

### P47A-L1 — Report and roadmap claim 20 corpus articles; there are 19
**Files:** `docs/reports/P4_7A_IMPLEMENTATION.md` (§1 table, §2, §8, §9 all say "20"), `docs/AI_AGENT_PLAN.md` (P4.7A *Delivered* note: "20 curated ar/en articles")
**Category:** documentation-accuracy
**Impact:** `HELP_ARTICLES` contains exactly **19** entries (`register-new-patient` … `change-language-and-theme`; verified by id enumeration). Every place the deliverable is quantified states 20. No test asserts the count, so nothing catches the drift, and the review artifacts that future phases trust for "what shipped" are wrong by one. Purely a factual/counting error — no functional effect.
**Remediation:** Either correct every "20" to "19" in the implementation report and the roadmap *Delivered* note, or add the one missing article that was presumably intended. If the count is meant to be load-bearing, add a trivial `expect(HELP_ARTICLES.length).toBe(19)` so it cannot silently drift again.

### P47A-L2 — Help-intent false positives strand singular-entity *data* questions
**File:** `lib/ai/platform/execution.ts:120-171` (`isHelpIntent` / `AGGREGATION_LEAD_RE`), routing at `:207-212`
**Category:** correctness / router
**Impact:** The report argues (§6) that a help false-positive "is filtered by the aggregation guard in exactly the cases where it would have hurt." That is only true for *aggregation/list* phrasings. A data question phrased with a help opener but **no** aggregation word routes to `staff_help`, whose mount excludes every clinic-data tool — so the model cannot answer it that turn. Confirmed empirically:
- `"how do I see patient Mohamed's appointments"` → `staff_help` (no data tools mounted)
- `"how do I find a patient with diabetes"` → `staff_help`

In both, if the user wanted the record (not instructions), the turn cannot produce it; the assistant can only search help and describe navigation. Self-correcting (the user can rephrase to `"show me …"`, which the `show me (?!how)` branch keeps on the data class), and the phrasings are genuinely ambiguous, so impact is low — but the report's stated guarantee is stronger than the code delivers.
**Remediation:** No code change strictly required; recommend softening the report's claim to acknowledge that only aggregation/list false-positives are filtered, and that a data intent phrased as "how do I see/find <entity>" is answered as guidance for that turn. If undesired, consider extending the guard with singular-entity/data leads (patient-name/file-number/"see/find … appointments|visit|balance") — but weigh against the additive-mount safety net that already prevents any *authorization* harm.

### P47A-L3 — Cost-discipline goal missed for "report"/"list" help questions
**File:** `lib/ai/platform/execution.ts:143-161` (`AGGREGATION_LEAD_RE` includes `\b(list|report|reports)\b` and `تقرير|تقارير|قائمة`)
**Category:** cost / router
**Impact:** The phase's headline cost rationale is that help turns must not burn the clinical budget. But because the aggregation guard treats bare `report`/`list`/`تقرير`/`قائمة` as data leads, legitimate help questions containing those nouns are **excluded** from the cheap `staff_help` route and fall to the pricier administrative/operational class. Confirmed:
- `"how do I run a report"` → **not** help (blocked by `report`) — despite a dedicated `run-clinic-report` corpus article
- `"كيف أشغّل تقرير"` → **not** help (blocked by `تقرير`)
- `"how do I list my patients"` → **not** help (blocked by `list`)

Answer correctness is preserved (help tools are additive in those classes, so `search_help` still runs), but exactly the report/list "how do I" topics — which the corpus is built to answer — never get the cheap route the class exists to provide.
**Remediation:** Optional. The overlap is intrinsic to a keyword router. If cost on these topics matters, gate the `list|report` branch behind an aggregation verb (`how many … report`, `list of …`) rather than the bare noun, or check the instructional-opener first and only defer to the aggregation guard for true aggregation leads. Document the accepted trade-off either way, since it partly contradicts the "must not burn budget" motivation stated for the class.

### P47A-L4 — `notifications`/`profile`/`preferences` declare `pageSlug: "dashboard"`, contradicting the stated authoring convention
**File:** `lib/ai/help/navigation.ts:461-496`
**Category:** convention / latent-correctness
**Impact:** The authoring convention (`navigation.ts:35-38`) states `pageSlug` must be "the `PageSlug` the route belongs to, exactly as `getPageSlugFromPath` would classify `href`." For `/notifications`, `/profile`, `/preferences`, `getPageSlugFromPath` returns **`null`** (they are not in the page-visibility system) — yet these three targets declare `pageSlug: "dashboard"`. It is benign today: `getPageVisibilityState` short-circuits `dashboard` to `"visible"` and every role has `dashboard`, so all three correctly resolve `available`. But the declaration is not what the convention says, and it silently makes the page-visibility gate a no-op for these targets via the dashboard shortcut rather than because the routes are genuinely ungated. A future change to dashboard visibility semantics, or a reader trusting the convention, could be misled. The registry-integrity test only checks `pageSlug ∈ PAGE_DEFINITIONS`, which `"dashboard"` satisfies, so it does not catch this.
**Remediation:** Either document these three as an explicit exception ("routes with no `PageSlug`; mapped to `dashboard` because they are always visible") in the entries and the convention block, or model always-available routes without borrowing an unrelated slug. No behavior change needed.

## 5. Info / Nits

- **I1 — `guidance` group value is currently cosmetic.** `AssistantToolGroup` gains `"guidance"`, but the only consumer (`components/assistant/assistant-chat.tsx:182`) branches solely on `group === "financial"`. What actually keeps a help lookup from rendering as "reviewing records" is the `labelKey` (`toolSearchHelp`/`toolNavigation`), not the group. The new group is harmless and forward-looking (P4.7B may use it) but does not itself do the work the comment at `tool-presentation.ts:55-58` attributes to it. No `groupGuidance` i18n key is needed today, and none was added — correct.
- **I2 — Arabic keyword lists are consistently shorter than English** across several articles (e.g. `register-new-patient` 6 en / 5 ar). The parity test enforces only *non-empty* both sides and step-count parity, not keyword-count parity. Retrieval still resolves Arabic queries (tested), because normalization + transliteration + the title/summary fields carry the load, so this is acceptable — but it is an asymmetry the "full ar/en parity" language in the corpus header slightly oversells.
- **I3 — Two safe API refinements vs. the roadmap tool signatures.** `search_help` takes `limit?` and reads locale from `ctx.locale` (not a model-supplied `locale`); `get_navigation_target` takes a closed `target` enum (not a free `feature` string). Both reduce model-controlled surface and are improvements, not regressions — flagged only so the signature difference from §8 is on the record.
