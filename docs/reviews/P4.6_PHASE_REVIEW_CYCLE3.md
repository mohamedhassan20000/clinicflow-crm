## 2. High Findings

### H1 — Small-cell suppression is fully reversible via `ai_get_clinic_summary`, and again via `patients_new_in_range` inside its own payload

`supabase/migrations/20260720130000_p46a_staff_analytics.sql` (`ai_get_clinic_summary` `patients_total`; `ai_get_patient_stats` `patients_new_in_range`), `supabase/migrations/20260720160000_…sql` (the suppression emit loop), `lib/ai/tools/registry.ts:181-202`, `lib/ai/prompts/staff.ts` (both locales)

`ai_get_patient_stats` goes to considerable, correct trouble to make the suppressed residual unrecoverable. When anything is suppressed it sets `patients_total: null` and publishes only `patients_total_approx`, floor-rounded to the nearest 5. The migration comment states the reason plainly: *"otherwise a floor-rounded approximation, so the suppressed residual cannot be recovered by subtraction."* That is review #1's H1, and within this one payload it works.

**`ai_get_clinic_summary` publishes the same total, exactly, with no suppression and no rounding:**

```sql
'patients_total', (
  select count(*) from public.patients pt
  where pt.clinic_id = v_clinic_id and not pt.is_deleted
),
```

Both tools carry `roles: ANALYTICS` and `requiredFeatures: [AI_ASSISTANT_FEATURE, AI_STAFF_ANALYTICS_FEATURE]` in the registry (`registry.ts:181-202`), so they mount together, for the same users, on the same turn, always. There is no configuration in which a caller has one and not the other.

**Reproduced live.** A `pro_ai` clinic with 100 O+, 4 A+, 3 B+ patients, admin token, two RPC calls:

```
--- ai_get_patient_stats (suppressed) ---
{ "patients_total": null,
  "patients_total_approx": 105,
  "buckets": [ { "bucket": "O+", "count": 100, "suppressed": false },
               { "bucket": "A+", "count": null, "display": "<5", "suppression_reason": "below_floor" },
               { "bucket": "B+", "count": null, "display": "<5", "suppression_reason": "below_floor" } ] }

--- ai_get_clinic_summary (same roles, same turn) ---
{ "patients_total": 107 }
```

107 − 100 = **7**, the exact suppressed residual. Two buckets, each constrained to 1–4 by their own `"<5"` label, summing to 7 → {4, 3}. Buckets are emitted descending by size (`for v_index in reverse v_count..1`), so A+ ≥ B+, giving **A+ = 4 and B+ = 3 exactly**. Both small cells are recovered with certainty, from two tool calls the model makes routinely and is authorized to make.

**A second, independent vector lives inside `ai_get_patient_stats` itself.** `patients_new_in_range` is an exact, unsuppressed `count(*)` over the same `patients` table, and the buckets it sits beside are all-time. Whenever the requested range covers the clinic's history it *equals* the withheld total. Reproduced on the 100/4/3 clinic with all patients created recently: `patients_total: null`, `patients_total_approx: 105`, `patients_new_in_range: 107`. The exact total is published in the same object as the approximation that exists to hide it. `MAX_RANGE_DAYS = 400` is not a mitigation — for any clinic under ~13 months old a single call covers everything, and for an older one the exact totals of disjoint ≤400-day windows sum to it.

**Why this is High.** It is not a cross-tenant leak and not an escalation: admin and manager can already read `patients` rows through RLS and count blood types themselves, which is why review #1 rated the analogous DB-boundary gaps Medium. But suppression in this phase is not an RLS control — it is a control on **what leaves the platform for a third-party inference provider**, applied at the tool boundary, and it is the phase's headline privacy feature. At that boundary it currently does not hold. The payload handed to the model contains everything needed to invert it, and the only thing standing between that and a stated answer is a sentence in the system prompt.

That sentence does not cover this. Both locales say *"never derive one by subtracting the visible groups from **a total**"* — which reads as, and in context means, the total in that payload. Nothing tells the model that `patients_new_in_range` is a total, and nothing tells it that a figure from a *different tool* must not be used against these buckets. A model asked "what's our blood type breakdown?" that calls both tools — which is a natural thing for it to do, since `get_clinic_summary` is the general-purpose overview tool — has the arithmetic in front of it and no rule against it.

This is the third appearance of review #1's H1. It was closed within one SQL function, then closed again at the rendering layer, and it is still open at the level the control actually operates on: the union of what one turn puts into model context.

**Suggested direction (not applied):** the suppression decision has to be a property of the caller's whole analytics surface, not of one function. The cheapest correct version is to make `ai_get_clinic_summary` apply the same floor-rounding to `patients_total` whenever the same clinic's `ai_get_patient_stats` would suppress anything — or, more simply and more robustly, to round `patients_total` in `ai_get_clinic_summary` unconditionally under the same floor, and to suppress or coarsen `patients_new_in_range` in `ai_get_patient_stats` on the same condition its sibling total is withheld. Whichever is chosen, the invariant worth stating and testing is: *no two tools available to the same caller may jointly determine a suppressed cell.* A test that calls every mounted analytics tool for one fixture clinic and asserts no suppressed bucket is solvable from the union would keep it closed — and would have caught this.

## 3. Medium Findings

### M1 — `patients_total_approx` publishes `0` for a clinic that has patients

`20260720160000_…sql` (`round(v_total::numeric / v_floor) * v_floor`)

Reproduced live: a clinic with **2** patients returns

```json
{ "patients_total": null, "patients_total_approx": 0, "patients_total_exact": false,
  "patients_total_approx_direction": "nearest",
  "patients_new_in_range": 2, "distribution_withheld": true }
```

`round(2/5)*5 = 0`. The L8 fix correctly established that rounding to nearest is the right privacy choice and correctly disclosed that the result may err in either direction — but "may be slightly higher or lower" does not prepare a user for **zero**. An admin asking about a two-patient clinic is told, under a prompt that mandates verbatim relay, that the clinic has approximately no patients. It reads as a broken tool, which is the same trust cost review #2's H1 identified, and the phase's own copy (`noticeApproximateTotal`) offers no way to distinguish "rounded to 0" from "empty".

It is also internally contradictory in the same object: `patients_total_approx: 0` next to `patients_new_in_range: 2`.

Clamping the approximation to a minimum of the floor when `v_total > 0` would fix the falsehood without weakening the privacy property (it publishes a *weaker* bound, not a stronger one). Note this interacts with H1 — as it stands, `approx: 0` combined with `new_in_range: 2` reveals the total exactly.

### M2 — The anti-subtraction prompt rule is the only remaining guard, and it names the wrong field

`lib/ai/prompts/staff.ts` (both locales), `lib/ai/tools/get-patient-stats.ts` (description)

Recorded separately from H1 because it is a distinct layer with a distinct fix, and because it is worth being explicit about what the prompt currently is and is not doing.

Both locales and the tool description carry the rule *"never derive one by subtracting the visible groups from a total"* / *"ولا بالطرح من الإجمالي"*. Written when the only total in scope was the one the same payload withholds, that phrasing was complete. It is now the sole barrier against H1's two vectors, and it addresses neither by name: it does not identify `patients_new_in_range` as a total, and it says nothing about combining figures across tool results.

The prompt layer is explicitly framed in `untrusted-text.ts` as blast-radius reduction rather than as what makes the system safe, and that framing is correct — which is precisely why it should not be load-bearing here. Whatever is done for H1 at the data layer, the rule should also be widened to "from any total, including one returned by a different tool in this conversation."

## 4. Low Findings

**L1 — `usage_limit_reached` is converted to a tool result, so the turn continues after the cap.** `lib/ai/tools/index.ts` (`harden`/`DENIAL_GUIDANCE`). The decision to convert every `AiToolAuthorizationError` uniformly is right, and `DENIAL_GUIDANCE.usage_limit_reached` correctly tells the model *"no further tools can run until the limit resets. Do not retry."* But that is guidance, not enforcement: the model may still call other tools, each of which will also be denied, audited, and — importantly — each round trip continues to consume provider tokens on a clinic that has already hit its monthly assistant limit. The pre-stream reservation in `prepareAiExecution` makes this rare rather than routine, so this is a cost-control note, not a correctness defect. Worth recording because `usage_limit_reached` is the one reason in the union where "let the model keep going and explain" has a billing consequence the others do not.

**L2 — Whitespace collapse is still lossy for pass-through free text, and is not signalled.** `lib/ai/untrusted-text.ts` (`sanitizeOne`: `text.replace(/\s+/g, " ")`). Review #1's M7 named two lossy rules — the 200-character cap and the newline/whitespace collapse. The cap was correctly made field-aware (`NAME_TEXT_LENGTH` / `FREE_TEXT_LENGTH`) and truncation is now surfaced via `text_truncated_fields`; the collapse was not revisited and still applies to every string, including the ≤2,000-character report free text `run_clinic_report` passes through from `lib/reports/data.ts`. Multi-line cancellation reasons and follow-up notes therefore still reach the model reflowed into one line, with no equivalent of `text_truncated_fields` to say so. The rule's justification (*"newlines let a single field pose as several"*) is sound for names and defensible for free text; the gap is only that M7 was reported as fully closed when one of its two halves is unchanged and unsignalled.

**L3 — The transport that now carries denials is the one not announced to screen readers.** `components/assistant/assistant-chat.tsx:244-249` renders `failureCopy` in a plain `<p>` inside `ToolActivity`, while the pre-stream error banner at `:588` carries `role="alert"` and the live region at `:497` announces only `busy`/`announcement`. Before review #2's H2 fix this did not matter — tool denials rendered as a generic chip nobody would want announced. Now that a revoked grant, a hidden page, or a lapsed subscription renders here as its own localized, actionable sentence, it is the primary denial channel and it is silent for assistive technology, while the secondary channel is not. Adding the tool-part failure copy to the existing live region (or `role="alert"` on that `<p>`) would align the two.

**L4 — Below-floor bucket *labels* are still published in the partial case, while the fully-withheld case removes them.** `20260720160000_…sql` emit loop. When suppression is partial, a `below_floor` bucket is emitted as `{ "bucket": "AB+", "display": "<5" }` — disclosing that the clinic has between 1 and 4 patients of that category. When suppression is total, the H1.2 fix removes the labels entirely, with the explicit and correct reasoning that emitting labels *"published 'this clinic has A+ patients' for nothing in return."* That reasoning applies equally to the partial case: the label is published, and what is returned in exchange is a range of 1–4. The two cases take opposite positions on the same question. This is defensible as-is — `"<5"` is the conventional k-anonymity presentation and the tool description discloses it — but the inconsistency should be a decision on record rather than an artifact of which case the fix touched.

**L5 — Notices are keyed by `notice.kind`.** `assistant-chat.tsx:253` (`key={notice.kind}`). `summarizeToolResult` cannot currently emit two notices of the same kind, so this is unreachable today. It becomes a silently dropped notice — a caveat the honesty pipeline exists to guarantee — the first time it can. A stable index or a composite key costs nothing.

## 5. Architecture, Security, Authorization & RLS

**The five-authority model holds, and I verified the database layer rather than reading it.** `pg_proc` confirms every P4.6 `SECURITY DEFINER` function is `stable`, and that the ACLs match the migrations exactly: `effective_ai_feature` is `{postgres=X/postgres}` and nothing else, reachable only from inside the DEFINER guard, which is what makes calling it a strengthening rather than a new surface. `normalize_search_text` and `normalize_phone` no longer carry the `PUBLIC` grant. `ai_permission_is_grantable` is `immutable` and `search_path`-pinned.

**The primary-admin rule is now enforced in every layer that can enforce it.** The `is_primary_clinic_admin` predicate is lifted from `assert_primary_ai_provider_admin` and matches `lib/primary-admin.ts` filter-for-filter and tiebreak-for-tiebreak; I compared all three. `SECURITY DEFINER` is correctly justified — as `INVOKER` the function would re-enter `profiles`' own RLS from inside a policy on another table — and it discloses nothing beyond a boolean about arguments the caller already supplies. The policy carries the predicate in both `using` and `with check`, so read, insert, update, and delete are all covered, and the `with check` additionally pins the target row's role through `ai_permission_is_grantable`. Review #2's own two-call reproduction is retained inverted as a regression test.

**Identity remains server-derived throughout.** No tool accepts a clinic id, actor id, or role. No aggregate RPC takes a tenant parameter — each re-resolves `auth_clinic_id()` itself. `verifiedId` closes the model-asserted-uuid path. `resolveToolMount` builds `grantedPermissions` from server reads, and `run_clinic_report` only ever *reads* that set for its description, with `describedByUserPermissions` making "this permission changes what I say, not what I may do" a declared property rather than a comment.

**Deny-by-default is structural.** A tool cannot be registered without declaring `roles`, `requiredFeatures`, and `taskClasses`; the mount filter reads all three; and each `execute()` re-asserts independently. The registry is consistent across all 15 entries — I checked each against its tool's internal gate and found no repeat of review #1's H1 class (a registry gate looser than its execute gate) anywhere.

**The one authorization property not enforced structurally is the one H1 reports** — and it is a different shape from every previous finding. It is not a missing gate on any single path. Every individual gate is correct. It is that a privacy invariant defined over *one function's output* is not preserved over the *union of outputs* the same mount produces. Nothing in the current architecture has a place to express that, which is why no layer caught it.

## 6. Prompt-Injection & Privacy

The three-layer injection model is unchanged and remains honestly framed — `untrusted-text.ts` still states plainly that neutralization reduces blast radius and is not what makes the system safe. Denial results pass through the same sanitize/provenance tail as any other result (`harden()` deliberately falls through rather than short-circuiting), and `isSystemAuthored` correctly gives them `system_generated:` provenance rather than the tenant framing. `DENIAL_GUIDANCE` enumerating every reason so a new one is a compile error is the right construction, and it mirrors `ERROR_COPY_KEYS` on the client half.

The field-aware cap is implemented the right way round — matched on the key, which we author, never the value, which tenants author — and `text_truncated_fields` closes the silent-truncation gap for length. See L2 for the whitespace half.

**Privacy is where this phase still has an open item**, and it is H1. The suppression construction is sound, the rendering is now truthful, and the terminal case is declined honestly. What is missing is that the property was reasoned about one function at a time. §5's framing applies: the control operates on what one turn sends to a third-party provider, so its correctness condition is a property of the turn, not of the function.

M5 of review #1 (PHI egress in the clarification candidate set) remains correctly closed — full `phone`/`email` only for a single `high`-confidence match, `contact_details_withheld` on the payload, and the tool description explains the absence so the model does not appear to have lost data.

## 7. UI Integration & Cross-Component Coherence

`lib/ai/capabilities.ts` deriving affordances from `resolveToolMount` remains the strongest structural decision in the phase — the panel and the model's tool array cannot disagree because there is one resolution — and the `unavailable` state closes the last case where the panel sent a user to the wrong person. The deliberate omission of `taskClass` (returning the union rather than one turn's mount) is correct for a UI superset and documented as such. The `Sentry`-captured fallback to `EMPTY` degrades affordances without degrading chat.

`ERROR_COPY_KEYS` typed by `AssistantErrorCode` and consulted by all three transports is the correct resolution of review #2's H2, and `noticeText`'s `permission_denied` branch keying off the same table means one denial cannot read three ways depending on how it arrived. `isAssistantErrorCode`'s fallback for unrecognized `errorText` is the right call — an SDK-internal string must not reach the user untranslated.

`tool-presentation.ts` remains dependency-free and non-authoritative with an explicit "a tool absent from this map still works" contract, and `safeInternalLink` still rejects `//host`, `/\host`, and non-absolute values.

The settings surface's three seams from review #1 (L10, L11, L12) are all closed, and `AiFinancialPermissions` remains the best-composed file in P4.6. i18n parity holds across both locales for all new copy — `noticeSuppressedMixed`, `noticeDistributionWithheld`, `errorPageHidden`, `errorRoleForbidden`, `errorLookupFailed`, `errorUnauthenticated` are all present and translated.

Residual UI items are L3 (a11y on the tool-part denial) and L5 (notice keying), neither of which is exploitable.

## 12. Summary

P4.6 is architecturally strong and two full fix cycles have made it substantially stronger. The database boundary enforces role, entitlement, per-user grant, and now the primary-admin rule, each verified live rather than inferred. The error transport is understood correctly and handled correctly across all three of its channels, pinned by tests that drive the real SDK. The audit ledger covers every invocation class at the one boundary that cannot be forgotten. Suppression renders truthfully and declines honestly when it has nothing to say. Every one of the 37 findings raised by the two previous reviews is closed, and none of the fixes introduced a regression.

The one blocking finding is the phase's oldest, appearing at a scope neither previous review examined. Small-cell suppression withholds the exact patient total from `ai_get_patient_stats` so that hidden buckets cannot be recovered by subtraction — and hands the same total, exact and unrounded, to the same user, in the same turn, through `ai_get_clinic_summary`. Two RPC calls and one subtraction recover both suppressed cells exactly; I ran them. The construction is right, the rendering is right, and the invariant is still violated, because it was never defined over the thing it has to hold for: the set of tools a caller actually has.

That is the corrective this phase already knows how to apply. `resolveToolMount` is trustworthy because the UI and the model read one resolution. `ai_assert_analytics_caller` is trustworthy because all five RPCs pass through one guard. Suppression is not yet trustworthy because five functions each decide independently what they may publish about the same population. The fix is the same shape as the two that worked: give the property one place to live, and test it where it actually has to hold.
