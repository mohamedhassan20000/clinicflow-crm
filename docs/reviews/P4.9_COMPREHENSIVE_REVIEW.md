Live integration coverage confirms non-null actor attribution on insert/update/delete for both tables and rejection of unauthorized/cross-clinic attempts.
- **P49A-M2 (source-inspection isolation tests):** replaced with genuine behavioral parity tests that exercise the real launcher resolver, `assertStaffToolAccess`, `assertFinancialInsightsAccess`, and `resolveToolMount`, comparing tool sets across placement changes.

No new high-, medium-, or low-severity **defect** was found. One low-severity **UX/documentation** observation is recorded below; it is non-blocking and does not affect the verdict.

## Cross-cutting assessment

- **Authorization:** `/settings/assistant` is `requireRole("admin")` → `isPrimaryClinicAdmin` → `/dashboard` redirect otherwise, resolving entitlement before any placement read. Both actions share `requireCustomizationAdmin` (mutation-role admin → primary admin → entitlement). Nav entry is gated by `canCustomize = admin && primary` in the settings layout, matching the page gate exactly. No secondary-admin or non-`pro_ai` path reaches a write.
- **RLS / tenant isolation:** both tables enable RLS, revoke anon/public, read via `auth_clinic_id()`, and write only under `is_primary_clinic_admin`. The role-settings write policy additionally enforces `updated_by = auth.uid()`. The user-override FK `(user_id, clinic_id) → profiles(id, clinic_id)` prevents cross-tenant targeting; the action independently re-verifies a same-clinic, active, non-deleted, registry-eligible target. Live two-clinic denial coverage passes.
- **Auditing:** every successful mutation writes a non-PHI `assistant_launcher_placement:{insert|update|delete}` row with the real primary-admin `actor_id`, clinic, table, and old/new composite-keyed payload. Actorless writes are rejected. Reads (resolver + read model) fire no trigger.
- **PHI protection:** placement rows and the read model contain only area, role/user id, and booleans plus the active-staff directory (id, full_name, role). No patient, appointment, invoice, conversation, prompt, message, usage, or billing data is read or logged.
- **Billing / usage / rate-limit:** placement resolution and the settings surface reserve no AI budget, increment no usage, select no provider/model, and execute no tool. The read is a Server Component render; writes are server actions; no new public endpoint is added. Chat execution remains the sole billable boundary.
- **Accessibility / i18n / RTL:** matrix uses `scope="col"`/`scope="row"` headers, an `sr-only` caption, per-control `aria-label`s, ineligible cells expose an accessible "not available for this role" label with no toggle, controls are disabled while a mutation is in flight, the matrix scrolls in its own `overflow-x-auto` container, and copy is fully localized (en/ar) with logical properties (RTL gate clean).
- **Failure containment:** the resolver throws on lookup error and the P4.8 resolver fails soft (omits the optional launcher, keeps the host page). The settings page fetch runs in `try`/`catch` into a nullable `data` with the JSX chosen outside the block, so a load failure shows a localized `role="alert"` and a render error is not swallowed.
- **Performance:** entitlement uses the existing tagged cache; the resolver issues two bounded concurrent placement reads per launcher; the read model issues three bounded concurrent reads. Placement rows are uncached so changes take effect on the next server resolution.

## Findings

### P49-L1 — Role/user toggle presents resolved visibility without reflecting downstream P4.8 gates (informational)

- **Severity:** Low (UX/documentation; not a defect, not a regression)
- **File reference:** `components/settings/assistant-launcher-customizer.tsx:71-74` (`inheritedValue`), `:238` (`checked` for role cells), `:373` (`checked` for user cells)
- **Problem:** A toggle rendered "on" for, e.g., the `revenue`/`reports`/`invoices`/`staff` areas reflects only the placement value (role setting or code default). Whether a launcher actually appears for that role/user still depends on the independent P4.8 gates — `ai.financial_insights` / `ai.staff_analytics` feature entitlement, the `AI_FINANCIAL_INSIGHTS_PERMISSION` per-user permission, page visibility, and persistence readiness. An admin could enable a placement toggle and reasonably expect the launcher to appear when a downstream gate still suppresses it.
- **Why it matters:** Minor expectation gap only. It is on the correct side of the security boundary: the mismatch can only make a launcher *not appear* despite being toggled on — placement can never cause a launcher (or any access) to appear where the P4.8 gates deny it. The in-product "Placement changes visibility only" banner already states that showing a launcher never grants access; it does not state that a shown toggle may still be suppressed by other requirements.
- **Required fix:** None required for approval. Optional future polish: add a localized helper note (or a "may require additional plan/permission" hint on financial/analytics areas) clarifying that a toggle sets placement but the final launcher still honors plan, permission, and page gates.
- **Required regression tests:** None required. If the optional hint is added later, assert the note renders for the gated areas and that no authorization behavior changes.
