## Final Verdict: **APPROVED WITH MINOR FINDINGS**

P4.5A is a disciplined, well-scoped implementation that meets every stated acceptance criterion:

- **P4 behavior passes unchanged through the new boundary** — authorization, RLS clients, prompts, tools, rate limiting, conversation ownership, streaming shape, and successful-turn persistence are all intact.
- **Provider/model ids no longer escape policy code** — `resolveModelId()` and the direct `@ai-sdk/anthropic` dependency are removed; agents receive an opaque `AiExecutionHandle` and cannot select a model.
- **Concurrent requests cannot overspend the clinic pool** — enforced by a per-period `FOR UPDATE` lock inside a `SECURITY DEFINER` service-role RPC.
- **Usage events reconcile to mocked provider usage with no content** — the ledger is column-constrained, allowlist-validated, and immutable.

No Critical or High findings. One Medium finding (**M1**) concerns the strictness of the "actual cost can never exceed the reservation" invariant, which relies on an input guard that does not count all billable tokens; combined with the hard `CHECK` that rejects over-runs, a large-context successful turn could be dropped from the ledger and refunded. This is a budget-integrity edge, fail-open in the clinic's favor, with low real-world likelihood — it should be addressed but does not block merge. The remaining items are Low/informational.

## 2. Architecture

**Strong.** The layering matches the plan's "ClinicFlow-owned AI policy boundary":

- `lib/ai/client.ts` is now a thin re-export barrel; the single execution entry point is `prepareAiExecution()`. Agents consume `execution.model` / `execution.providerOptions` and never touch a provider.
- `types.ts` cleanly separates the `AiExecutionProvider` interface from the Gateway implementation, so a future direct/regional provider can be added behind the same seam (as the plan requires). Gateway-specific objects are confined to `managed-gateway.ts`.
- The registry is data-only and `as const satisfies`-typed, giving compile-time guarantees that every route/policy is well-formed.
- Reservation, provider preparation, step observation, and reconciliation are all owned by the handle returned from `prepareAiExecution`, keeping the route thin.

No architectural objections.

## 3. Security, Authorization, RLS

**Strong. No tenant-isolation or privilege defects.**

- All three new tables (`ai_budget_periods`, `ai_budget_reservations`, `ai_usage_events`) have RLS enabled with **no policies**, and `all` is revoked from `public`/`anon`/`authenticated`. They fail closed until P4.5C adds safe projections. Verified by the integration test (`own`/`crossClinic` reads denied).
- Both RPCs are `SECURITY DEFINER` with `set search_path = ''`, an in-body `auth.role() = 'service_role'` gate, **and** an execute grant restricted to `service_role` — defense in depth. Non-service callers are denied at both layers (tested).
- All object references inside the functions are schema-qualified (`public.*`, `public.usage_metric`), so the empty search_path cannot be exploited. Nested `increment_usage`/`release_usage` calls correctly retain the `service_role` claim (auth.role() is session-scoped, not changed by SECURITY DEFINER).
- Identity remains server-derived: the route computes `task`/`persona` from `authorizeStaffAssistant()`'s role and derives the request id from server-side clinic/user ids plus client conversation/message ids — the client never selects a model, task, persona, or budget.
- The managed Gateway adapter sends **no** clinic/user identity by default; only a one-way HMAC pseudonym when `AI_TRACKING_HMAC_KEY` is explicitly set (tested: raw ids never appear in `providerOptions`).
- P4A per-tool authorization, RLS-respecting tool clients, and audit logging are untouched; the boundary layers cost accounting **before** model spend without widening tool access.

## 4. Concurrency, Transactions, Race Conditions, Budget Enforcement

**Correct.**

- `reserve_ai_budget` upserts the period row, then `SELECT … FOR UPDATE` on `(clinic_id, period_start)`. All concurrent AI requests for one clinic serialize on that row, so the pool check (`spent + reserved + new > limit`) and the `increment_usage` compare-and-increment happen atomically. The "exactly one winner under a one-slot pool" integration test confirms this.
- Idempotency: `unique (clinic_id, request_id)` plus the serialized existing-reservation lookup guarantees a duplicate request id returns `acquired=false` rather than double-charging. The request id is stable across a genuine transport retry (derived from conversation+message ids), so SDK-level retries are correctly deduped.
- Legacy `ai_messages` reservation and the cost ceiling are claimed in **one** transaction; any later failure (insert, budget update) rolls back the `increment_usage` too. This closes the P4B "reservation leak between count and cost" gap by construction.
- Reconciliation is lease-bound (`lease_token` must match) and status-guarded (`status <> 'reserved'` returns `false`), so the one-shot retry in `execution.finalize` is safely idempotent — a lost-response retry finds a non-`reserved` row and inserts nothing.
- Crash recovery: abandoned leases are reclaimed opportunistically at the next reserve, each getting a content-free `expired` event and releasing its legacy unit and reserved cost inside the same locked transaction.

## 5. Reservation Lifecycle & Cost-Ledger Correctness

**Correct, with one edge (M1).**

- Success: observed per-step attempts are inserted immutably; `reserved_micros` is released and `spent_micros += actual`; reservation → `reconciled`; legacy unit retained. 
- Failure/abort: partial observed spend is still booked to `spent_micros` (the tokens were really consumed), the reservation → `released`, and the legacy `ai_messages` unit is compensated. This matches P4B's "failed/aborted turns don't consume the request count" behavior while now also capturing true cost.
- The ledger is genuinely content-free: an exact JSON key allowlist, typed `jsonb_to_recordset` coercion, per-column length/`>= 0` CHECKs, and no prompt/completion/patient/tool columns. The unit test asserts the reconciliation payload contains no `prompt|completion|message|patient|tool|body`.
- Immutability trigger correctly blocks direct `UPDATE`/`DELETE` (incl. service role) while allowing cascade delete at `pg_trigger_depth() > 1` for whole-tenant erasure — both paths tested.

**Finding M1 (Medium — cost-ledger integrity under large context).** The report (§P4 agent compatibility) states each step is "guarded before provider spend with a conservative UTF-8 input ceiling, ensuring the request stays within the cost-reserved task envelope." `assertAiInputWithinPolicy(messages, maxInputTokensPerStep)` measures only the serialized **conversation messages** — it excludes the system instructions and the tool JSON schemas, which are billed input tokens. The worst-case reservation therefore is not a strict mathematical upper bound on actual cost; it holds today only because the reservation prices the full `maxInputTokensPerStep` at the *cache-write* rate (3.75 M vs. 3.0 M normal input), leaving ~12k tokens of headroom that happens to absorb the omitted system/tool tokens. Two ways this margin can be lost:
1. Provider-side prompt caching (if ever enabled on this route) bills the oversized input at the cache-write rate the reservation assumed for the *bounded* portion only.
2. A future increase in system-prompt or tool-schema size narrows the headroom.

If actual ever exceeds reserved, the `actual_cost_micros <= reserved_cost_micros` CHECK (added explicitly in `…122000`) makes `reconcile_ai_budget` raise; `finalize` retries once, fails, and the error is swallowed to Sentry. The reservation stays `reserved` and is later reclaimed as **expired** — refunding both the cost and the legacy `ai_messages` unit for a turn that actually succeeded and cost real money. Net effect: a silently free successful turn plus unrecorded managed spend.
**Recommendation:** either (a) include the system prompt + tool-schema byte estimate in the per-step guard, or (b) have `reconcile_ai_budget` clamp `actual` to `reserved` (booking the reservation as spent) instead of hard-failing, so genuine spend is never dropped from the ledger. Low likelihood today (no caching configured, wide margin), but the failure mode undermines the ledger's role as the authoritative economic record.

## 6. Policy & Provider Abstraction, Type Safety

**Strong.**

- Task→persona and task→model-alias resolution fail closed: an unknown persona throws `task_not_allowed`; an env override that doesn't map to a certified alias throws `model_not_certified` (tested). Fallback aliases are validated against the registry even though none are active.
- Legacy `AI_MODEL_DOCTOR`/`AI_MODEL_PATIENT` overrides are honored **only** when they resolve to a certified registry entry — preserving P4 configurability without reopening the arbitrary-model path.
- Types are precise: `AiCredentialMode` is the literal `'managed'`; `CertifiedModelRoute.privacy` uses `true` literal types; the generated `Database` types for both RPCs match the SQL signatures and return shapes exactly. `StepResult<TOOLS>` from the `ai` package structurally satisfies `AiObservedStep` (verified against `node_modules/ai/dist/index.d.ts`: `stepNumber`, `model.{provider,modelId}`, `response.modelId`, `finishReason`, `usage` all present), so `onStepFinish: execution.observeStep` is sound.

## 7. Error Handling

**Good.** Budget denials (`AI_BUDGET_EXCEEDED`/`USAGE_LIMIT_EXCEEDED`) map to the existing `usage_limit_reached` (429) surface; unexpected reservation errors fail closed to `lookup_failed` with a generic message and a Sentry capture that carries only clinic id + task (no content). Reconciliation errors during streaming are swallowed to Sentry so the already-delivered stream is not disrupted. Error classes are allowlisted (`safeErrorClass`) before storage — the "provider timeout: secret detail" test confirms raw provider strings never reach the ledger.

## 8. Performance

**Acceptable.** The period-row `FOR UPDATE` serializes a single clinic's AI requests, which is fine at expected per-clinic concurrency. Indexes exist for the active-reservation reclaim (`… WHERE status='reserved'`) and for the ledger's clinic/period and request lookups. No N+1 or unbounded scans introduced.

## 11. Findings Summary

| ID | Severity | Area | Summary |
|---|---|---|---|
| **M1** | Medium | Cost ledger / budget integrity | Per-step input guard excludes system prompt + tool schemas, so the worst-case reservation is not a hard upper bound; an over-run makes `reconcile_ai_budget` hard-fail and later refund a successful, truly-billed turn, dropping the spend from the ledger. Fix by counting system/tool tokens **or** clamping actual→reserved in reconcile instead of rejecting. Low likelihood today. |
| **L1** | Low | Ledger fidelity | First step's `latency_ms` measures reservation→first-step wall time (includes history load / `convertToModelMessages` / network), not provider latency. Cosmetic; consider seeding `lastObservedAt` at stream start. |
| **L2** | Low | Budget model | The cost pool ceiling is `ai_messages.limit × worst-case-cost`, and each request consumes exactly one of each, so the pool binds at the same point as the request count — `spent_micros` is the only genuinely new economic signal in P4.5A. Acknowledged in the report; noted so P4.5C decouples the ceiling. |
| **L3** | Low | Limit-source divergence | Pool `budget_limit_micros` is derived from the app-side `checkUsageLimit` limit, while `increment_usage` re-resolves `greatest(plan_limit, counter.limit_snapshot)` server-side. On a mid-month plan downgrade with a grandfathered snapshot these disagree, so the pool can deny slightly before the count. Fail-closed edge. |
| **L4** | Low / Info | Idempotency lifecycle | A completed/released/expired `request_id` permanently blocks re-reservation (returns `lookup_failed`). Benign because the client generates a fresh message id per send; document the invariant so a future auto-retry/regenerate feature doesn't reuse ids. |
| **INFO-1** | Info | Ops | Lease reclamation is opportunistic (next-request driven); a clinic that makes one crashing request and never returns keeps that unit/cost reserved until it does. Fail-closed and disclosed (no reaper job in P4.5A). |
| **INFO-2** | Info | Migrations | `…121000` (function-body rewrite via `pg_get_functiondef` string replace) and `…122000` (named CHECK add) are dev-DB reconciliation migrations that no-op on a fresh database. They are guarded (post-substitution assertion / constraint-def check) but are brittle string surgery; prefer folding such fixes into the base migration before this reaches an environment with real history. |

No Critical or High findings.

## 12. Recommendation

**Merge-ready.** Address **M1** before P4.5C makes `spent_micros` a billable meter (its correctness assumption becomes financially load-bearing there). L1–L4 and INFO-1/2 are non-blocking and can be scheduled with P4.5B/C. The boundary is safe, provider-neutral, tenant-isolated, and preserves all reviewed Phase 4 behavior.
