## Final Verdict: **APPROVED WITH REQUIRED FIXES**

P4.6A is a strong, well-argued sub-phase. The registry refactor is the right shape and genuinely makes deny-by-default structural; the aggregate RPCs never accept a clinic id; the financial double gate is real and re-run per invocation; the two deviations from the roadmap matrix (managers excluded from follow-ups, per-report role lists in `run_clinic_report`) are correct, narrow access rather than widen it, and are exactly the right instinct — *the assistant must not be a path to data the same user is refused in the UI*.

Verified independently: the registry's three gates behave as documented; `resolveToolMount` de-duplicates permission reads; every tool re-asserts inside `execute()`; the aggregate RPCs are `SECURITY DEFINER` / `STABLE` / `set search_path = ''` with `revoke all … from public`; the ranked search RPCs are `SECURITY INVOKER` and clinic isolation is genuinely inherited (`profiles_select_same_clinic`, `departments_select_own`, `services_select` are all `auth_clinic_id()`-scoped); `run_clinic_report` denies before any read. `tests/unit/ai/p46a-staff-analytics-tools.test.ts` re-run during this review: **35/35 passing**.

However, three findings must be fixed before P4.6B mounts these tools in the UI:

- **H1** — small-cell suppression in `ai_get_patient_stats` is **defeated by complementary disclosure**: the exact clinic total is returned alongside a bucket set that partitions it, so a suppressed bucket is recoverable by subtraction. This is the phase's headline privacy control and it does not currently hold.
- **H2** — the *second* line of defense is weaker than registration for receptionists. Both `assertAnalyticsToolAccess` and the SQL guard `ai_assert_analytics_caller` permit receptionists on `get_clinic_summary` / `get_patient_stats` / `get_appointment_stats`, which the registry restricts to admin/manager. The report's §5 claim that "each `execute()` re-runs role" is only true against *doctors*.
- **H3** — `user_ai_permissions` has a cross-tenant primary-key squat: the PK is `(user_id, permission_key)` but the RLS policies scope on the row's own `clinic_id`, and nothing binds `clinic_id` to the target user's actual clinic.

Six Medium, nine Low, and three Info findings follow. No finding is a live cross-tenant data leak.

## 2. High Findings

### H1 — Small-cell suppression is reversible by subtraction (`ai_get_patient_stats`)

`supabase/migrations/20260720130000_p46a_staff_analytics.sql:312-319`

The RPC returns, in one payload:

- `patients_total` — the exact count of all non-deleted patients in the clinic, **unsuppressed**; and
- `buckets` — a grouping over **that identical population** (`clinic_id = v_clinic_id and not pt.is_deleted`, no range predicate), where every patient falls into exactly one bucket because all three groupings `coalesce` their null case into `'Unassigned'` / `'Unknown'`.

The buckets therefore sum to `patients_total` by construction. When exactly one bucket is suppressed — the common case in a small clinic, and the *only* case suppression exists for — its exact count is:

```
suppressed = patients_total − Σ(visible bucket counts)
```

Worked from the implementation report's own verification data (§6): one clinic, 8 patients, an `O+` bucket of 6 and an `A+` bucket of 2. The tool returns `patients_total: 8`, `O+ → count 6`, `A+ → count null, display "<5"`. `8 − 6 = 2`. The suppressed cell is recovered exactly. With `group_by: "blood_type"` and a clinic small enough for the assistant to also enumerate its patients through `list_appointments` or `search_authorized_patients`, this reverses into an attribute statement about identifiable individuals — precisely the outcome §7 of the expansion proposal and the 2026-07-19 roadmap revision commit to preventing.

Two independent reasons it does not hold today: (a) the unsuppressed total is published alongside the partition; (b) there is no secondary-suppression rule, so a lone suppressed cell is always solvable even without the total whenever the caller knows the population from another tool.

The model is explicitly instructed ("never infer an exact number for a suppressed bucket") — but this is a *data* property, not a prompting one. The arithmetic is trivial and the instruction is not a control.

**Required:** suppress complementarily. The conventional fix is: if any bucket is suppressed, suppress at least one more (the smallest visible one), and either omit `patients_total` from this payload or round it to the same floor. A `suppressed_bucket_count` field lets the model still answer honestly ("2 groups were too small to report").

**Also note:** `ai_get_appointment_stats` applies **no** suppression at all to its buckets (`:378-392`) — `group_by: "doctor"` returns exact per-doctor cancelled/no-show/completed counts with no floor. That is defensible (appointment counts per doctor are operational, not patient-attribute, data, and these roles see them on the reports page), but it is an asymmetry the implementation report does not state and should be recorded as a deliberate decision rather than left implicit.

### H2 — Receptionists pass both defense layers for admin/manager-only aggregates

`lib/ai/authorization.ts:99-128`; migration `:120-152`

Three tools are registry-restricted to `["admin","manager"]` (`ANALYTICS` in `registry.ts:69`): `get_clinic_summary`, `get_patient_stats`, `get_appointment_stats`. But:

- `ANALYTICS_ASSISTANT_ROLES = ["admin","manager","receptionist"]` — so `assertAnalyticsToolAccess`, the per-invocation re-check every one of those tools calls, **admits receptionists**.
- `ai_assert_analytics_caller(false)` raises only for doctors; a receptionist passes.

So for these three tools the layered model collapses to a single layer: the `roles` array in the registry. The implementation report's §5 "Per-invocation re-authorization: registration is never sufficient. Each `execute()` re-runs role…" and §2's "a wiring mistake here cannot become a data leak" are both accurate for doctors and inaccurate for receptionists. A future registry edit that widened `ANALYTICS` to `ADMINISTRATIVE` — a one-token change, and a plausible one given `list_appointments` and `run_clinic_report` legitimately use `ADMINISTRATIVE` — would hand receptionists the clinic-wide blood-type distribution with nothing else objecting.

This is not currently exploitable: the registry is correct, so the tool is not mounted for receptionists, and P4.6B has no other call path. It is a defense-in-depth failure, not a live leak — but the entire argument for why the registry refactor is safe rests on this layer existing.

The tests reinforce the blind spot: `p46a-staff-analytics-tools.test.ts:165` ("excludes receptionists from clinic-wide aggregate tools") asserts only on the *mount*, and the integration suite asserts a receptionist denial only on the **financial** RPC (`:192`).

**Required:** split the role sets. Introduce a clinic-wide analytics assert (`admin`/`manager`) distinct from the operational-list assert (`admin`/`manager`/`receptionist`), point the three aggregate tools at the former, and add the receptionist branch to `ai_assert_analytics_caller` via a scope parameter (`operational` | `clinic_analytics` | `financial`). Add both a unit test (receptionist → `execute()` throws) and an integration test (receptionist → `ai_get_patient_stats` raises `42501`).

### H3 — `user_ai_permissions` allows a cross-tenant primary-key squat

Migration `:29-91`

```sql
primary key (user_id, permission_key)
```
…while both policies scope on `user_ai_permissions.clinic_id`, and **nothing constrains `clinic_id` to the target user's own clinic** — no composite FK to `profiles (id, clinic_id)`, no trigger, no check.

An admin in clinic B can therefore insert `(user_id = <a clinic-A manager>, permission_key = 'ai.financial_insights', clinic_id = <clinic B>)`. The `with check` passes (the row's `clinic_id` is B, and the actor is a B admin). Consequences:

1. **Denial of service across tenants.** The PK is now taken. Clinic A's admin calling `setStaffAiPermission` performs an upsert on `onConflict: "user_id,permission_key"`; the conflicting row belongs to clinic B, so clinic A's admin policy does not match it and the `UPDATE` half is refused. Clinic A can never grant that manager the financial permission, with no diagnosable reason surfaced to them.
2. The squatted row is **inert for reads** — `hasAiUserPermission` filters `.eq("clinic_id", user.clinicId)` (`lib/ai/permissions.ts:46`), so it cannot grant anything. Fails closed, correctly.

So: no privilege escalation, but a real cross-tenant integrity and availability defect in a brand-new table. It also means `clinic_id` is denormalized with no invariant, which will not age well.

Worth checking against `user_page_permissions`, which the report says this "mirrors exactly" — if that table carries the same shape, the finding applies there too and predates P4.6A; if it does not, the mirroring claim needs correcting.

**Required:** make the PK `(clinic_id, user_id, permission_key)` **and** add a composite FK `(user_id, clinic_id) references profiles (id, clinic_id)` (requires a unique constraint on `profiles (id, clinic_id)`), or enforce the same with a `before insert or update` trigger. Then the squat is rejected at write time.

## 3. Medium Findings

### M1 — `compare_revenue_periods` escapes the 400-day range clamp

`lib/ai/tools/compare-revenue-periods.ts:36-45`

It calls `resolveDateRange({ preset: "custom", … })` directly rather than `resolveToolDateRange`, so `MAX_RANGE_DAYS` (`range.ts:35`) never applies. The model can request `period_a = 2000-01-01 … 2026-07-20`, and the RPC will aggregate over `appointments`, `outstanding_settlements`, and `patient_deposits` for the whole history — twice, since `ai_compare_revenue_periods` calls `ai_get_revenue_summary` for each period.

This directly contradicts §5 of the implementation report: "Date ranges resolve through the same `resolveDateRange` core … and are clamped to 400 days, so no tool can be steered into an unbounded historical scan." It is also the *most* expensive tool to leave unclamped. Route both periods through `resolveToolDateRange` (or extract the clamp into a shared helper the custom path also uses).

### M2 — `taskClasses` registry metadata is declared and never read

`lib/ai/tools/registry.ts:62,72-81`

Every definition carries `taskClasses`, and `resolveToolMount` (`index.ts:32-55`) filters on role, features, and permission only. Grepping the tree, `taskClasses` is referenced nowhere outside `registry.ts` itself. So a `staff_clinical_summary` turn mounts nothing extra today only because the *role* happens to align — the declared contract that a task class constrains the tool surface is not enforced anywhere.

This matters beyond tidiness: the roadmap makes the registry the step vocabulary for P4.11 workflows and the source for P4.7's capability panel. Metadata that has never been executed will be wrong by the time something depends on it. Either filter the mount by `ctx` task class (the honest reading of §12 "task-class routing"), or drop the field until P4.7 needs it.

### M3 — Task-class routing is entitlement-gated, not intent-gated, and silently narrows the administrative persona

`lib/ai/platform/execution.ts:82-95`, `platform/registry.ts:94-105`, `app/api/agent/chat/route.ts:111-116`

`staffTaskForRole` returns `staff_operational_query` for **every** non-doctor turn whenever the clinic holds `ai.staff_analytics`. Since that key resolves true exactly on `pro_ai`, and `pro`/`basic` have no assistant at all, `staff_administrative` becomes effectively unreachable in production. Two consequences:

1. Every administrative turn on a paying clinic now runs at `maxSteps: 6` / `maxOutputTokens: 1200`, down from the base policy — including turns that use no analytics tool at all (a plain patient lookup, an availability check, an open-ended question). The tighter budget is justified for "typed aggregates and bounded lists" as the comment says; it was not justified for the general administrative persona, and this is a silent behavioral regression for the P4B surface.
2. A **receptionist** turn is routed to `staff_operational_query` even though the receptionist's operational mount is narrower.

The proposal's §12 describes routing per *task* ("`staff_help` for help/navigation; `staff_operational_query` for lists/stats"), not per entitlement. Recommend either keeping `staff_administrative` as the default and switching classes on detected intent (P4.7 will need this machinery anyway), or — if entitlement-based routing is the deliberate simplification — raising `staff_operational_query`'s budgets to the administrative baseline and recording the decision, since it is now the only administrative class that runs.

### M4 — UUID passthrough lets the model assert an entity id from free text

`lib/ai/tools/entity-filters.ts:56-60, 75-79`

```ts
if (UUID_RE.test(value.trim())) {
  return { status: "resolved", id: value.trim(), label: value.trim() };
}
```

A uuid-shaped argument short-circuits ranked resolution entirely: no lookup, no clinic check, no existence check, no confidence contract. This is a direct contradiction of the trust boundary the roadmap states repeatedly ("ids always come from resolution or user choice… the model never *asserts* an entity id from free text", §1154; expansion proposal §16). The `get_clinic_summary` payload hands the model a full doctor/department id directory, so it has a legitimate supply of uuids — but it also has conversation history, and a hallucinated or user-pasted uuid is accepted verbatim.

Impact is contained, not nil: `list_appointments` adds `.eq("clinic_id", …)` plus RLS, so a foreign uuid yields an empty list rather than a leak. The real risk is *silent wrong answers* — `run_clinic_report` passes `doctorFilter.id` straight into `getDoctorPerformanceData` (`run-clinic-report.ts:174-178`), and a stale-but-valid id produces a confidently reported report about the wrong doctor with no clarification path. It also silently reports "no appointments" for an id the caller mistyped.

Recommend validating any uuid against the same RPC (or a cheap `id`-scoped select) and falling into `not_found` when it does not resolve within the caller's visibility.

### M5 — The new trigram indexes cannot be used by the functions they were added for

Migration `:583-593` vs `:625-657`, `:683-715`, `:740-772`

The three indexes are `gin (search_name gin_trgm_ops)`. The three ranked functions never use a trigram-indexable operator — no `%`, no `<%`, no `<->`. They compute `similarity()` / `word_similarity()` as scalar expressions inside a CTE and then filter on the *result* (`where s.exact_name or s.prefix_name or s.name_score >= 0.18`). GIN trigram indexes accelerate the operators, not the functions; a predicate on a computed score is not sargable. Planner behavior here is a full scan of `profiles` / `departments` / `services` with a per-row similarity computation, then a sort.

Also note `like v_query || '%'` on a `gin_trgm_ops` index is not a prefix-index path either (that would need `text_pattern_ops` btree).

Practical impact is small — these tables are per-clinic and hundreds of rows at most — so this is a correctness-of-claim and future-cost issue rather than a live problem. But the implementation report presents the indexes as the performance story, and they are currently dead weight (with a write cost on every `profiles` update). Either add a `search_name % v_query` conjunct so the index is genuinely consulted before scoring, or drop the indexes and state plainly that these are scan-and-rank over small tables.

*(If `search_patients_ranked` from P4.6C shares this structure, the same applies there on a table that actually grows — worth a follow-up check even though P4.6C is out of scope here.)*

### M6 — `list_outstanding_invoices` is unbounded in time and includes non-billable appointments

`lib/ai/tools/list-outstanding-invoices.ts:35-42`

The only predicates are `clinic_id`, `deleted_at is null`, and `outstanding_amount > 0`. There is no date range (this is the one tool with no range input at all) and no `status` filter, so:

- it scans the full appointment history ordered by `outstanding_amount desc`; and
- it counts `cancelled` and `no_show` appointments carrying a residual `outstanding_amount` as outstanding balances.

Compare `ai_get_revenue_summary`, which scopes strictly to `status = 'completed'` (migration `:437`). So `list_outstanding_invoices` and `get_revenue_summary` can disagree about what is outstanding — and the report's stated goal for the financial tools is that the assistant's figures reconcile with the report page a user can open. Recommend aligning the status predicate with the invoices/revenue definition and adding an optional (clamped) range or an explicit "all time" acknowledgement in the returned payload.

## 4. Low Findings

**L1 — Range clamping is silent.** `range.ts:44-47` falls back to `this_month` when the span exceeds 400 days *or* when `preset: "custom"` arrives without both dates. The model is never told the substitution happened; it learns the effective range only by noticing `describeRange` disagrees with what it asked for. Return an explicit `clamped: true` / `requested` pair so the assistant can say "I limited that to this month" instead of quietly answering a different question.

**L2 — Audit `tableName` is inaccurate for several tools.** `get_clinic_summary` logs `tableName: "appointments"` though it reads departments, profiles, patients, appointments, and follow-ups; `run_clinic_report` logs `"appointments"` for every report including `followups` and `revenue`. The audit ledger is the answer to "what did the assistant touch"; a fixed wrong value degrades it. Log the report id / a `multiple` sentinel, or the primary table per report.

**L3 — Inconsistent grant hardening in the migration.** Every analytics RPC does `revoke all … from public` before granting to `authenticated`. `ai_suppress_small_cell` (`:116`) and all three `search_*_ranked` functions (`:661`, `:718`, `:775`) do not, so `EXECUTE` remains granted to `PUBLIC` by default (reaching `anon`). Harmless today — the search functions are `SECURITY INVOKER` and RLS returns nothing for `anon`, and the suppression helper is pure arithmetic — but it is an inconsistency inside one file and the kind that gets copied.

**L4 — Double-counted period boundaries.** Ranges use inclusive `<= p_end` for the current period and exclusive `< p_start` for the previous one (`:198/:203`, `:208/:213`). An event at exactly the boundary instant is counted in both the current period and the next call's period. Fine at day granularity as `resolveDateRange` produces it; worth normalizing to half-open `[start, end)` throughout so the trend arithmetic is unambiguous.

**L5 — `actions/ai-permissions.ts` is entirely untested.** This is the only write path for the financial grant — the control that decision 22 makes load-bearing. Untested: the `requireMutationRole("admin")` gate, the entitlement precondition, the `GRANTABLE_ROLES` role gate, the cross-clinic target rejection, and the `revalidatePath` behavior. §1067 of the plan calls for the permission matrix to be tested; the read side is well covered and the write side is not.

**L6 — No request-scoped memoization of the per-invocation checks.** `getEntitlements` is `unstable_cache`-backed, but `getPageVisibilityState` and `hasAiUserPermission` are not. `assertFinancialInsightsAccess` → `assertAnalyticsToolAccess` → `assertStaffToolAccess` means a single financial tool call issues one visibility read plus one permission read, and a 6-step turn calling several tools multiplies that. Correct (deliberately re-checked per call), but a `React.cache`-scoped memo per request would keep the semantics while removing the repeated round-trips.

**L7 — `get_patient_stats` buckets ignore the date range.** `patients_total` and `patients_new_in_range` respect `p_start`/`p_end`, but the `grouped` CTE (`:288-300`) has no range predicate — the distribution is always all-time. The payload nonetheless echoes `range`, and the tool description says "a distribution grouped by…", so a user asking "blood-type distribution this month" receives all-time buckets labelled with a month. Either scope the buckets to the range or rename/annotate the field (`buckets_all_time`) so the model cannot describe it wrongly.

**L8 — `list_pending_followups` returns patient phone numbers.** Both the `pending` and `recorded` mappings include `patient_phone`. The implementation report's field-allow-list rationale (§5) lists what was *stripped* (`national_id`, `payment_note`, amounts) but does not mention that direct contact details are retained and handed to the model. Defensible — the follow-ups page shows phones and the worklist is for calling people — but it should be an explicit, recorded decision, since it is the largest quantity of patient contact data any P4.6A tool emits (up to 50 rows per call).

**L9 — `docsSlug` is declared on `AiToolDefinition` and never set or read** on any of the 15 entries. Same category as M2; drop it or populate it.

## 5. Architecture, Security & RLS Assessment

**What holds up well:**

- **No RPC accepts a clinic id.** Verified across all five aggregate functions. Tenancy is re-derived from `auth_clinic_id()` inside the guard, matching the "identity is server-derived" rule everywhere else in the assistant. `p46a-staff-analytics-tools.test.ts:282` asserts this at the tool layer too, which is the right place to lock it.
- **`SECURITY INVOKER` for the ranked search functions is the correct call**, and it genuinely works: `profiles_select_same_clinic`, `departments_select_own`, and `services_select` are all `auth_clinic_id()`-scoped, so clinic isolation is inherited rather than re-implemented. Consistent with P4.6C's reasoning about soft-deleted patients.
- **`set search_path = ''` with fully-qualified references on every new function**, including the trigger. No shadowing surface.
- **`ai_compare_revenue_periods` delegating its guard** to `ai_get_revenue_summary` rather than re-implementing it is right, and the comment says why.
- **The financial double gate is real.** Entitlement and grant are both checked at mount *and* re-checked in `execute()`; `hasAiUserPermission` fails closed on lookup error; a revoked grant denies the next call. `:219` tests exactly this.
- **`run_clinic_report` denies before any read**, and its per-report role lists were checked against the underlying RPC guards — `get_followups_dashboard` does raise `42501` for managers (`20260512140000`), so both the tool's exclusion and the registry's are correct.
- **Field allow-lists are real allow-lists**, not omissions: `list_appointments` selects an explicit column list rather than `*`-then-strip, so a future column addition cannot leak by default. This is the right construction and worth preserving.

**Where the model is thinner than described:** H2 (second layer admits receptionists), H1 (the privacy control does not hold), M4 (id trust boundary). Together these mean the "defense in depth" framing in the implementation report is somewhat ahead of the code — the *first* layer is excellent, the second is partial.

**Prompt-injection surface (forward-looking, not a P4.6A defect):** `list_appointments` and `list_pending_followups` now return tenant-controlled free text (patient names) into the model's context — the exact scenario §1233 of the plan reserves for P4.12's adversarial corpus. P4.6A correctly does not own that work, but P4.6B mounting these tools is what makes the surface reachable in production. Worth flagging in the P4.6B plan rather than waiting for P4.12.

## 6. Tool Registry & Maintainability

The refactor achieves what it claims. `resolveToolMount` is 30 readable lines, the three gates are explicit, and the per-key permission de-duplication is a nice touch. The registry-integrity tests (`:626-660`) — every tool declares roles, features, bilingual copy; every financial tool declares both gates; no doctor-reachable analytics tool — are the right kind of test: they constrain future entries, not just current ones. This is the strongest part of the sub-phase.

Two structural notes beyond M2/L9:

- `buildDoctorTools` is now `buildStaffTools` verbatim (`index.ts:76-80`). Keeping the alias for compatibility is fine, but it now has no behavior of its own; a deprecation comment pointing at removal in P4.7 would stop it being mistaken for a distinct resolution path.
- `AI_TOOL_REGISTRY_BY_NAME` is exported and currently unused. Harmless (P4.11 will want it), but same family as M2.

## 7. Roadmap Compliance & Deviations

Both deviations from the §1055 matrix are **correct and should be kept**:

1. **Managers excluded from `list_pending_followups`** — verified: `get_followups_dashboard` raises `42501` for managers. Registering it would have shipped a guaranteed runtime error and advertised a non-existent access path.
2. **`run_clinic_report` per-report role lists** — each mirrors the underlying RPC's own guard, and denial precedes any read.

Both narrow access, both are motivated by the right principle, and both are documented in code comments at the point of the decision. Good practice.

**Process gap (I3):** the plan's normative matrix at §1055 still shows `list_pending_followups` as A/M/R. Shipped behavior and the roadmap now disagree in the document that is supposed to be normative. `AI_AGENT_PLAN.md` should be amended with the deviation and its justification, the same way the 2026-07-19/20 revisions were recorded — otherwise a future sub-phase will "fix" the registry back to the plan.

## 8. Performance

- **Aggregate RPCs:** one round-trip per question, aggregates only — the right shape, and far better than the model listing and counting. `ai_get_clinic_summary` does ~9 independent subqueries in one statement; on `appointments` filtered by `clinic_id` + `scheduled_at` this should be index-served, but it is worth confirming a composite index exists for `(clinic_id, scheduled_at)` and `(clinic_id, created_at)` on `patients` before P4.6B puts this on a hot path.
- **M1** (unclamped comparison) and **M6** (unbounded invoice scan) are the two real cost exposures.
- **M5**: the three new indexes do not serve their functions; they do add write amplification on `profiles`.
- **L6**: repeated visibility/permission reads per tool call.
- Adding three `STORED` generated columns takes an `ACCESS EXCLUSIVE` lock and rewrites `profiles`, `departments`, and `services`. All small tables, so acceptable — but this is a blocking DDL on `profiles`, which every authenticated request touches. Worth a line in the deploy notes.

## 12. Summary

P4.6A delivers its scope. The registry is the right keystone and is built well; the RPC design (no clinic id, server-derived tenancy, aggregates only) is sound; the financial double gate is real; and the two deviations from the roadmap matrix show good judgment about the assistant never being a back door. The gap between the implementation report's claims and the code is narrow but real in three places, and all three are in the parts the phase advertises most strongly: suppression is reversible (H1), the second authorization layer does not cover receptionists (H2), and the new permission table has a cross-tenant integrity hole (H3). None is a live data leak today. All three should be closed before P4.6B puts this surface in front of users.
