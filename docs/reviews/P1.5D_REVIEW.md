## 2. What is correct (verified)

- **Canonical monetary values are never rewritten.** The migration touches no monetary column (header comment states it; verified — only `phone`, `phone_e164_valid`, `display_currency`, `fx_rates` DDL). `convertForDisplay` ([lib/currency/conversion.ts:9-18](../../lib/currency/conversion.ts#L9-L18)) is pure and returns `canonical`/`canonicalCurrency` untouched; nothing on the branch writes converted amounts anywhere.
- **Conversion is presentational everywhere.** The only conversion call sites are the settings-context `formatCurrency` (display) and the export route (extra CSV columns). Approximate values are marked `≈ …` and rendered *beside* the canonical figure: `≈ US$32.57 (د.ك 10.000)` (unit-tested in `clinic-settings-context.test.tsx`).
- **Stale/expired FX handling is sound.** >48h → flagged `stale` (rendered "· stale rate"); >72h → conversion suppressed, canonical shown, `approximate: false` (unit-tested). Provider failure leaves the last successful `fx_rates` rows untouched: `refreshFxRates` throws before any write; `storeFxSnapshot` is a single upsert; the OER provider fails closed on non-200, non-USD base, missing timestamp/rates, and **incomplete symbol sets** (all-or-nothing snapshot), so a partial provider response can never mix rate vintages.
- **FX snapshot persistence:** one row per currency keyed `currency_code`, `provider_timestamp` + `fetched_at` stored, upserted via the service-role client only ([lib/supabase/admin.ts:25-38](../../lib/supabase/admin.ts#L25-L38)); staleness is computed from the *older* of the two legs' `fetched_at` — conservative and correct.
- **Cron endpoint protection:** `/api/cron/fx-rates` requires `Authorization: Bearer $CRON_SECRET`, fails **closed** when `CRON_SECRET` is unset (401), and the catch path leaks neither provider details nor credentials (unit test asserts the app id never appears in the snapshot output). Vercel cron sends this header automatically; `vercel.json` schedules daily 00:15 UTC. The middleware never gates the path (not protected/operator/auth), so the endpoint is reachable by Vercel cron but unusable without the secret.
- **Display-currency preference:** `updateDisplayCurrency` ([actions/profile.ts:101-109](../../actions/profile.ts#L101-L109)) requires an authenticated mutation user, validates against `isSupportedCurrency`, writes only the caller's own `profiles` row under existing RLS, and `revalidatePath("/", "layout")`; the selector is a labeled `Select` (aria-label "Display currency") with flag + country + code rendering exactly per spec, mounted in the shared header. An unsupported/garbage `display_currency` value (e.g. written directly via REST) degrades safely: no matching rate → conversion suppressed → canonical shown (no `Intl` crash path).
- **Currency-specific minor units:** registry carries `minorUnits` (KWD/BHD/OMR = 3, JPY = 0) and `formatMoney` applies them (unit-tested for KWD 3dp and JPY 0dp).
- **Registries are extensible:** both `lib/currency/registry.ts` and `lib/phone/registry.ts` are single-definition arrays consumed everywhere (selector, provider symbol list, conversion, component dropdown) — adding a currency or country is a one-line change; contract tests assert registry contents. The currency registry already exceeds the plan's initial nine (adds EUR/GBP/JPY), which the plan explicitly permits.
- **E.164 validation/normalization:** `libphonenumber-js` (plan-sanctioned) with per-country validation; round-trip unit tests for KW/EG/SA/AE/TR/US; profile action refines *and transforms* to E.164; `lib/signup.ts` `normalizePhone` now produces E.164 for the invitation/early-access write path; staff/clinic writes normalize at the action layer.
- **Export behavior:** invoices CSV now has explicit `canonical_amount` + `canonical_currency` columns always populated from the raw row values, with `approximate_display_amount`/`display_currency`/`fx_rate_timestamp` populated **only** when a conversion actually applied — canonical and converted are unambiguous, and expired FX yields empty display columns rather than a silent same-currency copy. Column counts verified per row type (15/15/15/15 including header).
- **Migration safety mechanics (partial — see R1/R4):** unparseable legacy values are returned verbatim and flagged `phone_e164_valid = false`, never dropped (integration-tested: `garbage-input` → `garbage-input`); already-E.164 and `00`-prefix values normalize correctly; `normalize_legacy_phone_e164` execute is revoked from public/anon/authenticated and granted to service_role only; SET expressions read OLD row values so `phone` and `phone_e164_valid` are computed consistently.
- **Rollback safety:** all DDL is `if not exists`/`drop policy if exists`; the backfill is idempotent for parseable values (an E.164 value re-passes the first regex branch and is returned unchanged), so re-running the migration is safe. Reverting the app code alone is safe: old code ignores the new nullable columns and `fx_rates`.
- **Client/server boundaries:** `provider.ts`, `open-exchange-rates.ts`, `refresh.ts`, `lib/supabase/admin.ts` are `server-only`; `registry.ts` and `conversion.ts` are isomorphic (client selector + context need them); the selector and phone input are `"use client"`.
- **Consistency of display currency on client money surfaces:** every client component that renders money already consumes `useClinicSettings().formatCurrency` (dashboard revenue widget, analytics charts, doctor dashboard, billing dialog, payment rows, settle dialog, packages section, revenue report, both report components) — the conversion applies there automatically. (Server-rendered exceptions → R5.)
- **Performance:** the protected layout adds two parallel queries (`profiles.display_currency` single row + `fx_rates` ≤ 12 rows) — negligible; conversion is O(rates) per format call with no allocation-heavy work.
- **Legacy formatter API preserved:** `lib/patient-phone.ts` keeps its exported surface (`normalizePatientPhone`, `formatTurkishPhone`, etc.) as wrappers, so pre-existing patient tests pass unmodified.

## 4. Required fixes (blocking)

### P15D-R1 — Backfill function aborts the whole migration for any country outside its 8 `WHEN` branches (empirically reproduced)
- **Where:** [supabase/migrations/20260712150000_p15d_intl_ux_foundations.sql:54-65](../../supabase/migrations/20260712150000_p15d_intl_ux_foundations.sql#L54-L65)
- **What:** the PL/pgSQL `CASE upper(coalesce(default_country,'')) WHEN 'KW' … END CASE` has **no `ELSE`**. In PL/pgSQL (unlike SQL `CASE`), a simple `CASE` statement with no matching branch and no `ELSE` raises `CASE_NOT_FOUND`. Reproduced locally: `select normalize_legacy_phone_e164('5551234567','US')` → `ERROR: case not found`.
- **Why blocking:** `clinics_country_check` allows **any** `^[A-Z]{2}$` (see `20260709091000_clinic_localization_columns.sql:19`), and `US` is a fully supported country in both P1.5D registries. The moment one clinic row carries a country outside {KW,EG,TR,SA,AE,QA,BH,OM} together with a non-E.164 phone, the entire migration transaction aborts — on production, at deploy time. It passed locally only because seeded data is KW/EG-shaped. The function is also granted to `service_role` for future use, where `'US'` input fails immediately.
- **Fix:** add an `else null;` (or `else return value;`) branch so unmatched countries fall through to the conservative `return value` / flagged-invalid path. Add `'US'`-country and unknown-country cases to the integration test.

### P15D-R2 — `null.startsWith` TypeError in the public early-access and signup phone refines (server 500 instead of a field error)
- **Where:** [actions/early-access.ts:27](../../actions/early-access.ts#L27), [actions/auth.ts:311](../../actions/auth.ts#L311)
- **What:** `.refine((value) => normalizePhone(value).startsWith("+"))` — `normalizePhone` ([lib/phone/registry.ts:25-28](../../lib/phone/registry.ts#L25-L28)) returns `string | null`, and returns `null` for any unparseable input (verified: `parsePhoneNumberFromString('abc','KW')` → `undefined`). Zod does **not** catch exceptions thrown inside refinements — `safeParse` rethrows non-ZodError exceptions — so an invalid phone crashes the Server Action.
- **Failure scenario:** anonymous visitor POSTs the public early-access form (or a crafted request) with phone `"abc"` (passes `.min(3).max(50)`) → TypeError → unhandled server error / generic 500, instead of the intended "Enter a valid international phone number" field error. Public, unauthenticated, trivially triggerable.
- **Fix:** `.refine((value) => normalizePhone(value) !== null, …)` or `Boolean(normalizePhone(value)?.startsWith("+"))`; add a unit test submitting a garbage phone through `requestEarlyAccess` and `signUpClinic`.

### P15D-R3 — FormData-submitted phone forms lose the selected country: every non-KW phone is rejected (or crashes per R2) on signup, early-access, and operator invitation forms
- **Where:** [components/shared/international-phone-input.tsx:26](../../components/shared/international-phone-input.tsx#L26) (the `name` prop is placed on the **local-number** `<Input value={local}>`); consumers: [components/auth/clinic-signup-form.tsx:30](../../components/auth/clinic-signup-form.tsx#L30), [components/auth/early-access-form.tsx:26](../../components/auth/early-access-form.tsx#L26), [app/(operator)/operator/invitations/page.tsx:53](../../app/(operator)/operator/invitations/page.tsx#L53)
- **What:** these three forms submit native `FormData` (`useActionState` / server-action `<form>`). The DOM input carries the **national** value (e.g. `0555 123 45 67` for Türkiye) — the E.164 value lives only in React state (`onChange`) which is never submitted, and the selected country is not submitted either. The server then re-parses with the hard-coded default `country = "KW"` (`normalizePhone(value)`), so any legitimately valid non-Kuwaiti number fails validation — today it *crashes* via R2; after fixing R2 it becomes a false "Enter a valid international phone number" rejection. The component's E.164 contract only holds for RHF-controlled consumers (staff/clinic/profile/patient forms), where `field.onChange` receives the normalized value.
- **Failure scenario:** a Saudi clinic owner picks 🇸🇦 +966, types `0501234567` on the public early-access form, submits → server receives `"0501234567"`, parses as KW → invalid → error/crash. The plan's acceptance ("adopt it at **every** phone entry point … stores **E.164**") fails for 8 of 9 countries on exactly the highest-stakes public flows.
- **Fix:** render a hidden input carrying the normalized E.164 value under `name` (keep the visible input name-less), or submit the country code alongside and parse server-side with it. Add form-level tests for a TR/SA submission through `requestEarlyAccess`.

### P15D-R4 — E.164 backfill silently skips profiles without a clinic (platform admins)
- **Where:** [supabase/migrations/20260712150000_p15d_intl_ux_foundations.sql:74-77](../../supabase/migrations/20260712150000_p15d_intl_ux_foundations.sql#L74-L77)
- **What:** the `profiles` backfill is an `UPDATE … FROM public.clinics c WHERE c.id = p.clinic_id`. Profiles with `clinic_id IS NULL` — platform admins, which the P1D design explicitly creates without clinic profiles — are never visited: their phones are neither normalized nor flagged, yet `phone_e164_valid` remains its default `true`, asserting a validity that was never checked. The plan requires backfill "across `clinics.phone`, `profiles.phone`, …" without exception, and the invitation backfill already demonstrates the right pattern (a second pass with a `'KW'` fallback for rows with no clinic).
- **Fix:** add `update public.profiles p set … from … where p.clinic_id is null` using `'KW'` as `default_country`, mirroring the `clinic_invitations` two-pass approach (contingent on R1 so unknown-country inputs can't abort).

### P15D-R5 — Display currency does not apply on three server-rendered money surfaces (acceptance: "applies consistently")
- **Where:** [app/(protected)/patients/[id]/page.tsx:56](../../app/(protected)/patients/[id]/page.tsx#L56), [app/(protected)/settings/services/page.tsx:28](../../app/(protected)/settings/services/page.tsx#L28), [app/(protected)/settings/packages/page.tsx:36](../../app/(protected)/settings/packages/page.tsx#L36)
- **What:** these server components format via `formatClinicCurrency(n, clinicLocale)` directly, bypassing the preference and the `≈`-marking entirely. The patient-detail page renders deposits, settlements, package pricing and outstanding balances — squarely a "billing surface" under the acceptance criterion "currency preference … applies consistently (dashboard, revenue, reports, billing surfaces)". A user who picked USD sees USD everywhere except when they open a patient record, where unmarked KWD figures reappear.
- **Fix:** thread the same `display_currency` + `fx_rates` inputs (already loaded one layout up) through these pages via `convertForDisplay`/`formatMoney`, or refactor them onto a shared server-side formatter. If the team deliberately wants the settings *price-list* pages canonical-only, document that exception in the plan/review; the patient page must convert regardless.

### P15D-R6 — `types/database.ts` is out of sync with the migration (`phone_e164_valid` × 5 tables and `staff_invitations.phone` missing)
- **Where:** [types/database.ts](../../types/database.ts) (hand-edited: `fx_rates`, `profiles.display_currency`, and the RPC signature were added; nothing else)
- **What:** `grep -c "phone_e164_valid" types/database.ts` → **0**, and `staff_invitations` has no `phone` member, although the migration adds both. The columns the migration creates are invisible to the type system, so the P3/P5 consumers this flag exists for (WhatsApp identity matching on normalized numbers, triage of flagged-invalid rows) will not compile against them, and any interim `select("phone_e164_valid")` is untyped.
- **Fix:** regenerate types from the migrated schema (`pnpm db:types` once the remote is migrated, or `supabase gen types --local` for now) and diff-review; do not hand-maintain partial rows.

### P15D-P4 — Legacy registry countries (GB/DE/FR) were dropped; existing E.164 values outside the 9 countries degrade in the editor

### P15D-P7 — Signup form's clinic-country select and the phone input's country are independent

### 8.2 New finding (Cycle 2)
