## 2. Deferred-loading verification

### Closed launcher

**Pass.** `resolveAssistantLauncher()` performs the code-owned registry/type/default/role checks, Assistant and source-page visibility lookups, subscription and required-feature checks, usage availability, and any declared per-user permission. It returns only the strict P4.8A context and available access result.

The page-time path does not call `loadAssistantConversationForSurface()` or `resolveAssistantCapabilities()`. `AssistantLauncherEntry` serializes only the strict context, presentation-only label, and role. It does not accept conversation, message-history, or capability props.

The launcher component has only erased type imports for message and capability shapes. Its executable `AssistantChat` dependency is a native dynamic import inside `loadSession()`, and `loadSession()` is invoked only when `onOpenChange` receives `true`. Before that event there is no `/api/agent/launcher-session` request and no chat render.

The direct component test asserts that a closed Sheet performs neither the session fetch nor chat render. Resolver tests independently assert that closed patient and dashboard launchers perform neither conversation nor capability resolution.

### Production bundle

**Pass.** The fresh production client-reference manifests for dashboard, appointments, and patient profile include `assistant-launcher.tsx` but do not include `assistant-chat.tsx` in their initial page entries. The compiled launcher invokes an asynchronous module loader from the first-open handler. Its three deferred chunks total 496,040 bytes raw and approximately 120 KB gzip, consistent with the implementation report's bundle evidence.

### First-open session hydration

**Pass.** On the first Sheet open, the launcher starts the chat dynamic import and authenticated session fetch in parallel. Repeated open events are deduplicated while a load is in flight, a successful session remains mounted, and a failed load exposes a localized retry path.

The successful session response is marked `Cache-Control: private, no-store` and returns only the owner-scoped conversation ID/history, truncation flag, current remaining usage, and authorized presentation capabilities.

## 3. Re-authentication and repeated authorization

**Pass.** `POST /api/agent/launcher-session` is a separate server boundary and begins with `authorizeStaffAssistant()`. That repeats server-derived session identity, staff-role eligibility, Assistant page visibility, active subscription, and the Assistant feature entitlement.

After independently parsing a strict P4.8A context, `resolveAssistantLauncherSession()` calls `resolveAssistantLauncher()` again. This repeats:

- registered/default-enabled P4.8A area validation;
- role eligibility;
- Assistant page visibility;
- source-page visibility;
- subscription state and every required feature;
- usage availability/cap state;
- any declared per-user permission.

For patient context, `assertDoctorPatientContextAccess()` runs before `loadAssistantConversationForSurface()`. It requires a doctor, reselects an undeleted patient through the authenticated Supabase client, scopes the lookup by the authenticated clinic, and requires assigned-doctor or same-department access. A denial prevents the conversation and `agent_messages` reads.

The subsequent conversation query remains scoped by clinic, owner, persona, active status, and exact patient/null-patient context. History is also filtered by clinic and conversation and limited to the most recent 40 messages.

## 4. Platform and security regression verification

| Control | Result | Evidence |
|---|---|---|
| Billing and provider accounting | Pass | The chat route still derives task/persona from authenticated role, entitlement, and message text; calls `prepareAiExecution()` before model work; and retains success, recovered-tool-error, abort, and failure reconciliation. Page context cannot choose a task, model, provider route, credential mode, budget, or usage metric. Opening a launcher does not reserve or bill a turn. |
| Usage limits | Pass | Page-time and first-open launcher gates call the existing usage check and fail closed on cap or lookup failure. The chat route independently performs atomic execution preparation and cap enforcement before model work. |
| Rate limiting | Pass | The chat route still rate-limits the authenticated clinic before execution reservation, conversation work, or model work and preserves the 429/`Retry-After` behavior. No context field participates in the rate-limit key. |
| Auditing | Pass | No new data tool or audit bypass was introduced. Actual tool calls still pass through the existing registry wrapper and per-tool audit path; page context itself performs no tool/data operation. |
| Tenant isolation and RLS | Pass | No schema, migration, service-role, or RLS-policy change exists in P4.8A. Patient and conversation reads use the authenticated client and explicit clinic/owner scope. The live two-clinic suite confirms same-tenant patient context succeeds and cross-tenant patient context is denied. |
| Tool-mount authorization | Pass | Non-patient context is omitted from `buildStaffTools()`. Only a server-authorized patient context can provide a doctor patient default. Role, task class, feature, per-user permission, and tool-execute checks remain authoritative and deny by default. |
