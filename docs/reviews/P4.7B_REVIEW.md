## Final Verdict: **APPROVED — ready for Phase-level review**

P4.7B is a disciplined, correctly-scoped, low-risk sub-phase and its central invariant holds structurally, not by convention. The roadmap's headline acceptance — *"every user's capability panel matches their true server-side tool mount"* and *"derived dynamically from the same registry resolution that mounts the model's tools (one source of truth — no hand-maintained list to drift)"* — is enforced by construction: there is exactly **one** function that answers "what can this user do?" (`resolveAssistantCapabilities`), it derives its answer from `resolveToolMount` (the same call that builds the model's tool array), and both the panel's `items` and the `list_my_capabilities` payload are the *mapped mount* rather than a second list. A capability the user does not have cannot appear in either, and one they do have cannot be hidden by a stale copy. The parity test asserts this on real resolution, not on mocks.

Independently verified during this review:
- **One resolution, three consumers.** `capabilityItems()` maps the resolved `definitions` (their `capabilityDescription[locale]` + `presentationFor().group`) — the same `definitions` the mount hands the model. No second capability list exists anywhere. The parity test (`payload.capabilities.map(name).sort() === mount.definitions.map(name).sort()`, and `capabilities.items === payload`) exercises the real `@/lib/ai/tools` + `@/lib/ai/capabilities`.
- **No hidden capability leakage / no escalation.** `list_my_capabilities` re-asserts `assertStaffToolAccess` on every invocation; a mid-session hidden page yields the structured `permission_denied: page_hidden` (via `harden()`), not a leaked list. The panel is server-rendered from `resolveStaffAssistantPage` (page-visibility + access gated) and holds no fallback list. Deny-by-default: registry entry is `roles: ALL_STAFF`, `requiredFeatures: [AI_ASSISTANT_FEATURE]` — absent that feature the tool does not mount (test confirms).
- **No PHI / no clinic data.** The tool reads no tenant table; its answer is registry metadata (static product copy) resolved against the caller's own entitlements/permissions. It audits via `logAgentTool` with `tableName: null` and records only `capability_count` — a number, preserved verbatim by `toolAuditSummary`. Verified there is no database read on the path.
- **Permission awareness through the shared resolution.** Entitled+granted admin gets `financial` group; manager without the grant does not but keeps `operational`; receptionist never sees financial/clinic-analytics; doctor sees only `clinical`+`guidance`; a clinic without `ai.staff_analytics` loses analytics/financial but keeps the base assistant. All five surface through the single mount, not a re-derived matrix.
- **Grouping is clean and future-proof.** `group` reuses the P4.6B `AssistantToolGroup`; order is `clinical → operational → financial → guidance`, stable across requests (asserted). The pre-existing `p46b-tool-presentation` test — *"covers every registered tool, so none falls back to the generic label"* — means a future tool added to the registry without a presentation entry is a **test failure**, so a new financial tool cannot silently render as `clinical` in the panel. Adding a tool needs no panel work.
- **Localization fully synchronized.** All ten new keys (`capabilitiesTitle/Description/Close/Empty/Button`, `capabilityGroup{Clinical,Operational,Financial,Guidance}`, `toolCapabilities`) are present in **both** `en.json` and `ar.json`; the Arabic-description test asserts real Arabic text under an `ar` locale; i18n parity gate passes (report: 2,745 leaf messages, no missing/unused).
- **Empty state honest.** `capabilitiesEmpty` renders when `items` is empty; the header toggle is hidden when there is nothing to show (`showCapabilityToggle = (capabilities?.items.length ?? 0) > 0`) — no invented generic list.

Re-run during this review: the five affected suites — `p47b-capability-panel`, `p47a-help-tools`, `p4a-doctor-tools`, `p46a-staff-analytics-tools`, `p46b-assistant-analytics-ui` — **111/111 passing**. `tsc --noEmit` clean; ESLint clean on the three primary changed files.

**No High, Medium, or Low findings.** Three Info notes follow; none blocks merge, none weakens authorization, and none requires a code change.

## 5. Info / Notes (non-blocking, no change required)

**I1 — `GROUP_ORDER` is duplicated in the client component, redundantly.**
`components/assistant/capability-panel.tsx:50-55` re-declares `GROUP_ORDER` to order the render buckets, while `lib/ai/capabilities.ts:88-93` already sorts `items` into exactly that order server-side. Because `items` arrive pre-sorted, a `Map` built by insertion would already iterate in the right order, so the client array is strictly defensive. This is not drift-prone in a harmful direction — both lists are the same fixed four-group ordering and a mismatch could only *reorder* buckets, never show or hide a capability — and the component comment explicitly flags that it "mirrors the server-side `GROUP_ORDER`." Acceptable as documented defensive code; noted only so a future reader knows the client copy carries no independent authority.

**I2 — Working-tree / branch hygiene (process, not code).**
The review was performed against the uncommitted working tree, which currently sits on `feat/p47a-system-knowledge` and contains **both** P4.7A and P4.7B changes together (e.g. `lib/ai/prompts/staff.ts`'s `buildProductKnowledgePrompt` append and `lib/ai/help/` are P4.7A). The report names the branch `feat/p47b-capability-panel`. This is a branch/PR-separation concern for the human merge process, not an implementation defect — the P4.7B code itself is correct and self-contained. Recommend the P4.7B commits land on their own branch/PR as the roadmap's merge order (P4.7A → P4.7B) intends.

**I3 — Union-mount semantics are correct but worth an explicit acknowledgement.**
`list_my_capabilities` returns the cross-task-class union, so during a cheap `staff_help`-routed turn the model can still enumerate, e.g., the operational/financial capabilities even though that specific turn mounted only the three data-free tools. This is intended (the next user message re-routes and re-mounts, and every tool re-asserts authorization in `execute()`), and it is the honest answer to "what can I ask?". No action needed; recorded so a later reviewer does not mistake the union for a leak of an unmounted capability. The `capability_only` marker correctly stops the model from *inventing* abilities beyond this authoritative set.

## 6. Security & Authorization Review

- **No authorization surface changed.** The panel and tool are display/answer data derived from the existing mount. Every tool still re-asserts role, entitlement, permission, page visibility, and RLS inside `execute()`; the chat route denies independently. The panel cannot grant, and a forged/stale panel returns only descriptions, never data.
- **`list_my_capabilities` is genuinely data-free.** Its only reads are `getEntitlements` + `hasAiUserPermission` (authorization state, not PHI) via `resolveToolMount`, and static registry copy. `tableName: null` is accurate. `capability_count` is the only audited datum and carries no PII.
- **Mid-session revocation is handled.** `assertStaffToolAccess` is re-asserted per call; `harden()` converts the thrown `AiToolAuthorizationError` into a structured `page_hidden` denial rather than letting a capability list escape — asserted by test.
- **Deny-by-default preserved.** Absent `ai_assistant`, the tool does not mount; a role absent from `ALL_STAFF` (none, here, but structurally) would not see it. The `staff_help` containment property (help/capability tools only, no clinic-data tool) is intact and re-asserted by the updated `p47a-help-tools` test (now exactly the three data-free tools).
- **No prompt-injection surface added.** The tool takes an empty input schema (`z.object({}).strict()`); its output is static product copy that passes through the same `harden()` sanitization as every other tool.

## 7. Maintainability, Performance, UX

- **Maintainability:** single source of truth — a new registry entry with a `capabilityDescription` + presentation group appears in the panel and the tool payload automatically; no hand-maintained list to update. The `p46b-tool-presentation` completeness test guards the one metadata coupling (registry ↔ presentation) at build time.
- **Performance:** panel resolution shares the mount already computed for the surface; `resolveStaffAssistantPage` runs conversation load + capability resolution in `Promise.all`. The tool's lazy `await import("@/lib/ai/capabilities")` is a documented, correct cycle-break (registry → tools index → capabilities → registry) and executes once at call time after module init — verified this is why a static import was avoided.
- **UX consistency:** panel financial styling (`amber-500/…`, `text-amber-900 dark:text-amber-200`) matches `ToolActivity`'s financial treatment; guidance/clinical/operational icons and group labels are consistent with the chat's existing tool-activity vocabulary; RTL-safe logical properties throughout; `aria-expanded`/`aria-controls`/`useId` wiring and a labelled close button are correct. Theme-aware in both light/dark.
