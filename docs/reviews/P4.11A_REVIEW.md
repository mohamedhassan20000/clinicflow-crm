## Verification against the required checklist

### ✅ Workflow plans are fully typed and server-validated
`workflowPlanSchema`/`workflowStepSchema` are `.strict()` Zod objects with a literal version, id/tool regexes, and `min(1).max(WORKFLOW_MAX_STEPS)`. `validateWorkflowPlan` ([lib/ai/workflows/plan.ts:192](../../lib/ai/workflows/plan.ts#L192)) rejects oversized JSON, malformed shapes, duplicate ids, forward/self/unknown dependencies, references not declared as dependencies, unknown/unmounted/non-executable/non-read tools, cost-cap overflow, and literal inputs failing the destination tool's own schema — all *before* a run row is created. Referenced inputs are re-validated against the tool schema after resolution ([plan.ts:309](../../lib/ai/workflows/plan.ts#L309), [executor.ts:216](../../lib/ai/workflows/executor.ts#L216)).

### ✅ Execution limited to the existing typed tool registry
Steps resolve only from `AI_TOOL_REGISTRY` via the caller's mount; `unknown_or_unmounted_tool` denies anything absent from both `definitions` and `tools`. No SQL, no free-form data path. Verified by the "denies an unknown or unmounted tool" test.

### ✅ Dry-run performs no tool execution
`mode === "dry_run"` builds a content-free preview and a SHA-256 hash and returns without invoking any tool ([executor.ts:127](../../lib/ai/workflows/executor.ts#L127)). The engine test asserts `execute` is never called and sensitive values never appear in the persisted summary.

### ✅ Every step preserves authorization, RLS, tenant isolation, PHI protection, auditing, billing, usage, and conversational context
Nested step tools are built through `harden()` ([lib/ai/tools/index.ts:154](../../lib/ai/tools/index.ts#L154)), so each invocation retains the existing per-tool role/subscription/visibility/feature/permission re-checks, authenticated RLS reads, `logAgentTool` auditing (success/denial/clarification/error), untrusted-text neutralization, and per-tool PHI minimization. The executor calls only `tool.execute` and never touches cores directly. Billing/usage are reserved once for the `staff_workflow` turn via `prepareAiExecution`; nested reads add no model steps. Active context is passed through unchanged as advisory identity, re-authorized per destination tool.

### ✅ Hidden nested tool mounts cannot be bypassed
Triple-layered: (1) only `execute_read_only_workflow` is model-visible in `staff_workflow` (mount test asserts `Object.keys(mount.tools) === ["execute_read_only_workflow"]`); (2) the read-tool union is held in a server closure whose build context sets `workflowStepMount: null`, so a nested tool cannot recurse into orchestration; (3) `workflowStepCandidates` requires `workflow.kind === "read"` and `validateWorkflowPlan` rejects `orchestrator`/non-read tools as step vocabulary (`non_read_only_tool`), covered by the "rejects the orchestrator … as step vocabulary" test.

### ✅ Step and cost limits cannot be bypassed
`WORKFLOW_MAX_STEPS = 6` enforced in schema and DB (`step_count between 1 and 6`); `WORKFLOW_MAX_COST_UNITS = 12` enforced in the validator and DB (`cost_units between 1 and 12`). The model tool-loop is independently capped at `maxSteps: 3`. Cost-cap denial is tested.

### ✅ `ai.workflows` entitlement correctly enforced
Enforced three times: at mount (`requiredFeatures` includes `AI_WORKFLOWS_FEATURE`), in `prepareAiExecution` for the `staff_workflow` task before provider reservation ([execution.ts:309](../../lib/ai/platform/execution.ts#L309)), and in `assertWorkflowAccess` before validation/ledger writes ([authorization.ts:162](../../lib/ai/authorization.ts#L162)). The engine test confirms the entitlement check precedes any ledger write; the migration seeds it `true` only for `pro_ai`.

### ✅ `ai_workflow_runs` contains no PHI or prompt/completion content
`summarizeWorkflowPlan` persists parameter *names* and structural *shapes* (`typeof`/`array:N`/`object:N`/`step_reference`) plus dependency/reference step ids — never values. Tool outputs live only on `WorkflowStepResult.output` returned to the model turn; the persisted `WorkflowStepLedgerState[]` excludes outputs entirely. `error_code` carries only bounded enum/reason codes (sliced to 100 chars, DB-constrained). Migration comments and the DB `CHECK` constraints reinforce this. The dry-run test asserts the patient name and id are absent from the summary; the RLS integration test passes (5/5).

### ✅ Owner-read / server-write-only RLS & tenant isolation
Select policy requires `clinic_id = auth_clinic_id() AND user_id = auth.uid()`; `authenticated` gets `select` only; writes are `service_role`-only through `createClinicScopedAdminClient`, which injects `clinic_id` on insert and scopes update by `clinic_id` ([admin.ts:1438](../../lib/supabase/admin.ts#L1438)) — the ledger update additionally matches `id` and `user_id`. Composite FKs `(user_id, clinic_id)` / `(confirmed_by, clinic_id)` prevent cross-clinic actors. Live RLS test confirms owner read, same-clinic colleague denial, cross-clinic denial, authenticated write denial, and service update.

### ✅ No action steps / UI / mutations / confirmation / unattended flows
Registry declares only `read` and one `orchestrator`; no write/action kinds exist. `grep` of `lib/ai/workflows/` finds no confirm/dispatch/booking/messaging mutation (only the orchestrator description that *forbids* them). Migration adds no RPC, action table, dispatch, appointment/report write, or confirmation function. `confirmed_by`/`confirmed_at` are inert nullable scaffolding; no code writes them. Presentation is label-only on the existing generic activity surface.

### ✅ P4.11B has not started
Roadmap and report both mark P4.11B unstarted; no confirmation API, resume path, message/booking/report mutation, workflow UI, or suggested-workflow prompt exists.

## Non-blocking observations (no action required for P4.11A)

1. **Redundant `startedAt` on running-step updates** — [executor.ts:205](../../lib/ai/workflows/executor.ts#L205) re-sends the run-start timestamp on every running update; `started_at` is already set at create. Harmless idempotent write.
2. **Clarification-only run reports `state: "failed"`** — a run whose only non-success step is `needs_clarification` with zero successes classifies as `failed` rather than a distinct clarification state ([executor.ts:44](../../lib/ai/workflows/executor.ts#L44)). Honest and safe; consider a softer terminal state in P4.11B when clarification UX lands.
3. **Multiple orchestrator calls per turn** each create their own run row (within the 3-step model budget and fully authorized). Acceptable; noted for future dedupe if desired.

These are quality notes only and do not affect correctness, security, or the phase gate.
