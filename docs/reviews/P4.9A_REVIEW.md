## Executive summary

P4.9A is correctly bounded to the customization core. The migration, entitlement vocabulary, server-only placement resolver, P4.8 resolver integration, generated types, scoped-admin classification, tests, and roadmap/report changes are present. No P4.9B route, settings UI, localized settings copy, upgrade-gate UI, mutation action, or client-side placement state was added. P4.10/P4.11 functionality is also absent.

The implementation preserves the P4.8 role/feature/page-visibility gates and keeps placement out of chat authorization, tool registration, PHI access, billing, usage accounting, and rate limiting. The entitlement → code default → role setting → user override order is deterministic, respects explicit `false`, and cannot enable a launcher for a role excluded by the P4.8 registry. Tenant isolation and direct authenticated-write RLS passed live two-clinic validation.

Two medium findings remain. First, service-role mutations—explicitly anticipated by the migration and enabled through the clinic-scoped admin wrapper—produce audit rows with a null actor. Second, the roadmap-required launcher-visibility-versus-authorization parity acceptance is represented by source-text assertions rather than behavioral tests. There are no high- or low-severity findings.

## Findings

### P49A-M1 — Service-role placement mutations lose the actor identity

- **Severity:** Medium
- **File and line reference:** `supabase/migrations/20260722120000_p49a_assistant_customization.sql:65`, `supabase/migrations/20260722120000_p49a_assistant_customization.sql:88`, `supabase/migrations/20260722120000_p49a_assistant_customization.sql:137`, `lib/supabase/admin.ts:1245`, `lib/supabase/admin.ts:1358`, `tests/unit/integration/p49a-assistant-customization-rls.test.ts:255`
- **What is wrong:** The placement audit trigger always writes `actor_id = auth.uid()`. That is correct for direct authenticated PostgREST writes, but `createClinicScopedAdminClient` is a service-role client and therefore has no authenticated clinic-user UID. A live, self-cleaning probe through that client produced `{ actor_id: null, action: "assistant_launcher_placement:insert" }`. The migration comment explicitly anticipates service-role mutations after an application-level primary-admin check, and both placement tables are classified for the scoped service client. The live audit test validates only authenticated inserts, so this path is not detected. Updates and deletes by the primary admin are also not behaviorally checked for their old/new audit payloads.
- **Why it matters:** The audit event proves that a row changed but cannot identify the administrator who changed it. That weakens the stated “primary-admin-only audited writes” guarantee and makes future P4.9B changes non-attributable if they follow the repository’s existing service-role settings-action pattern. For user overrides there is no `updated_by` column from which the missing actor could even be reconstructed.
- **Exact expected correction:** Keep the scoped service-role client read-only for placement resolution. Define the supported placement mutation boundary to run with the authenticated user’s Supabase session so the existing RLS policies and `auth.uid()` audit attribution execute together; role-setting writes must set `updated_by` to that same authenticated UID. If a service-role maintenance path is genuinely required, it must be a separate database RPC that requires an explicit actor, verifies inside the database that the actor is the current primary admin for the clinic, and writes that verified actor to the audit row. Raw service-role table mutations must not be the P4.9B product path. Update the implementation report’s service-role/audit wording accordingly.
- **Required regression tests:**
  - Exercise the actual supported server mutation boundary, not a direct table fixture, for primary and secondary admins.
  - Insert, update, and delete a role setting as the primary admin and assert non-null `actor_id`, exact action, composite key in old/new data, and the changed value.
  - Insert, update, and delete a user override with the same assertions.
  - Assert secondary-admin and cross-clinic attempts produce neither a mutation nor an audit row.
  - Add a service-role-path test proving it is either rejected as an unsupported product mutation or records a database-verified, non-null primary-admin actor.

### P49A-M2 — Authorization-isolation acceptance is tested by source inspection, not behavior

- **Severity:** Medium
- **File and line reference:** `docs/AI_AGENT_PLAN.md:1189`, `docs/AI_AGENT_PLAN.md:1191`, `tests/unit/ai/p49a-launcher-placement.test.ts:149`, `tests/unit/ai/p49a-launcher-placement.test.ts:156`, `tests/unit/ai/p48a-launchers.test.ts:185`
- **What is wrong:** The P4.9A test described as proving tool-mounting, authorization, and billing isolation only reads three source files and asserts that specific table/module strings are absent. The launcher test proves that a false placement returns `null` before surface/session hydration, but it does not invoke the global Assistant/chat authorization boundary or compare the authorized tool registry with placement enabled versus disabled. Consequently, the exact roadmap acceptance—disabled launcher does not block direct Assistant/API use, enabled launcher grants no unauthorized tool, and customization cannot mount/unmount tools—is not tested behaviorally.
- **Why it matters:** String-absence tests can remain green if placement begins influencing authorization indirectly, moves behind another module name, or changes billing through a helper. These are precisely the security boundaries the roadmap requires to remain independent. The current implementation is structurally safe, but the regression suite would not reliably detect future architectural drift.
- **Exact expected correction:** Retain lightweight architecture assertions if useful, but add behavioral parity tests around the real authorization and tool-resolution boundaries. Resolve the same authenticated user’s tool set and direct chat/API authorization with placement defaulted, role-disabled, user-disabled, and user-enabled; every authorization/tool result must remain identical. Placement may change only the launcher resolver result.
- **Required regression tests:**
  - With a permitted user and a disabled launcher, call the direct Assistant/chat authorization path and prove the same permitted tool remains mounted/usable while launcher resolution is null.
  - With an unauthorized role or missing financial permission and an enabled stored override, prove the launcher stays null and the protected tool stays unmounted/denied.
  - Compare the complete authorized tool-name set before and after role/user placement changes and assert exact parity.
  - Prove placement resolution and launcher-session hydration do not reserve AI budget or increment usage, while an actual chat send still uses the existing accounting boundary.
  - Exercise the launcher-session API with placement disabled and assert fail-closed hydration without changing the independently tested chat API result.
