P4.11 delivers the bounded, server-authoritative, plan → preview → confirm → execute workflow engine the roadmap specifies. ## Verification against the required checklist

### ✅ Typed, versioned, strict plan validation
`workflowPlanSchema`/`workflowStepSchema` are `.strict()` Zod objects with `version: z.literal(1)`, id/tool regexes, and `min(1).max(6)`. `validateWorkflowPlan` ([lib/ai/workflows/plan.ts:198](../../lib/ai/workflows/plan.ts#L198)) rejects oversized JSON (24 KB cap), malformed shapes, duplicate ids, self/forward/unknown dependencies, references not declared in `depends_on`, unknown/unmounted/non-executable tools, orchestrator-as-step, action-output dependencies, cost-cap overflow, and literal inputs that fail the destination tool's own schema — **before any run row is created**. Referenced inputs are re-validated against the tool schema after resolution ([plan.ts:363](../../lib/ai/workflows/plan.ts#L363), [executor.ts:226](../../lib/ai/workflows/executor.ts#L226)).

### ✅ Registry-only orchestration; no arbitrary tool execution
Steps resolve only from `AI_TOOL_REGISTRY` through the caller's resolved mount ([registry.ts:104](../../lib/ai/tools/registry.ts#L104)); `unknown_or_unmounted_tool` denies anything absent from both `definitions` and `tools`. The executor calls only `tool.execute` ([executor.ts:133](../../lib/ai/workflows/executor.ts#L133)) — no SQL, no free-form data path, no core called directly.

### ✅ Hidden nested mounts cannot be bypassed
Triple-layered and verified by the mount test: (1) only `execute_read_only_workflow` is model-visible in `staff_workflow` (the candidate filter forces `workflow.kind === "orchestrator"`, [tools/index.ts:96](../../lib/ai/tools/index.ts#L96)); (2) the read/action step union is built in a server closure whose build context sets `workflowStepMount: null` ([tools/index.ts:161](../../lib/ai/tools/index.ts#L161)), so a nested tool cannot recurse into orchestration; (3) orchestrator/action tools carry `taskClasses = ["staff_workflow"]`, so they never appear in ordinary/capability mounts.

### ✅ Read-only vs action classification is correct
Registry `workflow.kind` is `read` (all P4 data/report tools), `action` (only `send_appointment_reminders`, `send_invoice_reminders`, `create_pending_booking`), or `orchestrator` (only the entry tool). Action tools are additionally gated `taskClasses.includes("staff_workflow")` in the hidden mount ([registry.ts:111](../../lib/ai/tools/registry.ts#L111)).

### ✅ Dry-run invokes no action
A pure read plan in `dry_run` builds a content-free preview + SHA-256 hash and returns without invoking any tool ([executor.ts:324](../../lib/ai/workflows/executor.ts#L324)). Action tools in `preview` mode return `awaiting_confirmation` items and never reach `dispatchPatientMessage`/`createPendingWorkflowBooking` ([send-appointment-reminders.ts:173](../../lib/ai/workflows/actions/send-appointment-reminders.ts#L173), [create-pending-booking.ts:38](../../lib/ai/workflows/actions/create-pending-booking.ts#L38)).

### ✅ Every action forced to preview; confirmation recomputes & validates the preview (first confirmation)
`executeReadOnlyWorkflow` overrides any model-requested `execute` to `dry_run` whenever the plan `hasActions` ([executor.ts:314](../../lib/ai/workflows/executor.ts#L314)). The server-encoded invocation mode lives only in the `toolCallId` and cannot be set by the model/client ([executor.ts:86](../../lib/ai/workflows/executor.ts#L86)). On first confirmation ([executor.ts:484](../../lib/ai/workflows/executor.ts#L484)) the server re-runs the full preview under current RLS/authorization, recomputes `workflowActionSnapshotHash(plan, results)` — which covers the exact ephemeral plan values **and** the preview outputs — and rejects with `preview_stale` if it differs from the stored hash. A client that swaps a same-shaped value between preview and first-confirm is caught here because the recomputed hash diverges.

### ✅ Stale data / permissions / recipients / balances / channels / availability invalidate confirmation (first confirmation)
The snapshot hash includes read-step outputs and action-preview outputs (recipients, `outstanding_amount`, eligible `channels`, booking availability result). Any drift changes the hash → `preview_stale`. Each action additionally re-reads and re-authorizes at confirm time (`buildDrafts` re-reads pending/confirmed appointments; invoice reminders re-check `status='completed'` + `outstanding_amount>0`; booking re-runs `computeAvailableSlots`).

### ✅ Atomic, same-owner, non-replayable, tenant-safe confirmation claim
`claimConfirmation` is a single conditional `UPDATE … WHERE id=? AND user_id=? AND state='previewed' AND dry_run_snapshot_hash=? AND confirmed_at IS NULL` ([ledger.ts:104](../../lib/ai/workflows/ledger.ts#L104)) via `createClinicScopedAdminClient` (clinic injected). Two concurrent confirmations race on this atomic update; only one matches. After the claim the row is `state='running', confirmed_at=…`, so a replay fails the `WHERE` and a completed run (`state='succeeded'`) is excluded from the resume-eligible states — no replay. Composite FKs `(user_id, clinic_id)` / `(confirmed_by, clinic_id)` prevent cross-clinic actors; the live RLS test asserts forgery + cross-tenant denial.

### ✅ Resume cannot duplicate completed steps, appointments, or dispatches
Completed **action** steps are terminal across resume ([executor.ts:168](../../lib/ai/workflows/executor.ts#L168)). Retried actions pass through their idempotent cores: messaging uses an atomic per-channel `claimMessageDispatch` on `dedupe_key` (`appointment_reminder:<id>`, `invoice_followup:<id>:step0`) so already-sent channels return `duplicate`; booking uses the partial unique index `(clinic_id, ai_workflow_run_id, ai_workflow_step_id)` plus a pre-insert existence check and post-race re-select. Duplication is genuinely prevented.

### ✅ Partial failure & independent-step continuation
Dependents of a failed/denied step become `skipped/dependency_failed`; independent later steps continue ([executor.ts:179](../../lib/ai/workflows/executor.ts#L179)). `terminalState` honestly classifies `succeeded` / `partially_failed` (incl. `action_partial_failure`) / `needs_clarification` / `failed` ([executor.ts:41](../../lib/ai/workflows/executor.ts#L41)). The P4.11A non-blocking observation about clarification-only runs is resolved by the new `needs_clarification` terminal state.

### ✅ Step / cost / model-loop / plan-size / dependency / reference / schema limits
`WORKFLOW_MAX_STEPS = 6` (schema + DB `step_count between 1 and 6`), `WORKFLOW_MAX_COST_UNITS = 12` (validator + DB `cost_units between 1 and 12`), plan byte cap 24 KB, reference depth/array caps (12 / 100), prototype-pollution key blocklist on both collection and resolution paths ([plan.ts:20](../../lib/ai/workflows/plan.ts#L20), [plan.ts:332](../../lib/ai/workflows/plan.ts#L332)). The model tool-loop is independently capped (`maxSteps`). All bypass attempts are covered by tests.

### ✅ Per-step preservation of the full authorization/RLS/PHI/audit/billing spine
Every nested step is built through `harden()` ([tools/index.ts:218](../../lib/ai/tools/index.ts#L218)), preserving per-tool role/subscription/visibility/feature/permission re-checks, authenticated RLS reads, `logAgentTool` auditing, untrusted-text neutralization, and PHI minimization. Action tools re-assert their own gates: `assertWorkflowActionAccess` (role + `ai.workflows` + page visibility), `assertFinancialInsightsAccess` (financial feature + per-user grant) for invoice reminders. Billing/usage is reserved once for the `staff_workflow` turn via `prepareAiExecution`, which re-checks `ai.workflows` before provider reservation ([execution.ts:309](../../lib/ai/platform/execution.ts#L309)). P4.10 context stays advisory and re-authorized per destination tool.

### ✅ `ai.workflows` restricted; `ai_workflow_runs` content-free
Entitlement seeded `true` only for `pro_ai`; enforced at mount, in `prepareAiExecution`, and in `assertWorkflowAccess` before any validation/ledger write. The ledger persists only version, step ids/tool names, dependency ids, parameter *names + structural shapes* (`typeof`/`array:N`/`object:N`/`step_reference`), reference source step ids, counts, timings, bounded error codes, and the one-way snapshot hash. No values, recipients, balances, outputs, prompts, or completions. DB comments and `CHECK` constraints reinforce this; the dry-run test asserts patient name/id absence; live RLS confirms owner-read / service-write-only.

### ✅ Messaging via idempotent core; booking via availability core; pending-only; no patient notification
Reminders call `dispatchPatientMessage` (existing templates/settings/entitlement/usage/audit/rate-limit boundary). Booking calls `computeAvailableSlots` + inserts `status: "pending"` through the **RLS user client** (`createClient()`, not admin) with `patient_notification: "not_sent"` and **no dispatch import**. Confirmed: no patient notification is emitted from pending booking creation.

### ✅ No destructive / unattended / scheduled / auto-send / billing-mutation / P5 behavior
The action registry has no delete, status override, invoice/billing mutation, free-form SQL, arbitrary HTTP/tool, scheduler, cron, or patient-side entry. Booking is pending-only; sends occur only inside the exact run the authenticated user just confirmed. The system prompt explicitly forbids claiming a preview as done, confirming for the user, or requesting unattended/scheduled/destructive execution ([prompts/staff.ts:53](../../lib/ai/prompts/staff.ts#L53)). No P5 hold/expiry/patient-identity schema exists.

### ✅ UX / i18n / RTL / accessibility
`WorkflowConfirmation` ([assistant-chat.tsx:503](../../components/assistant/assistant-chat.tsx#L503)) renders a dedicated preview/confirmation card with `aria-labelledby`, `role="status"`/`role="alert"` live regions, a `min-h-11` (44px) confirmation control, `<bdi>` around bidirectional date content, logical CSS properties, and distinct idle/working/success/error/stale/resume states. All 24 new copy keys and the three suggested-workflow prompts exist in en + ar.

### ✅ P4.11A review observations resolved
(1) Redundant `startedAt` on running-step updates removed (running updates now send only `{ state, stepStates }`). (2) `needs_clarification` is now a first-class terminal state. (3) Multiple orchestrator runs per turn remains an accepted, bounded behavior.

### ✅ Roadmap & reports match the shipped implementation
The §8 roadmap block, P4.11A report, and P4.11B report accurately describe the three action tools, the closed registry, the confirmation/resume model, the migrations, and the explicit later-phase boundary. Spot-checks (task class, cost metadata, dispatch keys, migration constraints, file lists) all match the code.

## Findings

### Medium

**M1 — Resume after partial failure does not re-bind execution to the confirmed preview snapshot.**
`confirmOrResumeWorkflow` performs the snapshot recomputation + `preview_stale` check **only on the first confirmation** (`!stored.confirmedAt`, [executor.ts:484-503](../../lib/ai/workflows/executor.ts#L484-L503)). On the resume branch (`confirmedAt` set, [executor.ts:514-521](../../lib/ai/workflows/executor.ts#L514-L521)) it validates the incoming plan only for **shape/summary equality** (`workflowPreviewHash(stored.planSummary)`, which is content-free) and then executes directly against fresh reads. Two consequences follow, because outputs are never persisted and read steps are re-executed on resume:

- *Honest drift:* if an action input references a read step (the pattern the orchestrator prompt encourages), and the read set grows between confirmation and resume (e.g., a new tomorrow-unconfirmed appointment appears), the retried action dispatches to recipients that were never previewed or confirmed.
- *Client-supplied values on resume:* `confirmAssistantWorkflow` is a server action reachable independently of the honest UI. A caller can submit a plan with the **same shape but different literal values** (e.g., a different `appointment_id`/`patient_id` on a literal action input) for a run that is `partially_failed`/`failed`; the resume executes it because the summary hash matches and the snapshot hash is not re-checked.

**Failure scenario:** User previews & confirms "remind patients A, B, C"; the send step fails entirely (`status: failed`, run `partially_failed`). The browser then calls `confirmAssistantWorkflow(runId, plan')` where `plan'` has the same shape but targets patient D (or the referenced list now resolves to A–D). Resume re-executes the action against the new target and dispatches a reminder to D, who was never in any preview or confirmation.

**Why not Critical/High:** every retried action still runs the full per-tool authorization + RLS re-read within the confirming user's own clinic (no cross-tenant access, no PHI leak, no privilege escalation — the user could already send/book for D directly); resume requires a prior explicit confirmation of the *same run* by the *same owner*; core idempotency prevents duplicates; and the only expressible actions are benign, reversible reminders and pending bookings. The defect is a violation of the phase's stated "confirmation recomputes and validates the complete preview" / "stale data invalidates confirmation" / "exact preview + explicit confirmation" guarantees on the resume path specifically — a confirmation-integrity gap rather than an exploitable escalation.

**Suggested direction (do not implement here):** on resume, re-derive and compare a hash of just the *resolved action inputs* (excluding step statuses, which legitimately change after a partial run) against a value stored/derived at confirm time, and force `preview_stale` (re-preview) when the action targets differ from those the user confirmed. This preserves same-set idempotent retry while rejecting drifted or client-swapped targets.

### Low

**L1 — Raw ISO timestamps rendered in the confirmation card.** `WorkflowConfirmation` prints `action.booking.scheduled_at` and `item.scheduled_at` as raw ISO strings inside `<bdi>` ([assistant-chat.tsx:573](../../components/assistant/assistant-chat.tsx#L573), [assistant-chat.tsx:581](../../components/assistant/assistant-chat.tsx#L581)) rather than a locale/timezone-formatted, digit-aware date. Functionally correct and RTL-safe, but inconsistent with the clinic-locale formatting used elsewhere (`formatScheduledAt`). Preview readability polish only.

**L2 — All non-`WorkflowPlanError` failures in the confirm action collapse to `reason: "denied"`.** [actions/assistant-workflows.ts:54](../../actions/assistant-workflows.ts#L54) maps any thrown error (including a genuine internal/DB failure) to `denied`, which the UI renders as `workflowConfirmationFailed`. Fail-closed and safe, but a transient infrastructure failure is presented to the user as an authorization denial. Consider distinguishing an internal-error state for clearer UX/telemetry.

**L3 — Previewed action runs have no expiry.** A `previewed` run remains confirmable indefinitely. This is safe today because first-confirmation recomputes the snapshot and rejects drift, but there is no upper bound on preview age. Informational; a TTL is not required for staff-initiated workflows (unlike the P5 patient-booking hold TTL).
