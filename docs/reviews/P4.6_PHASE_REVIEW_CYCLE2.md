## Final Verdict: **NOT APPROVED — TWO REQUIRED FIXES**

The phase-review-#1 fixes are, with one important exception, real and well made. The database boundary now knows about entitlements and per-user grants (M1/M2 of review #1 — I confirmed both at the PostgREST boundary with a real manager token). The audit wrapper genuinely closes the denial/clarification/error blind spot at the mount boundary rather than per tool. Field-aware sanitization caps, the `cap + 1` row-count fix, `acceptsDoctor`, the `AiUserPermissionKey` typing, the `unavailable` capability state, and the L9 grant hardening are all correctly implemented and covered.

**All 21 findings from review #1 were re-verified. Nineteen are fully closed. One (H1) is closed in substance but rests on a factually incorrect premise, and two of its five sub-fixes are unreachable code (see H2). One (L11) is closed only at the application layer and is bypassable at the database boundary (see M1).**

Two findings must be fixed before P4.6 is considered done:

- **H1** — `ai_get_patient_stats`'s complementary suppression labels **above-floor buckets as `"<5"`**. A clinic with 200 O+ and 3 A+ patients is told *both* groups have fewer than five. The staff prompt instructs the model to state returned values exactly, so the assistant confidently reports a false figure. Reproduced live.
- **H2** — A tool that throws mid-stream **never reaches the client's error state**. The AI SDK routes a tool `execute()` throw to a `tool-output-error` part, not to a stream-level error, so `useChat`'s `error` is never set. Review #1's H1 fixes #3 and #4 (the route's `onError` reason code, and the client's typed `ERROR_COPY_KEYS` table) are unreachable for the transport they were written for.

Three Medium, eight Low, and three Info findings follow. **No finding in this review is a cross-tenant data leak, and no finding is a privilege escalation beyond what the same actor already holds.**

## 2. High Findings

### H1 — Complementary suppression labels above-floor buckets `"<5"`, and the prompt guarantees the assistant repeats it

`supabase/migrations/20260720130000_p46a_staff_analytics.sql:415-445`, `lib/ai/prompts/staff.ts` (both locales)

Review #1's H1 fix introduced complementary suppression: after primary suppression hides every bucket below the floor, the loop keeps extending the suppressed prefix until at least two buckets are hidden **and** their sum reaches the floor. That is the correct privacy construction, and I agree with it.

The defect is in how the extended suppression is *rendered*. The emit loop treats membership in the suppressed prefix as equivalent to being below the floor:

```sql
when v_index <= v_suppressed
  then jsonb_build_object('count', null, 'display', '<' || v_floor, 'suppressed', true)
```

A bucket suppressed *complementarily* is not below the floor — it was suppressed to protect a different bucket. Labelling it `"<5"` states something false about the data.

**Reproduced live** (clinic with 3 A+ and 200 O+ patients, `p_group_by: 'blood_type'`, admin token, `pro_ai`):

```json
"buckets_all_time": [
  { "bucket": "O+", "count": null, "display": "<5", "suppressed": true },
  { "bucket": "A+", "count": null, "display": "<5", "suppressed": true }
],
"suppressed_bucket_count": 2,
"patients_total_approx": 205,
"patients_total_exact": false
```

The O+ bucket holds **200** patients and is reported as `<5`.

Two things compound this into a user-facing wrong answer rather than an internal oddity:

1. **The prompt mandates verbatim relay.** Both locales say *"state the values exactly as returned. Suppressed groups appear as `<5` — never infer their size."* The model is explicitly forbidden from correcting the figure and explicitly instructed to report it. An admin asking for the blood-type distribution is told every group has fewer than five patients, alongside an approximate total of 205.
2. **`patients_total_approx: 205` next to two `<5` buckets is internally inconsistent** in a way an attentive user will notice and an inattentive one will not. It reads as a broken tool, which erodes trust in the numbers the phase is built to deliver.

There is also a usability consequence independent of the wrongness: any clinic with one rare category — which for `blood_type` is the *common* case, and is also common for `department` and `assigned_doctor` — loses its entire distribution. The tool returns nothing usable in its most typical configuration.

**Why the test suite does not catch it.** `tests/unit/integration/p46a-analytics-rpc-isolation.test.ts:194-203` uses a fixture of 6 O+ and 2 A+ and asserts only that the A+ bucket is suppressed. Under that fixture O+ is *also* suppressed complementarily, so the assertion passes while the whole distribution is hidden. The test would pass identically if suppression hid everything unconditionally.

**Suggested direction (not applied):** distinguish the two suppression reasons in the payload — e.g. `display: "<5"` with `suppression_reason: "below_floor"` for primary, and a non-numeric `display` (`"hidden"`) with `suppression_reason: "complementary"` for the rest — and give the prompt a matching rule. Separately, consider whether suppressing *every* bucket is the right terminal behavior or whether the tool should decline the grouping and say so.

### H2 — A tool that throws mid-stream never reaches the client's error state; two of review #1's H1 fixes are unreachable code

`app/api/agent/chat/route.ts:167-186`, `components/assistant/assistant-chat.tsx:73-104,427`, `lib/ai/errors.ts:18-32`, `node_modules/ai/dist/index.mjs:2911-2954,8472-8482,6109-6137,6176-6178`

Review #1's H1 asserted that a tool throwing inside the model loop *"lands in `toUIMessageStreamResponse`'s `onError`"* and is rendered as `error.message` on the client. The fixes report acted on that premise: it made `onError` return `error.reason`, and moved the client's copy table to a typed `Record<AssistantErrorCode, string>` keyed off that message.

**The premise is wrong, and I verified it against the SDK source rather than the mocked tests.**

In `ai` v6, a client-executed tool whose `execute()` throws is caught inside `executeToolCall` and converted to a `tool-error` content part (`index.mjs:2936-2954`). It is *not* a stream error. The UI-message stream then emits it as a **`tool-output-error` chunk** (`index.mjs:8472-8482`), and the client handler for that chunk (`index.mjs:6109-6137`) only calls `updateToolPart({ state: "output-error", errorText })`. It never invokes the chat's `onError`. Only the separate stream-level `error` chunk does (`index.mjs:6176-6178`).

`onError` *is* still called — as the `errorText` formatter at `index.mjs:8477` — so the route's `return error.reason` does execute and the reason code does travel. But it lands as `errorText` on a **tool part**, where:

- `useChat`'s `error` stays `undefined`, so `errorCopy` at `assistant-chat.tsx:427` is `null` and **the error banner never renders**;
- `ERROR_COPY_KEYS` is never consulted for this transport;
- `ToolActivity` renders the `output-error` state as a bare `t("toolFailed")` chip with **no reason, no guidance, and no localized copy** — the reason code is discarded by the UI entirely;
- the raw code string (`"permission_not_granted"`) is fed back into the model's context as the tool's error text, so the model improvises an explanation from an untranslated internal identifier.

**Why the tests do not catch it.** `tests/unit/api/p4b-chat-route.test.ts:288-300` calls `options.onError(new AiToolAuthorizationError("permission_not_granted"))` directly and asserts the return value. That proves the function body, not the transport. No test drives a real tool throw through `streamText` to the client.

**Practical impact is bounded but real.** `run_clinic_report`'s financial denial — the case review #1 was actually chasing — is fixed properly by returning a structured result (fix #1/#2/#5), and that path renders a correct localized `permission_denied` notice. What remains unreachable is every *other* mid-stream denial:

- `role_forbidden` from `run_clinic_report`, which the fixes report says *"keeps throwing, deliberately"* on the stated understanding that the transport carries a reason — it does not;
- a grant revoked, page hidden, subscription lapsed, or entitlement removed between mount and `execute()`, for any of the 15 tools;
- `lookup_failed`, which the fixes report says *"must fail closed and loudly"* — it fails closed, but silently.

Each renders as a grey "couldn't complete that step" chip. Authorization holds throughout; this is a state-communication defect, and it is the same defect review #1's H1 named, one layer further down.

**Suggested direction (not applied):** treat the tool-part error state as a first-class UI state — parse `errorText` against `AssistantErrorCode` in `ToolActivity` and render the same localized copy `noticeText` already has for `permission_denied`. The `ERROR_COPY_KEYS` table and the `AssistantErrorCode` union are the right abstractions; they just need to be consulted on the transport that actually carries tool denials. A test that drives a throwing tool through the real SDK is what would have caught this and would keep it caught.

## 3. Medium Findings

### M1 — Any admin, not only the primary admin, can grant the financial permission directly over PostgREST

`supabase/migrations/20260720130000_p46a_staff_analytics.sql:126-149`, `actions/ai-permissions.ts:62-65,151-155`

L11 of review #1 observed that the settings page required `isPrimaryClinicAdmin` while the server actions required only `admin`, and asked the two layers to state the same rule. The fix tightened both actions to the primary admin — correctly.

RLS was not tightened. The `"Admins can manage clinic ai permissions"` policy is `for all` with `p.role = 'admin'` and a clinic match, and no primary-admin condition. So the strict rule remains reachable only through the application.

**Reproduced end-to-end** against the live stack, with a clinic holding two admins and one manager:

1. The **non-primary** admin, using their own session token, `POST /rest/v1/user_ai_permissions` with `{user_id: <manager>, permission_key: "ai.financial_insights", granted: true}` → **succeeded** (`error: null`).
2. The manager, whose RPC was refused moments earlier, then called `ai_get_revenue_summary` → **succeeded**, returning the clinic's revenue aggregate.

So the bypass is not merely a write that lands somewhere inert: the row written by the unauthorized-per-policy admin is fully honored by the M1 database guard that the same fix cycle added.

Two things keep this Medium rather than High. A manager cannot self-grant — I confirmed the RLS policy refuses it (`42501`). And a non-primary admin already reads every financial page and could change the manager's role outright, so no data becomes reachable that this actor could not already reach or arrange.

But it is the *same class* of gap the phase just spent a cycle closing on the analytics RPCs, and it is now the only place in P4.6 where an authorization rule the product states is enforced in exactly one layer. Review #1's own framing applies unchanged: *"each layer must deny independently or it is not defense in depth."* The `updated_by` column also becomes misleading — it will name the non-primary admin for a grant the product claims only the primary admin can make.

**Suggested direction:** add the primary-admin predicate to the policy's `using`/`with check`, mirroring the `assert_primary_ai_provider_admin` authority the P4.5B migration already established and which `lib/primary-admin.ts` is documented as staying byte-for-byte aligned with.

### M2 — Any tool error fails the whole turn: the conversation is not persisted and the execution is billed as failed, even when the model recovered

`app/api/agent/chat/route.ts:163,167-168,187-200`

`onError` sets `streamFailed = true`, and `onFinish` then takes the failure branch: `finalizeExecution("failed", "stream_failed")` and — critically — an early `return` that skips `persistDoctorTurn`.

Per H2, `onError` is invoked for **every** tool-error part, not only for stream-fatal errors. But a tool error is not fatal to the turn: the SDK feeds it back to the model, which typically apologizes, tries another tool, and produces a complete, correct answer. The user watches that answer stream to completion.

The turn is then discarded. On the next page load the conversation has no record of it — the user's question and the assistant's answer are both gone — and the AI usage ledger records a `failed`/`stream_failed` execution for a turn that visibly succeeded.

This mechanism predates P4.6 (`streamFailed` is unchanged in the diff), but P4.6 is what makes it likely: the phase takes the tool count from 5 to 15, puts most of them on database round-trips that throw `new Error("… lookup failed.")`, adds entity resolution that throws on RPC failure, and deliberately retains `role_forbidden` and `lookup_failed` as mid-stream throws. Recording it here because it is a P4.6-amplified interaction between the route, the registry, and the audit ledger that no single sub-phase review would see.

**Suggested direction:** distinguish a fatal stream error from a recovered tool error. The SDK gives the signal — `finishReason` and the presence of assistant text are already checked in the same condition; the tool-error case is the one where `assistantText` is non-empty and `finishReason` is not `"error"`.

### M3 — `financialDenialReason` runs the analytics gate twice, and swallows a class of denial it should surface

`lib/ai/tools/run-clinic-report.ts:175-191,241-273`

`assertFinancialInsightsAccess` internally calls `assertAnalyticsToolAccess`, which itself calls `assertStaffToolAccess`. For a financial report the tool therefore runs the full staff spine, the operational role check, the analytics entitlement, the financial role check, the financial entitlement, and the grant read — and `financialDenialReason` catches only two of the reasons that chain can raise, re-throwing the rest.

That re-throw is correct in intent, and `lookup_failed` genuinely should fail loudly. But per H2 the loud failure is inaudible: it renders as a bare "couldn't complete that step" chip. So the three denials the chain can raise that are *not* `permission_not_granted` / `feature_not_entitled` — `page_hidden`, `subscription_inactive`, and `lookup_failed` — reach the user as the same unexplained chip, having deliberately avoided the structured-result path that would have rendered them.

`page_hidden` and `subscription_inactive` are as user-actionable as the two that are handled, and are more likely mid-conversation than the financial grant flipping, since both can change from an admin screen while a session is open.

The duplicated gate execution is minor by comparison (both reads are `cache()`-memoized per request), but it is worth noting that the non-financial branch calls `assertAnalyticsToolAccess` while the financial branch reaches it transitively — an asymmetry that reads as an omission on first inspection and needs the reader to trace three files to confirm it is not.

## 4. Low Findings

**L1 — The deployment runbook's blocking-statement table omits one of the four index builds.** `docs/runbooks/P4_6_MIGRATION_DEPLOYMENT.md:15-19` lists `idx_patients_search_name_trgm` as the only index build in `…120000`. The migration also builds `idx_patients_search_phone` (btree, `…120000:99-101`), which holds the same `SHARE` lock. The migration's own comment is accurate (*"the two `create index` statements below"*); the runbook, which is what the operator actually follows, is not. The "build concurrently instead" section correspondingly lists three statements to comment out when there are four. An operator following it literally would leave one blocking build in place.

**L2 — `normalize_search_text` and `normalize_phone` are still granted to `PUBLIC`.** `…120000:63-64` uses a bare `grant execute … to authenticated, service_role` with no preceding `revoke from public`, and `pg_proc.proacl` confirms `=X/postgres` on both — i.e. `anon` may execute them. They are `immutable`, pure, and touch no data, so there is no exposure. But L9 of review #1 hardened the four `search_*_ranked` functions for exactly the consistency argument that *"an inconsistency inside one feature is the kind that gets copied into the next function by someone reading the file for a pattern"* — and these two are in the same file, one section above.

**L3 — RLS on `user_ai_permissions` has no role check, so grant rows can be written for roles that can never use them.** Confirmed live: an admin successfully inserted an `ai.financial_insights` grant for a **doctor**. The row is inert — the doctor is refused by the registry, by `assertFinancialInsightsAccess`, and by `ai_assert_analytics_caller`'s role matrix (I confirmed the RPC returns `42501 "Not authorized for clinic analytics"`) — so this is not an access path. It is a data-integrity gap: `GRANTABLE_ROLES` in `actions/ai-permissions.ts:39-41` is the only thing keeping the table's contents meaningful, and a stale grant row surviving a role change (manager → receptionist) will silently re-activate if that user is ever promoted back.

**L4 — `exact_name` evaluates to `NULL` rather than `false` whenever `p_query_alt` is absent.** `…140000:165` — `c.search_name in (v_query, v_query_alt)` is three-valued: with `v_query_alt IS NULL` and no match on `v_query`, the result is `NULL`, not `false`. Every consumer happens to handle it correctly (`NULL` in the score `CASE` falls through; `false OR NULL` in the final `WHERE` excludes the row, which is the same outcome the score filter would reach), so there is no defect today. But the correctness depends on two separate expressions coincidentally tolerating a `NULL` the author did not intend, and the neighbouring `prefix_name` guards the same case explicitly. `c.search_name = v_query or (v_query_alt is not null and c.search_name = v_query_alt)` would make the intent match the behavior.

**L5 — `withProvenance` still mis-frames a clarification that carries no `candidates` key.** `lib/ai/untrusted-text.ts:200-206` requires `Array.isArray(result.candidates) && length === 0` to classify a clarification as system-authored. `filterClarification` always sets `candidates`, so today this holds — but a future clarification-shaped result that omits the key entirely gets the tenant framing (*"records entered by clinic staff"*) for a payload we authored. The L7 fix is right; the predicate is one shape narrower than the rule it encodes.

**L6 — `verifiedId` is `async` and awaits nothing.** `lib/ai/tools/entity-filters.ts:66-75`. Cosmetic, but it makes the function look like it performs the verification it is named for, when the caller does the read and this only classifies the result.

**L7 — The `run_clinic_report` doctor-filter description enumerates report ids the caller may not be able to run.** `run-clinic-report.ts:226-229` hardcodes *"Only cancellations, no_shows, revenue, and doctor_performance use it"* — including `revenue` for a manager whose grant is off, whose `allowed` list two lines earlier deliberately excludes it. Far milder than review #1's H1 (it describes a *parameter*, not an offer), but it is the same string re-introducing the same name into the same model context, and it is not derived from `REPORTS[].acceptsDoctor` the way the rest of the fix is.

**L8 — The `patients_total_approx` rounding can exceed the true total.** `…130000:453-455` uses `round(v_total / v_floor) * v_floor`, which rounds to nearest — 203 patients is published as 205. That is the correct choice for the privacy property (a floor would leak a lower bound), but nothing in the payload or the prompt says the approximation may be *higher* than the truth, and `noticeApproximateTotal`'s copy says only "the total shown is rounded". A user reconciling 205 against a patients page showing 203 has no way to know which is wrong.

## 5. Architecture, Security, Authorization & RLS

**The five-authority model now genuinely holds at all five layers, and I verified the database one rather than reading it.** For `ai_get_revenue_summary` a caller must satisfy: the registry (`roles` + `requiredFeatures` + `requiredUserPermission`), `assertFinancialInsightsAccess` in `execute()`, `ai_assert_analytics_caller('financial')` in the database, RLS on the underlying tables, and the surface gate. The `…150000` migration moved the third of those from "role only" to "role + entitlement + per-user grant", which was the central structural weakness review #1 identified, and it is correctly placed in the one guard all five RPCs pass through.

`effective_ai_feature` being executable only by `postgres` is exactly right, and is what makes calling it from a `SECURITY DEFINER` guard a strengthening rather than a new surface. Every P4.6 DEFINER function is `stable`, sets `search_path = ''`, schema-qualifies operators as well as functions, and revokes from `public` before granting.

**Identity remains server-derived throughout.** No tool accepts a clinic id, actor id, or role; no aggregate RPC takes a tenant parameter; `verifiedId` closes the model-asserted-uuid path; `resolveToolMount` builds `grantedPermissions` from server reads and the tool only ever *reads* that set for presentation.

**The one authorization rule enforced in a single layer is now the primary-admin grant rule (M1)** — a reversal worth naming, since before this cycle the single-layer rules were in the database's blind spots and now the sole one is in RLS's.

`describedByUserPermissions` is a good addition: it makes "this permission changes what I say, not what I may do" a declared property rather than a comment, and `resolveToolMount` resolving the union of required-and-described keys avoids issuing a financial read on a doctor's mount. Both the declaration site and the consumption site say it is presentation-only.

## 6. Prompt-Injection & Privacy

The three-layer model is unchanged from review #1 and remains honestly framed. The field-aware cap (M7) is implemented the right way round — matching on the **key**, which we author, never the value, which tenants author — and that distinction is stated at the declaration. `text_truncated_fields` closing the silent-truncation gap is a genuine improvement to the honesty pipeline rather than a gesture, and it is rendered as a user-visible notice, not only handed to the model.

The M5 masking is well judged: identity (`full_name`, `file_number`) is what a user disambiguates on, and it is untouched; contact details now require a single high-confidence match. `contact_details_withheld` on the payload plus the description sentence means the model can explain the absence rather than appearing to have lost data.

**Privacy regression: H1 is a privacy control that has become a correctness defect.** The suppression *construction* is sound — I traced the primary and complementary loops and agree that the subtraction attack is closed at the source — but the rendering makes the tool state falsehoods about the population, which is a different and in some ways worse failure than the one it fixed. A tool that is wrong is not private-and-useful; it is just wrong.

Residual: `bucket_scope: 'all_time'` continues to be handled well (explicit field, `all_time_scope` notice, and a prompt rule against describing buckets as belonging to the range).

## 12. Summary

P4.6 is architecturally strong and the review-#1 fix cycle was, in the main, done properly: the database boundary now enforces entitlements and per-user grants (verified live at PostgREST, not inferred), the audit ledger covers every invocation class at the one boundary that cannot be forgotten, and the sanitization, row-cap, capability-state, and permission-key fixes are each correct and tested. Nineteen of twenty-one findings are fully closed with no regressions.

The two required findings share a root cause worth naming plainly: **both are fixes that were validated against a model of the system rather than the system.** H1's suppression logic is provably correct as privacy mathematics and was never checked against what it actually prints — a live call shows a 200-patient bucket rendered as `<5`, under a prompt that instructs the model to repeat it verbatim. H2's transport fix was validated by calling `onError` directly, which proves the function body while leaving untested the one claim the fix depends on: that a tool throw reaches `onError` as a stream error. It does not. In both cases the test suite passes, and passes *because* the assertion was written against the same assumption as the code.

M1 is the third instance of the same pattern in a milder form — a rule tightened in the layer that was reviewed, left open in the layer that was not, and confirmed bypassable in two HTTP calls.

The corrective for all three is the one this phase already applies well elsewhere: `resolveToolMount` is trustworthy because the UI and the model read *one* resolution, and `ai_assert_analytics_caller` is trustworthy because all five RPCs pass through *one* guard. The same discipline applied to the assertions — exercise the real transport, the real renderer, the real policy — is what would have caught every finding in this review.
