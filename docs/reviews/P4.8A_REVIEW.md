## 1. Findings

### P48A-M1 — Closed launchers eagerly load and serialize the full assistant session

**Severity:** Medium  
**Category:** performance / UX / scalability  
**Files:** `lib/ai/launchers.ts:143-157`, `lib/ai/conversations.ts:8-8`, `lib/ai/conversations.ts:51-68`, `lib/ai/conversations.ts:72-102`, `components/assistant/assistant-launcher.tsx:6-6`, `components/assistant/assistant-launcher.tsx:93-103`

Every authorized dashboard, appointments, or patient-page request resolves the latest conversation and loads up to 40 persisted messages before the user opens the Sheet. The launcher also imports and renders the complete `AssistantChat` client tree inside the initially closed Sheet. P4.8A therefore expands the existing patient-page cost to the dashboard and appointments page, including:

- conversation and message-table reads on every authorized page request;
- capability resolution on dashboard and appointments requests;
- serialization of up to 40 messages into the page payload;
- eager delivery/hydration of the chat UI on two high-frequency pages even when the launcher is never opened.

This is not an authorization or correctness defect, and the work is started in parallel with the main page queries. It is nevertheless an avoidable regression in page payload, database work, and client JavaScript on core surfaces.

**Required remediation:** split launcher visibility from session hydration. Resolve only the lightweight role/page/entitlement/usage gate during page rendering, then load the conversation, capability payload, and chat client on first Sheet open through an authenticated server boundary. Dynamically split the chat UI as part of the same change. Preserve the current independent chat-route and tool authorization checks. Add coverage proving that a closed launcher does not query `agent_messages` or serialize conversation history, plus a measured page-payload/bundle comparison for dashboard and appointments.

### P48A-L2 — Resolver and P4.8B source tests overstate several untested branches

**Severity:** Low  
**Category:** test completeness / regression protection  
**Files:** `tests/unit/ai/p48a-launchers.test.ts:62-197`, `tests/unit/components/p48a-entry-points.test.ts:9-29`, `docs/reports/P4_8A_IMPLEMENTATION.md:76-85`

The new suite is substantial and covers the security-critical patient reauthorization and live cross-tenant denial path. However, the report's coverage description is broader than the executable assertions:

- visibility tests make only the Assistant page hidden/failed; they do not separately exercise a hidden or failed source-page lookup;
- the optional `requiredUserPermission` resolver branch is not exercised;
- the generalized multi-feature surface gate is not tested with more than the legacy Assistant feature;
- the source-level P4.8B absence test checks revenue, reports, and staff only, not departments or the invoice/doctor-schedule host components;
- page entry-point tests are source-string assertions rather than rendered server-entry tests, so the resolver role matrix—not an end-to-end page render—proves visibility behavior.

These are regression-protection gaps, not evidence of a current bypass. Repository-wide inspection confirmed that only patient, appointments, and dashboard entry points are wired.

**Required remediation:** add fail-closed cases for both source-page `hidden` and `lookup_failed`; cover a multi-feature entitlement requirement and the optional user-permission branch; enumerate every P4.8B host surface in the absence contract; and add at least one rendered/server-entry test per P4.8A area showing authorized presence and unauthorized absence.

## 2. Architecture and correctness verification

### AssistantPageContext trust boundary

**Pass.** `lib/ai/page-context.ts` defines one strict zod discriminated union. Objects reject unknown keys; UUIDs are syntactically validated; appointment statuses and report/filter values are closed enums; calendar dates are checked for real dates; ranges must be ordered and no longer than 400 days. Malformed or unknown context is dropped rather than allowed to affect a valid turn.

The browser transmits only the typed contract. Patient names remain a presentation-only `contextLabel` and are not included in `buildAssistantChatRequestBody`.

### Independent server validation and authorization

**Pass.** `app/api/agent/chat/route.ts` reparses the untrusted request independently. Patient context alone is passed into `ensureDoctorConversation`. That function requires a doctor, scopes an existing conversation by clinic and owner, rejects patient/conversation mismatches, reselects a new patient through the authenticated RLS client, scopes by clinic, excludes deleted records, and enforces assigned-doctor-or-department access. The route then rebuilds the effective patient context from the authorized conversation result before prompt or tool construction.

Appointments, dashboard, and validation-only future variants remain ephemeral prompt metadata. They do not enter conversation patient scope and do not alter the server-derived user, clinic, task classification, execution policy, or tool context. Closed enums, UUIDs, and date values also prevent free-text prompt injection through the context object.

### Launcher registry and resolver

**Pass.** `ASSISTANT_LAUNCHER_REGISTRY` contains exactly patient, appointments, and dashboard. Unknown and P4.8B context types are rejected before any visibility lookup. Every registered definition declares roles, source page, required features, and a code-owned enabled default.

The resolver fails closed on:

- absent registration or disabled default;
- role mismatch;
- hidden or failed Assistant/source-page visibility;
- inactive subscription or missing feature;
- usage-cap or usage-lookup failure;
- missing persistence;
- a declared per-user permission denial;
- any operational exception.

Launcher visibility remains an affordance only. The chat API and every mounted tool independently repeat their authorization checks.

### Entry-point correctness

**Pass.** The patient launcher is doctor-only and is omitted for deleted or independently unauthorized patients. The appointments launcher appears only for admin, receptionist, and doctor—the roles that own that page—and its official server-rendered context includes the visible range, validated status, and only a same-clinic cached doctor selection (or the authenticated doctor's own ID). Dashboard launchers are resolved once from server-owned identity and rendered for all four dashboard roles.

The shared Sheet uses one reusable localized component, logical `inline-end` placement, unique accessible descriptions, localized titles/copy, and responsive action wrapping.

## 4. AI-platform regression review

### Billing, usage, and provider execution

**Pass.** Task/persona classification still depends on the authenticated role, entitlement, and user message—not page context. `prepareAiExecution` still reserves before model work; the existing execution object still supplies model, provider options, step limits, token limits, and reconciliation. Success, failure, abort, and recovered-tool-error finalization paths remain intact. Context cannot change the budget, usage metric, provider route, credential mode, model alias, or fallback policy.

### Audit logging

**Pass.** Page context performs no data operation and therefore creates no new audit event. Every actual tool still passes through the existing hardened registry wrapper and its per-tool audit path. No tool execution path was bypassed.

### Usage limits and surface gates

**Pass.** Launcher visibility checks subscription, feature entitlement, usage availability/cap, and persistence. The chat route still performs its normal authorization, rate limit, and atomic execution preparation independently. A hidden launcher does not imply API permission, and a visible launcher does not grant it.

### Tool mounting and capabilities

**Pass.** `createStaffAgent` derives `patientId` only for a doctor with authorized patient context. Non-patient context is not supplied to `buildStaffTools`. The existing task-class, role, feature, and user-permission registry resolution therefore remains authoritative. Dashboard and appointments capabilities are display metadata derived from that same mount resolver.

## 5. Maintainability and roadmap compliance

The implementation has good structural separation: validation/prompt projection, launcher metadata/resolution, reusable UI, route authorization, and tool mounting remain distinct. The current sub-phase is explicitly typed as `P48AAssistantPageContext`, while the stable full protocol can accept later roadmap variants without registering them as entry points.

The roadmap and report accurately describe the material delivered scope. P4.8A contains the context contract, reusable launcher, registry/resolver, and patient/appointments/dashboard entry points. No P4.9 customization schema or placement settings were introduced.

**P4.8B was not implemented.** There are no launchers on revenue, reports, invoices, staff, departments, or doctor-schedule surfaces, and `suggestionsFor` remains context-independent. The full union and prompt projection for future variants are protocol preparation owned by P4.8A; those variants are absent from the launcher registry and therefore cannot create an entry point.
