## 1. Required findings

### FR-M1 — P47-M5 remains open: the corpus still misstates manager access to patient files

**Files:** `lib/ai/help/corpus.ts:88-141`, `lib/page-permissions.ts:40-45`, `lib/supabase/middleware.ts:271-278`  
**Severity:** Medium  
**Category:** corpus accuracy / authorization honesty

The `register-new-patient` article says in English and Arabic that doctors **and managers** can view patient files but cannot create them. That conflicts with the shipped page-access contract:

- `ROLE_PAGE_SLUGS.manager` does not contain `patients`;
- middleware redirects a role whose page set excludes the resolved page slug to `/dashboard`;
- the adjacent `find-patient-file` article and its navigation target correctly exclude managers and explicitly document that managers have no Patients page.

The three statements corrected in the remediation report are accurate, but the broader P47-M5 requirement that the corpus describe only shipped behavior is still unmet. The added corpus contract test checks only the three previously named articles and does not cover this contradiction.

**Required remediation:** correct the `register-new-patient` note in both locales and add a contract assertion tied to the actual Patients role/page matrix so the statement cannot drift independently again.

### FR-M2 — P47-M1 is incomplete: the real primary-admin error path cannot produce `lookup_failed`

**Files:** `lib/primary-admin.ts:5-36`, `lib/ai/help/navigation.ts:664-674`, `tests/unit/ai/p47a-navigation-registry.test.ts:38-67`, `tests/unit/ai/p47a-navigation-registry.test.ts:168-195`  
**Severity:** Medium  
**Category:** primary-admin navigation honesty / test fidelity

Secondary-admin handling is correct: both `settings_ai` and `settings_customize` declare `requiresPrimaryClinicAdmin`, a secondary admin receives no route or actionable steps, and batch resolution shares the lookup.

The lookup-failure handling claimed by the remediation report is not reachable for an ordinary database error, however. `getPrimaryClinicAdminId` converts a Supabase query error to `null`; `isPrimaryClinicAdmin` then converts that to `false`. The navigation resolver interprets `false` as a verified secondary admin and returns `primary_admin_required`. Its `lookup_failed` branch runs only when the helper rejects or throws.

The new test mocks `isPrimaryClinicAdmin` to throw. That proves the resolver's catch branch, but it does not model the shared helper's real database-error contract. The result still fails closed and exposes no link, so this is not an authorization bypass; it is a false authorization diagnosis and leaves the P47-M1 failure contract/test claim incomplete.

**Required remediation:** preserve a distinct lookup-failure result through the primary-admin helper/resolver boundary, and test the real helper contract or a faithful tri-state result instead of testing only an artificial thrown error.

### FR-L1 — P47-L2 is incomplete: the committed Axe flow does not cover RTL

**Files:** `tests/e2e/p4b-assistant.spec.ts:96-128`, `tests/unit/components/p46b-assistant-analytics-ui.test.tsx`  
**Severity:** Low  
**Category:** RTL/accessibility coverage

Direct component coverage now verifies open/close behavior, ARIA state, grouped rendering, Arabic capability content, the empty state, long-list scrolling, focus restoration, and destination-specific links. The authenticated Playwright flow expands the panel and runs Axe, but it does so only in the default English/LTR session. It neither switches the user to Arabic nor asserts an RTL document before running Axe.

P47-L2 specifically required browser/Axe coverage of the expanded panel in both directions. Rendering an Arabic description inside the English component fixture is not an RTL browser pass.

**Required remediation:** add an authenticated Arabic/RTL capability-panel Axe case and run both LTR and RTL cases when the local Supabase browser-test environment is available.

## 3. Capability-union and authorization verification

The corrected contract holds in the inspected implementation:

- `STAFF_TASK_CLASSES_BY_ROLE` defines the router-reachable staff task classes for each role.
- `resolveToolMount({ taskClass })` returns the narrower active-turn mount and rejects unsupported role/class pairings with an empty mount.
- `resolveToolMount` without `taskClass` returns the authorized union across only that role's supported staff classes.
- Both modes use the same registry role, feature, task-class, and per-user-permission gates.
- `resolveAssistantCapabilities`, the capability panel, and `list_my_capabilities` derive from that unscoped registry resolution.
- The model-facing payload explicitly identifies `capability_scope: "authorized_task_class_union"` and warns that a turn may mount only a subset.
- Roadmap text, implementation reports, comments, English/Arabic UI copy, and tests state the same union/subset semantics.
- For admin, manager, receptionist, and doctor fixtures, every active mount is a subset of the displayed union and the union of all supported mounts equals it exactly.
- Missing entitlements, missing manager financial grants, ineligible roles, and unsupported task classes remove capabilities rather than exposing them.

No unauthorized capability was found in the panel or tool payload. Tool execution remains independently protected by the existing staff, role, entitlement, per-user permission, and RLS boundaries.
